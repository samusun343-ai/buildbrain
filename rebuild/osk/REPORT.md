# OSK v2（入力統合）レポート

対象: スクリーンキーボード＋文字入力・変換・物理キーボードの統合（独自実装）。
前提の監査判定: 旧 `bui_osk` はローマ字→ひらがな表止まりで廃棄。本実装は新規。
**これは「完成」ではない。** 統合フェーズ（実セッションへの組み込み、既定セッション化）と
実機/QEMU ゲスト検証が残る。本レポートの数値は全てホスト実測。

### 入力モード（4つ）
- **フリック（12キー）**: あ〜わ行＋記号キー＋濁点/半濁点/小字キー。タップ=中央、
  上下左右フリック=段の文字（分類は純関数 `osk_flick_classify`、閾値 14px）。
  キーは高さ 60px・幅 約134px（≥56px 要求を満たす）。
- **トグル連打**: 同じ12キーで あ→い→う→え→お と循環（フリックも併用可）。
  **タイマーを使わない決定方式**（別キー/確定/削除で封止）— §6-2 参照。
- **QWERTY ローマ字**: 画面キーも物理キーも同じローマ字状態機械
  （`osk_romaji`、約120規則: shi/chi/tsu、ky系拗音、促音、撥音、x/l 小字、ゔ、句読点）。
- **50音表**: 10行×5列（セル高 48px。50セルを収めるための意図的な逸脱として明記）。
- **数字・記号**: 2ページ（数字・全角記号 / 英大文字・ASCII記号）、末尾セルがページ切替。

### 編集キーと変換フロー
候補バー（第0文節の候補、タップで選択=DOWN 時点で確定反映）、変換キー/スペースで
次候補、↑↓で候補移動、←→は preedit 中は**文節伸縮**（`bi_session_resize`）、
確定は第0文節を `commit_first` で確定し残りを継続変換、削除は
「ローマ字バッファ→読み→対象バッファ」の順に作用、ESC で preedit 全取消。

### 統合経路
読みは OSK が保持し backend セッション（本番=libbrainime、未接続時=かなのみ
フォールバック）へ渡す。変換結果は対象 TextField/TextView に
`TK_EV_COMPOSITION`（preedit）として、確定分は `TK_EV_TEXT_INPUT` として配送され、
textcore の composition 機構で表示される。物理キーボードは OSK ウィジェットを
フォーカスしてキーイベントを流すことで**画面キーと完全に同じ経路**を通る
（テスト K 群で実証）。

## 3. 性能とサイズ（ホスト実測、`osk/bench_osk.c`）

| 段階 | VmRSS |
|---|---|
| プロセス開始 | 1,884 kB |
| エンジン open 後（辞書 1.94MB + bisc 7.86MB を mmap） | 5,556 kB |
| OSK セッション live 後 | 5,568 kB（**OSK 自身の増分は約 12 kB**） |
| 180 文変換後 | 11,104 kB（後述の通り頭打ち） |
| teardown 後 | 2,888 kB |

- RSS が変換で増える分は**リークでもフィクスチャ側でもなく、辞書/bisc の
  ページイン**であることを分離プローブで確認した: エンジン単体で同条件を回すと
  約30文で 10,512 kB に達して**その後 180 文まで完全に横ばい**、close で解放される。
  つまり常駐コストは「触れた辞書ページの working set」で決まり、変換回数では増えない。
- 再変換レイテンシ（OSK が `session_set_reading` 周りで自前計測）:
  bench 平均 3.43 ms / 最悪 61.6 ms（コールドページイン込み）。
  ウォーム後の分離計測では、文頭からの prefix 再変換（実際の打鍵パターン）
  平均 1.71 ms。最悪値のスパイクは未踏ページのフォルト由来。
  **ARMv5 実機/QEMU では当然これより遅くなる。実機計測は統合フェーズの課題**であり、
  ここで「爆速」とは言わない。
- 候補表示まで（入力→候補バーのレイアウト構築完了）: bench 平均 3.44 ms（同上コールド込み）。

## 4. コピー/オーバーヘッド削減のためにした設計判断

OSK→composition→TextField→libbrainime の経路で、コピーと再計算を以下の通り削った。
いずれも機能は削っていない（削ったのは無駄だけ）。

1. **変換結果文字列はコピーしない**: 以前は OSK 内に 1KB のコピーバッファを持っていたが、
   セッション所有の文字列へのポインタ保持に変えた。composition 配送は同期的で、
   受け側 textcore が自分のバッファへ取り込む**境界での1回だけ**が経路上の唯一の
   文字列コピー（OSK 側の中間コピーは 0）。
2. **レイアウトセルの文字列はポインタ**: 描画/ヒットテストのホットパスにある内部セルは
   ラベル・入力文字列をポインタ（静的表・リテラル・セッション所有の候補文字列）で持ち、
   コピーしない。候補文字列が 15 バイトで切れる旧設計の問題もこれで消えた。
   コピーが起きるのは公開 `tk_osk_layout()` のスナップショット変換時だけ
   （呼び出し側が明示的に要求したときのみ）。
3. **ローマ字の一括フィードは再変換1回**: 文字列フィード（貼り付け相当、複数文字の
   TEXT_INPUT）は文字ごとに変換せず、読みへ蓄積して最後に1回だけ再変換する。
   ローマ字封止（pending の「ん」確定）も、呼び出し側が直後に sync する場合は
   そちらへ合流させ、二重変換を避ける（`osk_seal_romaji(sync=false)`）。
4. **読みバッファの長さを保持**: 追記パスが毎回 `strlen` で再走査しないよう
   `reading_len` を維持。削除は末尾オフセットを直接使う。
5. **候補幅の計測は1パス1回**: 候補バーの構築は、各候補の幅をローカル配列に
   1回だけ測ってからセル化する（旧方式は溢れた場合に全候補を再計測して作り直していた）。
   さらにレイアウトキャッシュ（§5）により、再計測自体が読み変化時しか起きない。
6. **候補「選択」は再構築ゼロ**: 候補タップ/変換キーは候補リストもレイアウトも
   変えないため generation を上げない。次回描画はキャッシュ済みセルを再利用し、
   変わるのはハイライトと対象の composition だけ（テスト L 群で再構築カウンタにより実証）。
7. **イベントごとの再計算なし**: POINTER_MOVE はレイアウトに触れない。
   POINTER_DOWN/UP もキャッシュ済みセルへのヒットテストのみ。
8. 残るコピー（理由付きで残したもの）: OSK の読み文字列とセッション内 preedit は
   別所有のため `session_set_reading` で1回コピーされる（backend の API 境界）。
   確定/文節伸縮のときだけ、セッション側 preedit を OSK の読みへ書き戻す1回。
   どちらも打鍵ごとではなく操作単位であり、現時点では API 境界として妥当と判断。

## 5. キャッシュ/メモリ管理の方針

- **上限と追い出し方針（全キャッシュ明示）**:
  - レイアウトキャッシュは2系統に分離: 候補バー側（上限 40 セル）とキーグリッド側
    （上限 160 セル）。どちらも**固定サイズ配列**で、追い出しは generation 無効化による
    窓ごと差し替え（蓄積型ではないので LRU 等は不要、という設計判断）。
    実測最大はグリッド 55 セル（50音）/ 候補バー約 12 セルで、上限には十分な余裕がある。
  - 候補の計測対象は先頭 96 件まで（バー表示の窓）。96 件超の候補も変換キーの
    巡回では到達可能（表示窓の制限であり機能制限ではない）。
  - 読みバッファは 512 バイト固定（超過分は切り捨て。文節変換の実用長に対して十分）。
  - 学習履歴は 4,096 ペアでハードキャップ（§6-1）。bonus 自体も 10 回分で頭打ち（従来仕様）。
  - **時間ベースの追い出し・有効期限は一切使わない**（§6-2: 時刻が信用できないため）。
- **差分更新**: 候補更新は候補バー側キャッシュだけを再構築し、キーグリッドは再利用する
  （打鍵ごとにグリッド約 55 セルを作り直さない）。モード変更はその逆。
  再構築回数は診断カウンタ `tk_osk_layout_builds()` で観測可能にし、テストで回帰を検出する。
- **メモリ管理**:
  - OSK の状態は**単一 calloc**（固定バッファ＋キャッシュ配列を含む）。入力ホットパスでは
    **ヒープ確保を一切しない**（ローマ字出力はスタック、読み追記は固定バッファ内 memcpy、
    レイアウトは固定配列への書き込み）。確保はウィジェット生成時とセッション生成時のみ。
  - 辞書は libbrainime が **mmap 読み取り専用**で開くため、複数プロセス
    （シェル/グリーター/将来の fcitx アドオン）でページを共有でき、常駐コストは
    触れたページ分だけ（§3 の実測がその裏付け）。
  - **グリフ描画はツールキット共有のフォント/グリフキャッシュを使う**
    （`tk_canvas_draw_text` / `tk_text_width` 経由）。OSK 独自のフォント保持・
    グリフキャッシュは作らない（重複キャッシュの禁止）。
  - 候補・変換結果の「キャッシュ」は OSK 側に複製を持たず、セッション所有の
    実体へのポインタ参照のみ（§4-1）。二重三重の保持をしない。

## 6. 実機の現実への対応

### (1) ちょくちょくリセットする — 永続化の耐障害性
- **OSK 自身は永続状態を一切持たない**（読み・preedit・候補選択は全て揮発。
  リセットで消えるのは入力途中の文字列だけで、壊れるものはない）。
- 永続化が絡むのは libbrainime の**学習履歴**のみ。従来実装は
  「毎 commit、`fopen(path,"w")` で**その場で切り詰めて書き直し**」であり、
  書込み途中の電源断で履歴ファイルが壊れる方式だったため、本作業で差し替えた:
  - 保存は**原子的書換え**: `<path>.tmp` へ書き、`fflush`+`fsync` してから
    `rename` で差し替え、ディレクトリも `fsync`。電源断が起きても
    「旧ファイル全体」か「新ファイル全体」のどちらかしか残らない。
    残った `.tmp` は次回 enable 時に削除する。
  - 読込みは**末尾回復つき**: 完全な `\n` 終端行だけをデータとして扱い、
    電源断で切れた末尾行は捨てる。形式（読み TAB 表層 TAB 数字のみ）も厳密に検証し、
    壊れた行・文字化け行・過長行は読み飛ばす。
  - **壊れた学習ファイルで IME が起動不能になることは構造的にない**:
    読込みの失敗経路は存在せず、最悪でも「学習ボーナスを失う」だけ。
    パスへ書けない場合は学習自体を無効化してエンジンは通常動作する
    （`bi_engine_enable_learning` の -1 はその意味）。
  - テスト P 群（17件）で実証: OSK 経由の学習→再起動で保持、断裂末尾＋
    不正行の混入でもエンジン起動・変換・有効エントリ保持、ゴミだけの
    ファイル→履歴0で起動、ファイル欠落＋`.tmp` 残骸→残骸除去して起動。
  - なお保存は commit ごとに fsync 2回を伴う（履歴は最大 4,096 行で小さい）。
    SD への書き込み頻度と耐久性のトレードオフは統合フェーズで再評価する余地があるが、
    「黙って壊れる方式にはしない」を優先した。

### (2) ネットはデフォルトで繋がらない、時刻も信用できない
- 変換は**完全にオフライン**（辞書・接続行列は端末内ファイル）。通信を行う
  コードは入力スタックに存在しない。オンライン前提の機能（クラウド変換、
  辞書更新チェック等）は持ち込んでいない。
- **日数ベースの有効期限・失効の概念を持ち込まない**: 学習履歴にも
  レイアウトキャッシュにも時刻による追い出しはない（追い出しは容量上限と
  generation 無効化のみ、§5）。学習の eviction を時刻順（LRU）にしなかったのも
  この理由による。
- 時刻の使用は `CLOCK_MONOTONIC` によるレイテンシ計測だけ（単調時計、
  振る舞いには一切影響しない）。トグル連打の確定もタイマーではなく
  「次の操作で封止」という決定的方式にしたため、時刻・タイマ精度に依存しない。

### (3) WinCE と Brainux の併用 — SD は共有メディア
- **辞書ファイルは読み取り専用**（mmap, MAP_SHARED 読み取り）で開く。
  OSK/IME が辞書のある場所へ書き込むことは一切ない。WinCE 側が同じ SD を
  使っていても、辞書領域は読み手として触るだけである。
- **Brainux が占有前提の状態の置き方をしない**: 入力スタックが書き込むのは
  学習履歴ファイル1つだけで、その置き場所は呼び出し側（シェル統合時）が
  Brainux 側のホーム領域に決める想定（辞書と同居させない、WinCE から見える
  共有領域に状態ファイルを置かない、ロックファイルで占有しない）。
  本ライブラリはパスを引数で受けるだけで、場所に関する前提を埋め込んでいない。
- SD が抜かれた/マウントされていない状況では、学習の保存は単に失敗して
  スキップされ（旧ファイルが無ければ学習なしで動作）、変換自体は
  mmap 済みページの範囲で継続する。長時間タスクを持たない設計
  （変換は打鍵単位の短い処理）なので、中断・再開の特別な仕組みは不要。

## 7. 未実装・既知制限（範囲外として明記）

- **予測変換**（入力途中の候補提示）: 未実装。現行は読み確定部分への変換のみ。
- **絵文字パネル、手書き入力、音声入力**: 未実装（範囲外）。
- 候補バーの表示窓を超える候補はバーに直接出ない（変換キー巡回では到達可能）。
  バーのページ送りは1件単位のスクロール。
- フリック押下中のプレビュー表示（指の下の候補文字ポップアップ）: 未実装。
  現状はキー上の4方向ヒント表示のみ。
- 文節の操作対象は第0文節のみ（候補選択・伸縮・確定）。2文節目以降を直接
  触る UI は未実装（確定で順に進める方式）。
- ローマ字の打ち間違い救済（例: "kxa" のような不正系列）はリテラル出力に
  フォールバックするのみ。
- 50音セルの高さは 48px（≥56px 要求に対する意図的逸脱、§1）。
- TextField の composition 表示はツールキット既存実装の `[ ]` 囲み表示のまま
  （下線等の本格的な preedit 描画はツールキット側の課題として残る）。

- 変換品質そのものは libbrainime M2 の水準（held-out top-1 67.2%）のまま。
