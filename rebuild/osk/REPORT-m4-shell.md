# OSK M4: システムワイド OSK（シェル/WM 統合）報告書

問い（2026-11-20、ユーザー）:「スクリーンキーボードとして使えるようになっている？（全画面だと使えないけど？）」への回答として実施した監査・実装・検証の記録。

## 1. 現状監査（実施前、コードと実動で確認）

| # | 質問 | 実施前 | 根拠 |
|---|---|---|---|
| 1 | テキスト欄フォーカスで OSK が出るか | ✗ システムレベルでは出ない | `shell/src/*.c`＋`braindesk2.c` に OSK 参照 0 件。WM プロトコルにテキストフォーカス通知なし。出るのはアプリ自前埋め込み（notes）とグリーターの手動トグルのみ |
| 2 | 全画面ウィンドウの上に重なるか | ✗ 重ならない | セッションはシェル root を先に描き WM 窓を上に合成。ポインタも WM が先取り。シェル側に描いても全画面窓の下になりタッチも届かない |
| 3 | 入力欄を隠さないか | ✗ 仕組みなし | workarea はパネル分のみ。OSK 高さの inset も窓の移動連動もなし |
| 4 | 物理キーボードと競合しないか | △ 競合以前 | システム OSK 自体が無い。埋め込み OSK は物理入力しても引っ込まない |

## 2. 実装

### 表示モデル（方式選択と根拠）
- **最大化/全画面ウィンドウ = リサイズ方式**。WM に bottom inset を新設し、実効画面＝画面 − inset としてジオメトリを決める。ジオメトリが「状態＋エリア」の純関数になるため、閉じたときの復元が正確（保存した旧座標への復帰ではない）。OSK 高さ 272px のとき全画面の内容は 800×208、最大化は 800×(480−272−装飾42)。
- **通常ウィンドウ = 移動方式**。クライアントが報告した入力欄 rect（無ければフレーム）がストリップに重なる分だけ窓を上へ移動する。バッファ再確保なし。**閉じても自動では戻さない**（ユーザーのドラッグと競合するため。根拠として明記）。
- OSK は**シェル専用の別 root** に置き、セッションが WM 合成の後に描画。ポインタはストリップ内で始まったジェスチャを OSK が最初に claim＋capture する（全画面クライアントより上に表示・入力の両方で成立）。

### WM プロトコル（v1 拡張、shell/include/wm.h）
- `BD_WM_IM`（c→s）: テキスト編集の active 報告＋欄 rect（内容座標、w<=0 は不明）。
- `BD_WM_COMP`（s→c）: コンポジション文字列の配送。空文字＝クリア。
- クライアントライブラリ: `bd_wm_client_im_notify()` と `bd_wm_client_im_sync(cl, root)`（フォーカス中の TextField/TextView を検出し変化時のみ送信）。参照実装は `clients/wm_sample_tk.c` と `tests/im_client.c`。
- **制限（明記）**: コンポジションは WM 越えでは単一セグメントとして送る。文節分割はワイヤに載らない（v1 の制約）。

### シェル OSK 状態機械（shellui.c / session.c）
- 表示条件: シェル自身のテキスト欄フォーカス（ローカル attach）＞ リモート（フォーカス窓の IM active）。非テキスト欄では出ない。
- リモート時の OSK 出力は新規ウィジェット **TK_W_SINK** で受け、セッションが WM へ転送（確定テキスト＝キーイベント、変換中＝BD_WM_COMP、BS 等＝キーイベント）。
- **物理キーボード共存**: 物理タイピング（文字キー/BS/Del/Enter/Space）を検出したら OSK を閉じ、入力ターゲットの同一性が変わるまで再表示しない（ラッチ）。
- braindesk2 は実辞書（`libbrainime/data/brainux3.bid3`、環境変数上書き可）を開いて実エンジンを配線。辞書が無ければカナ fallback で動作。

### テスト中に見つけて直した製品バグ
- **ラッチが二度と解けない**: リモート対象の同一性を「active か否か」だけで見ていたため、inactive→active のフォーカスサイクルがセッションステップ間に畳み込まれると（実機でも起こる）ラッチが永続化した。対策: WM サーバが IM 状態変化（活性化エッジ＋欄 rect 変更）を数える **IM シリアル**（`bd_wm_server_im_serial`）を新設し、シェルはそれを対象の同一性に使う。test_wm にシリアルの単調性・重複報告で増えないことの検証を追加。

### 再描画コストの削減（実測が起点）
- 実測で、OSK の1打鍵がストリップ全域 435,200 B の再描画になっていた（コアが「処理したウィジェットの全面」をダメージにするため）。
- 汎用機構 **damage hint**（`tk_root_damage_hint`、最大3矩形、対象 rect でクリップ）を新設。OSK は「押したセル＋候補バー＋フリックプレビュー」に絞る。レイアウト変更（モード/シフト/ページ＝grid_gen 変化）は全域のまま。
- シェルの OSK は生成時にフォーカス済みにし、初回タップのフォーカス移動による全域再描画も回避。

## 3. 検証（全て製品コードの経路）

### テスト結果（回帰ゼロ）
| スイート | 前 | 後 | 備考 |
|---|---|---|---|
| ツールキット | 641 | 645 | tk3 に damage hint の回帰テスト +4（打鍵 DOWN <20k px / UP <120k px / モード切替 >150k px） |
| シェル | 495 | 588 | test_wm 51→90（IM/inset/シリアル）、test_session 48→102（OSK E2E 全シナリオ） |
| OSK | 307 | 319 | sink グループ +12（SINK への attach で変換・確定・キーがコールバックへ出る） |
| アプリ | 1,048 | 1,048 | 無変更（apps/ には触っていない） |

test_session の E2E シナリオ: 欄タップで OSK が開く／OSK 打鍵→コンポジション→確定が実クライアントの欄に届く／物理キーで閉じてラッチ／フォーカスサイクルで再表示／欄が隠れる位置では窓が上がる（移動量を px 単位で検証）／全画面 800×480→208→480 の往復が正確／閉時に inset が戻る。

### ダメージ量の実測（RGB565 転送量、OSK 単体・定常状態）
| フレーム | 改善前 | 改善後 |
|---|---|---|
| キー DOWN | 435,200 B | **9,856 B**（押したセルのみ） |
| キー UP（変換候補更新） | 435,200 B | **86,656 B**（候補バー 76,800＋セル 9,856） |
| 静止フレーム | 0 B | 0 B |
セッション全体では OSK を開く遷移が 768,000 B（全画面1回分: ストリップ初描画＋窓の再描画が重なる）。打鍵フレームはクライアント側の欄再描画と合算される（実測 0〜約 650KB とばらつく主因はテスト用クライアントの全面 commit。実アプリはダメージ矩形 commit をすれば欄分だけになる）。

### 実寸評価（PW-SH6: 5型 800×480、対角 5 インチから算出）
- パネル実寸 108.9 × 65.3 mm、ピッチ 0.1361 mm/px。
- キー高さ 56px = **7.62 mm**。800 幅時: セルピッチ 80px = 10.89 mm、キー面 約 76px = **10.35 mm** 幅。抵抗膜＋指先でも誤タップしにくい寸法（一般的な最小目安 7mm、推奨 9mm 級を満たす）。
- OSK ストリップ 272px = 37.0 mm（画面高の 57%）。全画面時は残り 208px = 28.3 mm がアプリ領域。
- **480 幅時（既知の問題の実寸評価）**: 10 列行のセルピッチ 48px = **6.53 mm**、キー面 約 44px = **5.99 mm** 幅で、幅方向は 7mm 目安を割る。高さは 7.62 mm を維持。実機は 800 幅が常態で、480 幅は狭い窓・縦寄り配置の例外。フリック/50音レイアウトはセルが大きく、狭幅ではそちらが実用的。

## 4. コピー/オーバーヘッド・キャッシュ/メモリの方針
- コピー: OSK の描画はダメージ駆動のまま（上記 hint で転送量を削減）。WM の inset 変更は最大化/全画面窓のみ再配置し、通常窓は移動のみ（バッファ再確保なし）。
- キャッシュ/メモリ: 新規キャッシュなし。OSK のレイアウトキャッシュは従来どおり世代カウンタで無効化。追加状態は WM の欄 rect＋シリアル、シェルの対象同一性のみ（固定サイズ）。

## 5. 実機の現実への対応
- 永続状態を持たない（表示状態のみ）ため、突然のリセットで壊れるものはない。OSK の開閉はフォーカス状態からの純粋な導出で、再起動後は自然に閉じた状態から始まる。
- eMMC には触れない。辞書は読み取り専用で開く。

## 6. 残件・引き継ぎ
- 実アプリ（apps/）の WM クライアント化と IM 報告の実装は統合フェーズの担当（契約は参照クライアントで実証済み）。現行アプリは埋め込み OSK のまま動作する。
- グリーターは従来どおり手動トグルで不変（test_greeter 系は全 PASS）。
- コンポジションの文節分割を WM 越えに載せるにはプロトコル v2 が必要。
- ゲスト/実機での実操作検証は統合フェーズの合格条件（本フェーズはホスト上の製品コード経路で検証）。
- 観測メモ: 並行ビルド中に /tmp（512MB tmpfs）が枯渇し apps のビルドが一度失敗した。自分のテスト残骸と古い bdrec-* を消して 30MB 回収済み。/tmp/shimeji-src（434MB、別作業のマスコット素材）には触っていない。
