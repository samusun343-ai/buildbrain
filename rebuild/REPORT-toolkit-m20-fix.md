# REPORT — M20 判断材料撮影の異常切り分けと是正（2026-11-21）

起点: AUDIT §18.4 の判断材料撮影（screenshots/m20_fit_android.jpg /
m20_fit_winui.jpg）へのユーザー指摘「おかしくない？」。親エージェントが
実画像で確認した異常3点について、tests/shot_m20.c とライブラリ描画
コードを読み、プローブ（shot_fit と同じツリーを再現しピクセルマップを
出力）で切り分けた。

結論の要約: **異常のうち2件はライブラリの描画バグ、1件（ボトムバー）は
描画位置のバグではなく、撮影側のアイコンが主因**。ライブラリのバグは
修正し、形状を固定する回帰テストを追加した。マトリクスのセル記号は
変更していない（● 410 のまま）が、Android #6 B / #7 B / #19 B の ● の
根拠は置き換わった（§4）。判断待ち (a) 11件の分類と Slider の形状は
動かしていない。

## 1. 異常2（先に結論が出た順）: Android ラジオが角丸四角＋ドット

- **切り分け: ライブラリ側。**
- 実測: プローブのピクセルマップで、M3 ラジオの 18×18 グリフボックスは
  全周（隅を含む）が border 色の四角い輪郭だった。ドットは正しく円。
  WinUI 側は輪・ドットとも円で正しい。
- 原因: src/tk_widgets.c の TK_W_RADIO、M3 経路。fill は
  `tk_canvas_fill_round_rect(c, box, 9, t->surface)`（円）なのに、輪郭は
  `tk_canvas_stroke_rect(c, box, 1, t->border)`（四角）だった。無効状態の
  経路は元々 `stroke_round_rect`（r9）で正しく、有効経路だけが四角だった。
- 修正: 有効経路も `tk_canvas_stroke_round_rect(c, box, 9, 1, t->border)`
  に是正。修正後のマップで輪が円（隅クリア＋辺中点が輪郭上）になった
  ことを確認。

## 2. 異常3の本体: チェックボックスの状態が揃って見えない

- **切り分け: 状態は元々揃っていた。ライブラリ側（M3 のマーク形状）。**
- 実測: shot_m20.c は両モードとも `tk_checkbox_new("Checkbox", true)`
  （checked）で同一コード。プローブのマップで、WinUI は塗り＋チェック
  グリフ（2ストローク）で正しくチェック済みに描かれるのに対し、M3 は
  アクセント塗りの箱＋中央に **10×10 の on_accent 塗り正方形**で、
  チェック形ではなかった。白い正方形が箱の内側に抜けて見えるため、
  チェック済みが「空の枠＝未チェック」に誤読された。これが2枚の
  「状態不一致」の正体。
- 原因: TK_W_CHECKBOX の M3 経路が、チェックマークとして
  `tk_canvas_fill_rect(..., 10, 10, t->on_accent)`（glyph_pos で拡大縮小）
  を描いていた。無効 checked 経路も同じ正方形。同型の3件目として、
  「Checkbox と同じ 18px ボックス言語」を自称する **ListView チェック
  可能行の箱**も同じ 10×10 正方形だった。
- 修正: 共通ヘルパー `paint_check_glyph()` を新設（チップのグリフと
  同じ 2×2 ブロックの2ストローク。短腕 (4,9)→(7,12)、長腕 (7,12)→(13,5)
  を 18px ボックス座標で定義し、glyph_pos で中心から拡大 — ラジオの
  ドットと同じ成長様式）。適用先: Checkbox 有効経路（gp 連動）、
  Checkbox 無効 checked 経路（等倍）、ListView チェック可能行（等倍）。
  あわせて Checkbox / ListView 箱の輪郭を、r3 の fill に沿う
  `stroke_round_rect` に是正（従来は四角ストロークが角で fill から
  はみ出していた）。
- 修正後のマップで、チェックの両腕と中心交差が on_accent、旧正方形の
  隅がアクセント塗りに戻ったことを確認（マーク画素数 100 → 約35）。

## 3. 異常1: WinUI ボトムバー（ハイライト無し・白アイコン・左端の青い縦線）

- **切り分け: 描画位置のバグではない。主因は撮影側（アイコン）、
  副因は参照トークン自体の淡さ。**
- 実測（プローブ、shot と同じ構成）:
  - バー rect (412,231) 372×81、セル0 (414,233) 117×77。
  - アクセント画素の bbox = (414,259)–(416,282) = **3×24px、セル左端・
    垂直中央**。コード（tk_bottombar_paint_indicator の style==2 経路）
    の指定どおりの位置で、ずれていない。tests/test_tk7.c の
    test_winui_bottombar が同じ位置（セル左端＋1px、中央高）をピンして
    いる、ライブラリの設計形（NavigationView 形）である。左端のセルでは
    バーの外周左端とほぼ重なるため「断片」に見えた。
  - 選択セルの塗りは theme の subtle = (0,0,0,alpha 9) =
    SubtleFillColorSecondary 相当。白いバー上では (246,246,246) となり、
    ほぼ不可視。これは参照トークンの忠実な適用結果で、コードの
    数値ミスではない。
  - アイコン: shot_m20.c の合成アイコンは純白 (0xffffffff)。ライブラリは
    アイコンを素通し blit する（実消費者は色付きビットマップを渡す）
    ため、淡い面の上では両モードともほぼ不可視だった（Android 側も
    container (234,221,255) 上の白で低コントラストだったが、WinUI 側が
    より顕著だった）。
- 対応: ライブラリは変更しない。撮影側でグリフをテーマのテキスト色で
  生成するよう変更（実アイコンの「内容色に従うグリフ」の再現）。
  撮り直し後は両モードともアイコンが視認できる。なお subtle 塗りの
  淡さと「左端の縦線」という形自体への異論は、ライブラリの設計判断
  （tk7 でピン済みの NavigationView 形）の話であり、本タスクの範囲
  （描画の正しさ）では変更していない。

## 4. ● の再判定

- Android #6 B / #7 B: 従来の ● は tk12 / tk13 の「存在のみ」サンプル
  （中心ピクセルの色、塗りの有無、寸法）に依拠し、**グリフ形状・輪形状を
  固定していなかった**。今回の欠陥はまさにその盲点。修正＋形状テスト
  （下記）で ● の根拠を置き換えた。記号は ● のまま据え置くが、根拠は
  従来分ではなく test_glyph_shapes である。
- Android #19 B: ListView チェック箱が同じマーク欠陥を共有していた
  ため、同様に根拠を置き換えた。
- WinUI #6 B / #7 B: プローブのマップで正形（チェック・円）を確認。
  変更なし。tk17 に正形のガードも追加した。
- WinUI #29 B / E: §3 のとおり描画は設計形どおりで、異常は撮影側。
  変更なし。
- (a) 11件（#6 A、#7 A、#29 A ほか）の分類は不変。Slider 形状も不変。

## 5. 回帰テスト（形状の固定）

tests/test_tk17.c に test_glyph_shapes（25件）を追加:

- M3 チェック済み: マーク画素数が 15..70（正方形は100）、旧正方形の
  隅2点がアクセント塗り、両腕と中心交差が on_accent。
- M3 ラジオ選択: 輪の四隅が border でない（四角ストロークなら失敗）、
  辺中点4点が border、中心がドット色。
- M3 ListView チェック箱: 隅がアクセント塗り、腕と中心が on_accent。
- WinUI チェック/ラジオ: 両腕の点、画素数帯、輪の隅クリア＋辺中点
  （正形のガード）。

既存ピンの前提更新（2件、いずれも性質の検証は維持）:

- test_tk13.c / test_tk15.c の ListView チェック箱の塗りサンプル
  (bx+1, by+1) → (bx+2, by+2)。旧サンプル点は四角ストローク時代には
  アクセント塗りだったが、輪郭が r3 の弧に沿うようになった後は弧上
  （border）にあるため。コメントに理由を明記。

## 6. 撮影の撮り直し

tests/shot_m20.c の変更:

- グリフアイコンをテーマのテキスト色で生成（§3）。
- チェックボックス/ラジオを **両状態**（checked/unchecked、
  selected/unselected の2行）で両モード同一に配置。
- 参照ラベルをモード別に分離（WinUI 側に Material の dp 参照が
  印字されていた問題を解消）。例: Android「#3 FAB 64px (ref 56dp =
  65px)」/ WinUI「#3 FAB 64px (no WinUI FAB)」、ListView は WinUI 側
  「ref 40epx = 57px」。WinUI の長いラベルが左カラムからはみ出して
  重なったため、各ラベルは実測幅に収まる長さに調整済み。

再生成: screenshots/raw/m20_fit_{android,winui}.raw → PNG / JPG
（convert.py と同形式・同 quality で2枚のみ変換）。**撮り直した2枚は
自分で開いて目視確認した**: チェック形・円形・両状態の一致・
アイコンの視認性・ラベルの重なり無し・モード別ラベル、すべて確認。
拡大でも Android のチェック済み＝チェック形、ラジオ＝円＋ドット、
WinUI バーの Home ＝ subtle 塗り＋左端アクセント＋視認できる
アイコン、を確認した。

## 8. 未対応の観測（範囲外として記録）

- メニューのチェック可能項目のマークも 10×10 のアクセント正方形
  （tk_widgets.c のメニュー描画、両モード共通）。専用のチェック溝に
  置かれるため「未チェックとの誤読」は起きにくいが、チェック形では
  ない。今回の指摘範囲（判断材料撮影の3異常）外のため未変更。
  チェック形に寄せるかは別判断。
- WinUI ボトムバーの subtle 塗り（alpha 9）は参照トークンどおりだが、
  白いバー上では選択がアクセント縦線頼みになる。形の変更は設計判断
  として別途。
