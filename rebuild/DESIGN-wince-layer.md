# WinCE 互換レイヤー 実現可能性調査と設計（BrainCE Layer v2）

作成: 2026-11-21（第1弾: 実現可能性調査＋設計。本文書は調査の進行に合わせて追記される）

## 0. 本書の位置づけ・方法・制約

- 本書は buildbrain repo の `docs/wince-layer.md`（旧設計。現行 HEAD では削除され
  git 履歴にのみ残る。本書では「元設計」と呼ぶ）を出発点に、方式選定を Web 調査で
  裏付け、対象アプリの実態を手元資料で確定させた上で、ストレージ設計・非破壊の
  検証計画・統合の深さの推奨までを定める設計文書である。
- **絶対条件**: 通常の WinCE 起動が互換レイヤーの変更で壊れないこと。eMMC の
  WinCE 領域はレイヤーのストレージに使えるが、**非破壊が証明できる範囲でのみ**
  触る。それ以外の eMMC 書込みは禁止。
- 法的境界（元設計から継承し厳守）: 実装するのは Microsoft が公開ドキュメントで
  仕様を公開している WinCE 標準 API の互換実装のみ。SHARP 独自のドライバ・独自
  API・独自アプリの中身は再実装・複製・再配布しない。実行されるアプリと DLL は
  ユーザが自分の実機に正規搭載されている自分のソフトウェアであり、レイヤーは
  それを複製しない。仕様は公開資料とブラックボックス観察のみから取る。eMMC の
  解析はしない（本書の数値は、QEMU 側プロジェクトが自らの成果物として公開して
  いる静的センサスの集計と、本プロジェクトの公開情報のみに基づく）。
- 規模見積もりは全て根拠（実測した関数数・モジュール数）と一緒に書く。出典の
  無い数値は「推定」と明記する。

## 1. 結論サマリ

- **推奨方式は (a) API レベルの再実装（Wine 型）＋「coredll より上位の DLL は
  原本バイナリをホストする」橋渡し**。CPU が同一（ARM926EJ-S / ARMv5TEJ、
  454MHz、RAM 128MB）ため命令翻訳は不要で、必要なのは PE ローダと coredll
  シムと GWE シムと FS ブリッジのみ。この構成だけが 128MB の予算内で
  「Brainux の一機能として CE アプリを使う」到達点を持ち得る。
- 先行事例は事実上存在しない。Wine 本体は Windows CE をサポートしていない
  （Wikipedia の Wine 記事が CE 対応を「missing」と明記）。唯一の試み WineCE は pre-alpha の
  proof-of-concept のまま 2013 年時点で「Not much interest」とされ停止している。
  組み込み Linux 向けの CE 互換レイヤーは商用・OSS とも確認できなかった
  （Toradex の公式フォーラム回答も「直接の等価物は無い」と明言）。**つまり
  流用できる土台は無く、自前実装が前提**。ただし後述のとおり、対象表面は
  実測で上限が閉じている（coredll 全輸出 2,927 件中、全 ROM モジュールが
  静的に import する union は 1,063 件）。
- coredll 自体はホストできない（CE カーネルのユーザ側表現であり、カーネルと
  一体の存在）。ホストできるのは coredll を「顧客として使う」アプリケー
  ション層 DLL（SharpLib 等）だけであり、この切り分けが設計の要である。
  SHARP 層の DLL はほぼ coredll のみに依存するため（SharpLib: coredll
  239 件＋ole32 6 件）、シムの到達範囲がそのまま SHARP アプリの到達範囲を決める。
- ストレージは **eMMC は読み取り専用マウントのみ、書込みは全て SD 側
  オーバーレイへ逃がす**。非破壊は「マウント方式の多重化された書込み拒否」
  「前後ハッシュ照合」「CE 側チェックリスト」の3点セットで証明する（§7）。
- 統合の深さは **段階案（まず分離レイヤーとして実装し、窓・入力の橋だけを
  braindesk の既存サーフェスプロトコルに接続。深い統合は実アプリが動いた後に
  項目ごとに判断）** を推奨する。最終決定はユーザーが行う（§8）。

## 2. 元設計からの前提訂正

調査で元設計の記述に2点の事実誤り／不正確さが見つかった。設計判断に影響する
ため先に訂正する。

### 2.1 CE 6.0 に「32MB スロット」モデルは無い

元設計は「WinCE (CE 6 系) のプロセスは 32MB スロット前提のアドレス配置」と
書くが、32MB スロットと32プロセス上限は **CE 5.0 以前**のモデルである。
Microsoft の技術解説（Douglas Boling, *Windows Embedded CE 6.0 Advanced
Memory Management*, Microsoft Learn）によれば、CE 6.0 はカーネルを書き換え、
プロセス毎の仮想空間を 32MB から **2GB** へ拡大し、プロセス上限も 32 から
32,000 へ引き上げた。PW-SH6 の OS は CE 6.0 系である（本プロジェクトの
前提）。影響:

- ローダの仕事はスロット再現ではなく、デスクトップ PE に近い「プロセス毎の
  アドレス空間への ImageBase 配置＋再配置」に単純化される。Wine の preloader
  的な「共有アドレス空間の予約」は不要。
- ただし CE 6.0 にはユーザ DLL を 0x40000000 以降の領域に置く規約があり、
  アプリが DLL の配置や共有メモリ領域（CE 5 互換の共有領域）に前提を置く
  場合はシム側でその見え方を再現する必要がある（§5.3）。
- XIP（ROM 内実行）モジュールはファイルオフセット＝RVA の特殊な格納形を取る
  ことが実測されている（QEMU 側 p50: SharpLib の ROM XIP イメージで
  file offset == RVA）。ローダは通常の PE ファイル配置と XIP 配置の両方を
  扱えなければならない（§3.4、§5.2）。

### 2.2 「DLL の橋渡し」は coredll には適用できない

元設計の橋渡し節はドライバ DLL を主対象に正しく書かれているが、線引きを
明確化する。Microsoft Learn の Kernel Services 解説は「Windows CE カーネルは
Coredll モジュールによって表現される」と述べ、CE 6.0 では GWES・ファイル
システム・デバイスマネージャがカーネル内へ移され、coredll はそのユーザ側の
顔である。すなわち **原本 coredll.dll は CE カーネル無しには意味を持たない**
ため Linux 上にホストできず、再実装（シム）が必須である。逆に SharpLib の
ようなアプリケーション層 DLL は coredll API の顧客であり、シムがその import
を満たせば原本のまま実行できる。橋渡しの可否は「その DLL の import が全て
シム済み API か」で機械的に判定できる（§6.3 に実測の判定材料）。


## 3. 対象アプリの実態（手元資料による確定事項）

数値の出所は QEMU 側プロジェクトの静的センサス（`exports-census.json`:
輸出を持つ ROM モジュール 151 本・全輸出 10,154 件、`callers.json`:
輸出→呼び出し側の静的対応表）を本タスクで集計したものと、同プロジェクトの
レポート p46–p56、および本プロジェクト側 brain-tools の自作 CE アプリ群の
ビルド成果物（imports.json）である。静的解析由来の数値は「実際に動的解決
される呼び出しを取りこぼす／未実行経路を含む」両方向の誤差を持ち得る。
計画には上限側の数値を使う。

### 3.1 ハードウェアと OS

- SoC: NXP i.MX283（ARM926EJ-S、ARMv5TEJ、454MHz）。DRAM 128MB。eMMC 8GB。
  画面 800×480（本プロジェクトの fb 前提）。出典: Brain Hackers / buildbrain
  knowledge 資料（PW-SH1 の表だが SoC 世代共通の値）、日経クロステックの
  Brainux 特集（第2世代＝i.MX283 の整理）。
- ゲスト OS: Windows CE 6.0 系。シェルは explorer.exe ではなく SHARP 独自の
  **wceprj.exe** が占有する（QEMU 側 p44/p53 で確定）。起動順は
  HKLM\init: Launch20 device.dll → Launch30 gwes.dll → Launch50 explorer.exe
  相当の枠組みだが、GUI シェルの座は wceprj が占める。

### 3.2 アプリの形態と起動経路

- 収録アプリは「アプリケーションフォルダ＋ `AppMain.exe`」の形で
  \Nand（本体）と \Nand2（FAT16 ボリューム）等に置かれる。追加アプリの登録
  実体は `index.din`（SSMA2.50 形式、p46）だが、**起動時に din は読まれない**。
- 起動ゲート（p49 で実コード検証済み）: wceprj がカード経路の起動時にだけ
  `AppMain.cfg`（表示サイズ条件）と同フォルダの `AppMain.blr`（1024 バイト、
  バイト和と XOR のみの検査。暗号署名は無い）を検証する。本体 \Nand 経路は
  接頭辞バイパスで無検査。**これはシェル（wceprj）の方針であり OS の要求では
  ない**。互換レイヤーのランチャーは blr を再現する必要はなく、exe を直接
  起動できればよい（ゲートは「誰が起動してよいか」の話で、バイナリ自体は
  何も検査していないことが p49 で確認されている）。
- 辞書・書籍コンテンツは \Nand、\Nand3 の `.zbf` 等のデータファイルであり、
  アプリ（とその DLL 群）がファイルとして読む。レイヤーからは「CE 名前空間
  の実体として実ファイルが見える」ことが要件になる（§7）。

### 3.3 依存 DLL の実測

センサスの集計結果（本タスクで実施）:

| 対象 | 実測値 |
|---|---|
| coredll.dll の全輸出（この CE ビルド） | **2,927 件** |
| ROM モジュール 151 本が coredll から静的 import する union | **1,063 件**（全輸出の 36%） |
| .exe モジュール全体の coredll import union | 506 件 |
| アプリ系 exe 27 本（AppMain.exe 群＋ToolsApp＋アプリフォルダ）が直接呼ぶ coredll 関数（callers 静的対応） | **874 件** |
| 同 27 本が直接呼ぶ SharpLib 関数 | 198 件 |
| coredll / ole32 / oleaut32 のみに import が閉じるモジュール | 151 本中 **79 本** |

主要 DLL の輸出数と依存（全て import は coredll が中心）:

| DLL | 輸出数 | 主な import |
|---|---|---|
| coredll.dll | 2,927 | （カーネルの顔。それ自体は再実装対象） |
| commctrl.dll | 77 | coredll のみ |
| ws2.dll（Winsock） | 82 | coredll のみ |
| ole32.dll | 40 | coredll のみ |
| toolhelp.dll | 14 | coredll のみ |
| commdlg.dll | 5 | coredll のみ |
| gwes.dll | 25 | coredll のみ（実体はカーネル内 GWES の顔） |
| **SharpLib.dll** | **465** | **coredll 239 件＋ole32 6 件** |
| XMDFViewerDLL.dll | 43 | coredll 281 件＋SharpLib 50 件＋ole32 3 件 |
| edwecli.dll（辞書エンジン） | 234 | coredll 83 件＋edwopt 47 件＋edwgsp 3 件 |
| edwopt.dll | 115 | coredll 72 件＋edwecli 5 件 |
| dbapi2ed.dll | 74 | coredll 57 件 |
| vt_jpn.dll（TTS 音声） | 88 | coredll 67 件 |

読み取れる構造:

1. **この CE ビルドのユーザ空間は「全てが coredll の顧客」という単層構造**
   で、デスクトップ Windows のような kernel32/user32/gdi32 の分離は無い。
   シムは coredll 1 本に集中できる。
2. SHARP 層（辞書エンジン群・XMDF ビューア・TTS）は coredll と SHARP 内部
   DLL 相互のみで閉じており、**カーネル直結の依存（CEDDK 等）を持つのは
   dvfc.dll のようなドライバ寄りモジュールだけ**。アプリ層の橋渡しは
   coredll シムの到達範囲だけで決まる。
3. アプリ系 exe が commctrl を直接呼ぶのは 6 件のみ。画面部品の多くは
   SharpLib 経由で供給されていると見られる（aygshell.dll はこのビルドの
   輸出センサスに現れない。SHARP のシェル方針アプリでは shell API の主役は
   aygshell ではなく SharpLib）。**「SharpLib 原本を動かせるか」が辞書級
   アプリ到達の試金石**になる。

### 3.4 自作 CE アプリ（到達可能性の実証サンプル）

本プロジェクト側で既に実機 CE 上で動作実績のある自作アプリは、全て
**coredll のみに import が閉じている**。互換レイヤーの初期マイルストーンの
テストベクタとしてそのまま使える:

| アプリ | coredll import 数（実測） | 内容 |
|---|---|---|
| P47App（最小 GUI） | 25 | 窓生成・メッセージループ・GDI 塗り・ファイル書込み |
| BrainCon.dll（ストリームドライバ） | 14 | イベント・クリティカルセクション・LocalAlloc 等のみ |
| P47Term / BrainTerm（端末） | 約45–70 | 上記＋フォント・テキスト描画・ディレクトリ列挙・CreateProcess |
| マスコット AppMain（p56） | 50 | 上記＋BitBlt・DIBSection・リージョン（SetWindowRgn 等）・VirtualAlloc |

ビルド経路も既にある: clang `-target armv5te-none-eabi` ＋ 自作 PE リンカ
（brain-tools の pe-link47.py）が coredll を序数で import する PE を生成する。
**シム DLL のビルドとテスト用バイナリの生成に、この経路をそのまま使える**
（シムは「CE ABI で書かれた Linux 側実装」をこの形式で束ねるか、ローダ側で
序数→実装の表として持つ。§5.2 で選定）。


## 4. 方式候補の比較（Web 調査による裏付け）

### 4.1 先行事例の調査結果

- **Wine 本体は CE をサポートしない**。Wikipedia の Wine 記事は
  「Windows CE support (either x86 or ARM) is missing」と明記し、非公式の
  pre-alpha proof-of-concept「WineCE」の存在を注記するに留まる。
- **WineCE**（André Hentschel、github.com/AndreRH/winece）: Wine に coredll
  等を足して CE バイナリを動かす試みだったが、作者自身の FOSDEM 2013
  講演資料で「More like a proof of concept」「Not much interest」と総括
  され、以後実質停止。対象は主に x86 CE（エミュレータ用バイナリ）で、
  到達点は「一部の単純なバイナリが起動する」段階と見られる（本調査では
  それ以上の到達を示す資料は確認できなかった）。ライセンスは Wine 本体と
  同じ LGPL 2.1 以降。
- **「Windows CE Compatibility Layer」**（Emulation General Wiki の一覧に
  MIT ライセンスとして掲載）: 一覧上の活動度は「~」、推奨度は最低档。
  本調査ではリポジトリの実在と到達点を一次資料で確認できなかったため、
  **流用候補としては数えない**（存在自体を否定するものではない。未確認と
  明記する）。
- **組み込み Linux 向けの CE 実行環境は確認できなかった**。Toradex の
  公式コミュニティ回答（Colibri VF61 = i.MX 系モジュールでの同種の質問）に
  も「WINE は Windows CE アプリ向けに設計されておらず、組み込み向けの
  直接の等価物は無い。選択肢は移植・エミュレータ・書き換え」と明言されて
  いる。2000 年に Lineo が Embedix 向け WinCE 互換レイヤーを発表した記録
  があるが（Linux Journal のニュース短信）、製品の技術資料や後継は確認
  できなかった。
- 名前の紛らわしい **Wine-CE（Chimera Edition）** は Windows CE とは無関係
  （デスクトップ Windows PE を異アーキテクチャで動かす Wine＋QEMU の統合
  プロジェクト）。本書の検討対象ではない。

結論: **「既存の CE 互換レイヤーを採用・改修する」選択肢は存在しない。**
方式は「自前で API 再実装」「システム全体のエミュレーション」「バイナリ
変換」の3つから選ぶことになる。

|---|---|---|---|---|

### 4.3 推奨

**(a) を採用する。** 理由は3点に集約される。

1. 表面が閉じている: 対象は coredll 1 本＋その顧客 DLL 群で、必要表面は
   実測 1,063 件（静的 union）が上限の目安になる。デスクトップ Win32 の
   ような際限の無い表面ではない。
2. 資源が閉じている: 命令翻訳ゼロ、シムは共有マッピングで済み、アプリの
   実メモリ消費は実機 CE 上と同程度（元々 128MB の機械で動いていたアプリ
   である）ことが期待できる。※期待であり実測は M1/M3 で取る（§10）。
3. 法的境界と一致する: 再実装するのは公開 API のみ、SHARP の資産は原本を
   「実行するだけ」で複製しない、という元設計の方針をそのまま実装できる。

(c) は却下ではなく**補完**として位置づける: レイヤーで動かないアプリの
受け皿は「通常の WinCE 起動（デュアルブート）」であり、それが絶対条件で
保護される対象そのものでもある。QEMU（デスクトップ上）はレイヤーの実装を
検証する際の「正解系」として使う（§9.3）。

## 5. 推奨アーキテクチャ

元設計のコンポーネント構成（ce-loader / coredll シム / GWE シム / FS
ブリッジ / 段階的スタブ）を継承し、§2 の訂正と §3 の実測を反映して具体化
する。

### 5.1 全体像

```
[CE アプリ AppMain.exe] [原本 DLL: SharpLib 等]      ← CE ABI の PE 群
        │ import (序数/名前)      │ import
        ▼                        ▼
[ce-loader] ── 束縛 ──→ [coredll シム (CE ABI の顔を持つ Linux 実装)]
                              │ 内部は通常の Linux ライブラリとして実装
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
        [FS ブリッジ]    [GWE シム]        [レジストリ実装]
        CE 名前空間→     libbrainui2 /    SD 上の専用ストア
        実マウント       braindesk WM     （§7.4）
        （§7）           サーフェスへ写像
```

- シム DLL は「PE としてビルドされたシム」ではなく、**ローダが序数→実装
  関数の表を持ち、IAT を Linux 側の実装へ直接束縛する**形を第一候補とする。
  理由: (i) CE の呼び出し規約は AAPCS とほぼ同一で、引数・戻り値の変換層が
  薄く済む関数が大半であること、(ii) シムを PE として作ると「PE の中から
  Linux を呼ぶ境界」が全関数に必要になり、Wine の Unix-call 方式のような
  変換層が恒常コストになること、(iii) 本プロジェクトの原則（コピーと
  オーバーヘッドの極小化）に合うこと。構造体返し・浮動小数・可変長引数・
  コールバック（WndProc 等、CE→シム→CE の再入）など ABI の角は、関数群
  ごとに実測して表側で吸収する。代替案（シムを PE 化し境界を一箇所に
  集約）は、再入と例外の扱いが複雑化した場合の退避先として §10 に残す。
- プロセスモデル: CE アプリ 1 本＝Linux プロセス 1 本。CE のスレッドは
  pthread へ、CE の同期オブジェクト（イベント/ミューテックス/セマフォ/
  クリティカルセクション）はプロセス内実装＋名前付きは共有メモリ＋futex
  系で実装する。プロセス間通信（HWND メッセージのプロセス跨ぎ、名前付き
  オブジェクト、メモリマップドファイル共有）は GWE サーバプロセスが仲介
  する（§5.4）。

### 5.2 ce-loader

- PE32（ARM、サブシステム Windows CE GUI/CUI）のパーサ: セクション配置、
  再配置、インポート解決（**名前と序数の両方**。本ビルドのモジュールは
  coredll を序数で import するのが常態であるため序数解決が主経路）、
  遅延ロード、TLS コールバック、エントリ呼び出し（WinMain / DllMain の
  DLL_PROCESS_ATTACH 連鎖）。
- XIP 形式への対応: ROM モジュールはファイルオフセット＝RVA の格納形が
  ある（§2.1）。原本 DLL をマウント済み CE ボリュームから読む場合、その
  ままマップできる形と、通常 PE として再構成が必要な形の2通りを S0
  （§7.2）で実測して決める。
- アドレス配置: プロセス毎に ImageBase を尊重し、衝突時は再配置で逃がす
  （CE 6.0 のプロセス毎 2GB モデルの範囲内）。DLL の共有は「同一ファイルの
  読み取り専用マッピングをプロセス間で共有する」形で、CE の DLL 共有
  セマンティクス（コード共有・データはプロセス毎）を再現する。
- 起動経路: 通常はランチャー（braindesk のアイコン／専用コマンド）から。
  binfmt_misc への登録は任意の追加（§8）。登録する場合も magic は
  「MZ＋PE シグネチャ＋CE サブシステム＋ARM マシン」の複合条件にし、
  通常の ELF や他形式 PE を誤認しないこと（binfmt_misc の magic は先頭
  128 バイト以内という制約があるため、PE ヘッダへのオフセット可変性と
  両立する登録方法を M1 で実測する。無理なら拡張子ベース＋ランチャー
  経由に留める）。

### 5.3 coredll シム

§6 の見積もりに基づき、以下の順で実装する（各群とも「公開ドキュメントの
仕様＋ブラックボックス観察」で実装し、未実装はログ付きスタブ）。

1. **基盤群**: メモリ（Local/GlobalAlloc、VirtualAlloc 系、ヒープ）、
   文字列・CRT（coredll は C ランタイムを含む。malloc/free、wcs 系、
   sprintf 系）、エラー（Get/SetLastError、TLS）。
2. **実行群**: プロセス/スレッド（CreateThread、同期オブジェクト、
   Sleep、GetTickCount、Interlocked 系）、モジュール（LoadLibrary、
   GetProcAddress、FreeLibrary）。
3. **ファイル群**: CreateFile/ReadFile/WriteFile/SetFilePointer、
   FindFirstFile 系、属性・ディレクトリ操作。実体は FS ブリッジ（§7）。
4. **レジストリ群**: §7.4 のストアに対する RegOpenKeyEx 系。
5. **GWE 群**: §5.4。
6. **その他**: デバイス（CreateFile のデバイス名→Linux デバイス/シム
   ドライバへの写像。ストリームドライバの原本ホストは元設計の橋渡し節を
   継承し、対象を「import がシム済み範囲で閉じるドライバ DLL」に限る）、
   電源・通知（Notify 系は Brainux 側デーモンへの連携として後段）、
   Winsock（ws2.dll 自体も coredll 顧客なので、必要なら原本ホストか薄い
   シムかを実測で選ぶ）。

### 5.4 GWE シム（最大の作業量）

- ウィンドウ/メッセージ: HWND、メッセージキュー、WndProc コールバック、
  タイマ、フォーカス、キャプチャ、ポップアップメニュー、リージョン
  （SetWindowRgn — p56 で実アプリの使用が確認されている）等を、
  braindesk の WM（Unix ソケット＋memfd のサーフェスプロトコル）の
  クライアントとして実装する。CE アプリのウィンドウは Brainux の通常
  ウィンドウとして現れる。
- GDI: DC、BitBlt 系、DIBSection、フォント（実フォント描画は libbrainui2
  のフォント基盤を再利用）、ペン/ブラシ、テキスト描画（DrawText、
  ExtTextOut）。辞書アプリの本文描画はテキスト系の正確さが品質を決める。
- コモンコントロール: commctrl.dll（輸出 77 件、import は coredll のみ）
  は **原本ホストを第一候補**とする。シムの GWE が commctrl の使う
  coredll 表面を満たせば、再実装せずに済む可能性が高い（実測は M3）。
  同様に commdlg（5 件）も原本候補。
- 入力: キーボードは実機キー表（本プロジェクトで確定済みの48キー＋借用
  コードのフェイスバリュー扱い）を CE の仮想キーへ写像。タッチは抵抗膜
  1本指を WM_LBUTTON 系へ。日本語入力は当面 CE 側の仕組み（原本 DLL が
  担う範囲）に任せ、libbrainime との統合は §8 の深い統合の項目とする。
- IME/手書き: HWR（手書き認識）DLL 群は coredll 顧客として閉じている
  （§3.3）ため原本ホストの対象。SIP（ソフトウェアキーボード）は GWES
  側の仕組みであり、初期範囲では対象外（実機の物理キー＋OSK の扱いは
  §8 で判断材料を出す）。

### 5.5 資源予算（設計目標。実測は M1/M3 で取る）

- シム一式の常駐コスト: 共有ライブラリとして実メモリ数 MB 級を目標
  （ページ共有でプロセス数を増やしても増えない部分）。
- アプリ毎の増分: 実機 CE で動いていた際の作業集合と同程度＋ローダ/
  シムのプロセス内固定費（目標 ≤ 4MB）。
- 辞書級アプリ同時 1 本＋DE 常駐で、128MB の既存予算（DE＋Linux）に
  収まることを M3 の合格条件に入れる。
- キャッシュ方針（本プロジェクト共通原則）: フォントグリフ・アイコン等の
  キャッシュはバイト予算と追い出し方針を持ち、プロセス間で共有する。
  CE ボリュームは読み取り専用マウントのため、ページファイルへの書き戻し
  は発生しない。


## 6. カバーすべき API 表面の見積もり

### 6.1 総量（実測、§3.3 の再掲と解釈）

- 天井: coredll 全輸出 **2,927 件**。この全てを実装する必要はない。
- 静的到達範囲: ROM モジュール 151 本の import union **1,063 件**。原本
  DLL を全てホストし、アプリも全て動かす場合の上限の目安。
- アプリ起点の到達範囲: アプリ系 exe 27 本が直接呼ぶ **874 件**＋各アプリが
  使う SHARP DLL の import（例: SharpLib 経由なら＋239 件のうちアプリ直接分
  と重ならない分）。実務上の計画数値は **900–1,100 件**とする。

### 6.2 機能群別の内訳（アプリ直接呼び 874 件のうち名前解決できた 437 件）

| 機能群 | 件数 | 実装の性質 |
|---|---|---|
| CRT / 文字列 | 106 | 機械的。既存 C ライブラリへの写像が大半。ただし CE 独自の書式・ロケール差異は観察で詰める |
| ウィンドウ / メッセージ | 78 | **意味論が本体**。GWE シムの中核 |
| GDI / 描画 / フォント | 56 | テキスト描画の正確さが品質を左右する |
| 実行 / 同期 / モジュール | 32 | pthread 等への写像。名前付きオブジェクトのプロセス間共有が要点 |
| ファイル / マッピング | 26 | FS ブリッジへの写像。件数は少ないが全アプリの前提 |
| レジストリ | 10 | ストア実装への写像 |
| メモリ | 8 | mmap 系への写像 |
| その他（通知・電源・デバイス・時刻等） | 120 | 個別に小さい。スタブから実需で実装 |
| 序数のみで名前未解決 | 437 | センサスの ordmap で名前解決できる。分類は M0 の作業（本書では未分類として数える） |

未分類 437 件は上記群と同様の分布（CRT と GWE が厚い）と推定されるが、
**推定であり実測ではない**。M0 で ordmap を適用して分類を確定させる。

### 6.3 DLL 別の方針

| DLL | 方針 | 根拠 |
|---|---|---|
| coredll | **再実装（シム）** | カーネルの顔でありホスト不能（§2.2） |
| SharpLib ほか SHARP 層 | **原本ホスト** | 再実装は法的境界の外。import が coredll＋ole32 に閉じる（§3.3） |
| commctrl / commdlg | 原本ホストを第一候補、不可なら薄いシム | import は coredll のみ。ただし commctrl は GWES の内部状態（サブクラス・内部クラス）に依存する可能性があり、M3 で実測 |
| ole32 / oleaut32 | 薄いシムから開始 | 輸出 40/（oleaut32 はセンサス値未集計）。アプリ直接は 3/2 件と薄いが SharpLib が 6 件使う |
| toolhelp | 薄いシム | 輸出 14 件。自作アプリでも使用実績あり |
| ws2（Winsock） | 後段（必要になったアプリで判断） | 輸出 82 件。初期対象アプリはオフライン前提 |
| aygshell | 本ビルドでは主対象にしない | 輸出センサスに現れず、アプリの shell API 需要は SharpLib 側が主（§3.3-3） |
| CE ドライバ DLL（ストリーム） | 原本ホスト（段階導入） | 元設計の橋渡し節を継承。import がシム済み範囲で閉じるものに限る。割込み/DMA を伴うものは UIO 等の別設計が要り初期範囲外 |
| gwes / fsdmgr 等のシステム DLL | 対象外 | カーネル側の存在。シムと FS ブリッジが役割を代替する |

### 6.4 実装規模の見積もり（根拠付き）

- ローダ: PE パーサ＋再配置＋序数/名前 import＋TLS＋DllMain 連鎖。
  既存の自作 PE リンカ（pe-link47.py、生成側）の知識が流用できる。
  **2,000–4,000 行級**と見積もる（推定）。
- coredll シム: 900–1,100 件のうち、大半は「Linux 呼び出しへの薄い写像」
  （数十行/件）だが、GWE 群（ウィンドウ意味論・GDI テキスト・クリップ・
  リージョン）と CE DB 等の深い部分が工数の過半を占める構造になる。
  Wine がデスクトップ Win32 全体に 30 年級を要したのに対し、こちらは
  (i) 表面が約 1/3 の輸出に閉じ、(ii) 実需ベースで段階実装でき、
  (iii) 描画先の部品基盤（libbrainui2）が既にある、ため **全体で
  10^5 行級・1–2 人年級**（辞書級アプリの実用まで）を計画値とする。
  これは関数件数と群構成からの外挿であり、**実測ではない**。M1/M2 の
  実績（実装速度とスタブ解消率）で補正する。
- GWE シムが最大の不確実性。理由: ウィンドウメッセージの順序・描画
  無効化の粒度・フォーカス遷移など、ドキュメント化されない振る舞いを
  実アプリが前提にする度合いが、動かしてみるまで分からないため。
  QEMU 側の実 CE を「正解系」として差分観察できることが、この不確実性
  への主要な対策である（§9.3）。

## 7. ストレージ設計と非破壊の証明

### 7.1 前提（実測と既知事項）

- Brainux の本拠は microSD（p1=FAT32 boot、p2=ext4 rootfs）。WinCE は
  eMMC にあり、SD の FAT boot 領域からチェーンブートされる（本プロジェ
  クトの確定事項）。
- CE 側のボリューム構成（QEMU 側センサス）: \Nand（システム＋辞書・書籍
  データ）、\Nand2（FAT16。追加アプリとユーザデータ）、\Nand3（書籍）、
  \Nand4、ほかに SD は \Storage Card として CE からも見える。
- **未解決の既知問題**: WinCE のパーティションが Linux 側から認識され
  ない件が既に報告され、原因は Linux ドライバ側と利用者が明言し調査が
  開始されている（2026-11-19）。本設計の S0 はこの線上に置く。

### 7.2 読み取り経路（S0: ストレージ第0マイルストーン）

順序を厳守する。**いずれの段階でも eMMC への書込みは行わない。**

1. Linux のブロック層から eMMC の領域境界を「読む」方法を確立する
   （パーティション認識問題の解消を含む）。配置の事実確認には QEMU 側
   プロジェクトが公表済みのセンサスを参照し、本プロジェクトで新たな
   ダンプ解析は行わない。
2. CE ボリュームを **読み取り専用**でマウントできることを示す。
   マウント方式の候補: (i) カーネルの FAT ドライバで `ro` マウント、
   (ii) loop デバイスの read-only 設定、(iii) device-mapper の
   read-only ターゲット、(iv) FUSE による読み取り専用公開。\Nand 本体が
   素の FAT なのか CE 独自のストア管理下なのかは S0 の実測で確定させる
   （\Nand2 が FAT16 であることは確定済み。本体側は未確定と明記する）。
3. ROM モジュール（XIP）が Linux 側マウントでどう見えるかを実測する
   （そのまま PE として読めるか、再構成が要るか）。

### 7.3 書込みの逃がし先（オーバーレイ）

- CE ボリュームは常に読み取り専用マウント（下層）。アプリからの書込みは
  **SD 上の上層**へ透過的に逃がす（overlayfs、または FS ブリッジ内の
  経路振り分けで実装。どちらにするかは S0 の結果で決める）。
  - 上層の置き場: SD の ext4 領域内 `/braince/upper/<volume>/`。
  - 読み取りは下層優先・上層で遮蔽（whiteout 相当）の通常の union 意味論。
- レイヤーが eMMC に対して行う操作は、ブロックデバイスの読み取りと
  読み取り専用マウントのみ。**レイヤーのプロセスは eMMC のブロック
  デバイスノードへの書き込み権限を持たない**ことを権限設計で保証する
  （マウントは特権ヘルパーが ro で行い、レイヤー本体は通常ユーザで動く）。
- 新規に導入する CE アプリ（ユーザが Brainux 側で追加する分）は SD に
  のみ置く。eMMC への追加インストールは行わない。

### 7.4 レジストリ

- CE のレジストリはハイブファイル＋オブジェクトストア側の状態からなる。
  初期実装（v1）は **シム専用ストアを SD に置く**方式とする: アプリから
  見えるレジストリはレイヤーが SD 上で原子的に管理する（書換えは
  tmp→fsync→rename→dir fsync の本プロジェクト標準手順）。
- 収録アプリが前提にする既存キー（SHARP 側が \Nand 上に用意した設定等）
  が必要になった場合は、**読み取り専用に開いたハイブから値を読んで種
  データとして取り込む**段階（v2）を別途設計する。ハイブへの書き戻しは
  どの段階でも行わない。
- これにより「レジストリ経由で WinCE の状態を壊す」経路は構造的に存在
  しない。代償として、CE 側で変更した設定は Brainux 側のレイヤーには
  反映されない（v2 の種取り込みは一方向）。この非対称は仕様として明記
  する。

### 7.5 非破壊の証明プロトコル

「壊れないこと」は主張ではなく、以下の手順で毎マイルストーン証明する。

1. **ベースライン取得**（CE 側）: 通常起動し、チェックリストを記録する
   — wceprj のアプリ一覧が表示されること、辞書アプリが起動すること、
   追加アプリが起動すること、各ボリュームの空き容量表示、主要設定値。
2. **事前ハッシュ**（Linux 側）: CE 領域（S0 で境界が確定した範囲）の
   SHA-256 を計算する。読み取りのみの操作である。対象範囲が 8GB 全域に
   なる場合は所要時間を見積もってから実施方法を決める（454MHz の ARMv5
   での SHA-256 はソフトウェア実装で数 MB/s 級と推定され、全域では
   十数分級になり得る。※推定値。S0 で実測する）。
3. **レイヤーの実行**: 当該マイルストーンの作業（マウント、アプリ実行、
   オーバーレイ書込みを含む）を実施し、終了後にアンマウントする。
4. **事後ハッシュ**: 同範囲を再計算し、**バイト単位で一致**することを
   確認する。不一致があれば即座に作業を止め、原因が特定されるまで
   次へ進まない。
5. **CE 側再検証**: 通常起動し、ベースラインのチェックリストと全項目
   一致することを確認する。
6. ストレージ関連の変更を含むマイルストーンでは 2–5 を **10 サイクル**
   繰り返してから合格とする。オーバーレイ書込みについては「書いた
   ファイルが SD 上層にのみ存在し、eMMC ハッシュが不変」を同時に示す。
7. 常時ガード: マウントヘルパーは ro が保証できない場合にマウント自体を
   拒否する。Brainux 起動時の自己確認として、CE 領域の要所（先頭・末尾・
   ストア管理領域）の部分ハッシュ照合を組み込むことを S0 の設計項目と
   する（全域ハッシュは保守作業として別途）。

### 7.6 失敗時の扱い

レイヤーは eMMC に書かないため、ロールバックは「binfmt 登録の解除＋
アンマウント＋SD 上層の削除」で完結し、復旧作業は存在しない。万一
7.5-4 で不一致が出た場合は、それ自体が「想定外の書込み経路が存在する」
証拠であり、レイヤー全体の停止と原因究明を優先する（そのための
プロトコルである）。


## 8. 統合の深さ: 選択肢と推奨

### 8.1 選択肢

| | (I) 分離レイヤー | (II) 段階統合（推奨） | (III) 深い統合 |
|---|---|---|---|
| 形 | レイヤーは独立したユーザ空間コンポーネント一式（ローダ＋シム＋ランチャー）。braindesk とは「窓サーフェス」と「起動」の2点だけで接する | (I) で開始し、実アプリが動いた後に統合項目を1つずつ採る | binfmt_misc で .exe 直接起動をシステム既定にし、GWE サーバを braindesk プロセス内蔵にし、クリップボード・IME・電源・設定を全面共有 |
| 絶対条件との関係 | 最も安全。レイヤーを止めれば痕跡は SD 上のファイルのみ | 各統合項目ごとに §7.5 の証明を回せる | 接点が増える分、検証面も増える。最初から採る理由はない |
| 利用感 | CE アプリは Brainux の窓として普通に使える。クリップボード共有・日本語入力の共有は無し | 実需の出た項目から順に利用感が上がる | 最も一体感が高い |
| 障害時の影響 | レイヤーのクラッシュは CE アプリのみ | 統合した項目の分だけ広がる | DE 全体に波及し得る |
| 工数 | 最小 | 中（項目ごと） | 最大。しかも初期から |

### 8.2 推奨: (II) 段階統合

- 第1段（M1–M3）: (I) の形で実装する。ただし GWE シムと braindesk WM の
  接続は「WM の既存サーフェスプロトコルへのクライアント実装」として
  設計し、後から内蔵化する余地を残す（プロトコルを介す分離は、内蔵化の
  前段階として無駄にならない）。
- 第2段（M4 以降、項目ごとに判断）: 候補は優先順に
  1. クリップボード共有（CE の OpenClipboard 系 ↔ Brainux 側）
  2. binfmt_misc 登録による .exe 直接起動（§5.2 の実測条件を満たせば）
  3. 日本語入力の共有（libbrainime の出力を CE アプリへ。CE 側の入力
     経路がアプリ依存であるため、対象アプリを定めてから設計する）
  4. 設定アプリへの統合（レイヤーの有効/無効、オーバーレイ管理）
  5. 電源・通知の連携（CE の Notify 系 ↔ Brainux のデーモン）
- **決定はユーザーが行う**。本書は判断材料として、各項目の前提条件
  （どのマイルストーンの実績が必要か）を §9 に紐付けて示すに留める。

## 9. マイルストーン

元設計の M0–M4 を、本書の調査結果に基づいて再定義する。S0（ストレージ
読み取り経路）は M1 と並行可能な独立線として切り出す。

### 9.1 M1（第1マイルストーンの提案）: ローダ＋最小 coredll で自作 CE バイナリが動く

**範囲**

- ce-loader: PE32/ARM の読み込み、再配置、序数・名前 import の束縛、
  DllMain/WinMain 呼び出し、XIP でない通常 PE のみ（XIP は S0 の結果で
  M3 までに追加）。
- coredll シム最小集合（**25–40 件**を目安）: ファイル入出力
  （CreateFileW/ReadFile/WriteFile/SetFilePointer/GetFileSize/
  CloseHandle）、メモリ（LocalAlloc/LocalFree/VirtualAlloc 最小）、
  GetTickCount、Sleep、Get/SetLastError、OutputDebugStringW、テスト
  バイナリが必要とする CRT/文字列の最小集合。
- FS ブリッジ v0: CE 絶対パス（`\CE-TEST\...` 等）を **SD 上または
  開発ホスト上の通常ディレクトリ**へ写像するだけのもの。この段階では
  eMMC に一切触らない。
- 未実装 API はログ付きスタブ（呼び出しを記録して失敗を返す）。
  M1 の対象バイナリの実行経路でスタブが踏まれないことを合格条件に
  含める。

**テストバイナリ**

- 既存の実績経路（clang armv5te＋pe-link47.py）で自作する。仕様:
  ファイルを作成して既知のバイト列を書き、読み戻して照合し、結果を
  別ファイルへ記録するだけのもの（P47App のファイル部分が原型）。
- 実行環境は2段: (i) 開発ホスト上の qemu-arm（ユーザモード）で
  ローダごと ARM バイナリとして動かす開発ループ、(ii) 実機 Brainux。
  qemu-arm 上ではローダもゲストコードも TCG 実行されるため、これは
  正しさの検証であり速度の検証ではない。

**合格条件**

- テストバイナリが (i)(ii) 両方で期待どおりのファイルを生成する。
- 実行経路上の未実装スタブ呼び出しが 0 件（ログで示す）。
- eMMC には触れていないこと（この段階の設計自体が触らない。S0 と
  合流する M3 以降で §7.5 の証明を適用する）。

### 9.2 後続マイルストーン（概要）

| 段階 | 内容 | 合格の目安 |
|---|---|---|
| S0 | §7.2 の読み取り経路確立＋§7.5 プロトコルの初回実施 | CE 領域が ro で読め、ハッシュ前後一致＋CE 側チェックリスト一致を 10 サイクル |
| M2 | GWE 最小（窓・メッセージループ・GDI テキスト・塗り） | 自作 GUI バイナリ（P47App 級、25 件）が Brainux の窓として表示・操作できる |
| M3 | 実アプリ（単機能）＋原本 DLL ホストの初実証 | commctrl 原本ホストの可否を実測。単機能の収録アプリ（例: ToolsApp の小物）が実機で起動。§7.5 証明を適用 |
| M4 | 辞書級アプリ | SharpLib 原本ホスト（import 239 件の到達度を実測で示す）＋辞書アプリの検索・表示。RAM 予算（§5.5）の実測 |
| M5 | 段階統合の各項目 | §8.2 の項目ごとにユーザーが採否を決める |

### 9.3 検証基盤

- **正解系**: QEMU 側プロジェクトの実 CE 環境（PW-SH6 の完全仮想化）が
  デスクトップ上に存在する。レイヤー上のアプリの振る舞い（画面・ファイル
  出力・API の戻り値）を実 CE と突き合わせる差分観察を、各マイルストーン
  の標準手順とする。
- **テストベクタ**: 自作 CE アプリ群（§3.4）は coredll import 数が
  14–70 件と段階的であり、そのまま到達度の物差しになる。
- 回帰: シムの関数を追加するたびに「既に動いているバイナリが引き続き
  動くこと」を自動で確認する仕組みを M2 までに用意する。

## 10. リスク・未調査・未検証（正直な棚卸し）

**未調査・未確認（本書の結論に影響し得る）**

1. 「Windows CE Compatibility Layer」（Wiki 一覧掲載）の実体と到達点は
   一次資料で確認できていない（§4.1）。存在すれば §4 の結論の一部
   （流用土台なし）が変わり得る。
2. \Nand 本体ボリュームの Linux 側での見え方（素の FAT か、CE ストア
   管理下か）と、XIP モジュールの読み取り形は未実測（S0 の対象）。
3. アプリ直接呼び 874 件のうち 437 件が序数のみのままで機能分類が
   未確定（§6.2）。M0 で ordmap を適用して確定させる。
4. アプリが前提にする GWES の未文書化の振る舞いの深さは、動かすまで
   分からない（§6.4）。M2/M3 で初めて実測される。
5. commctrl 原本ホストの可否は未実証（§6.3）。不可の場合、リストビュー
   等の部品は libbrainui2 側の部品への写像で代替する設計に切り替える
   （部品基盤は本プロジェクトに既にあるため、致命的ではない）。
6. CE 領域の全域ハッシュの所要時間は推定のまま（§7.5-2）。S0 で実測。
7. 本書のハードウェア値（i.MX283 / 454MHz / 128MB）は PW-SH1 の資料と
   世代整理に基づく。PW-SH6 個体の実測値ではない。

**設計上のリスク**

- レジストリ v1 の非対称（§7.4）: CE 側の設定変更がレイヤー側に反映
  されない。アプリによっては初回起動時の前提キーが無くて動かない
  可能性があり、その場合は v2（読み取り種取り込み）を前倒しする。
- オーバーレイの意味論差: CE のファイルシステム前提（大文字小文字を
  区別しない、属性、ファイルロック）との差異は FS ブリッジで吸収する
  設計だが、ロックと共有モードの厳密さは実アプリで初めて試される。
- Thumb コード: 自作アプリは ARM 状態のみでビルドされているが、収録
  アプリに Thumb/Thumb-2 が混在するかは未確認。ローダとシム境界は
  両状態の混在を前提に設計する（AAPCS の状態遷移規則に従う）。

**本書で「できる」と言っていないこと**

- 収録アプリの全てが動くとは言っていない。到達範囲は coredll シムの
  実装到達度に比例し、ドライバ直結・カーネル前提・未実装 API を踏む
  アプリはその都度対象外になる。進捗は「動くアプリと、その根拠である
  スタブ解消ログ」で報告する（虚偽の報告は禁止という本プロジェクトの
  規律に従う）。
