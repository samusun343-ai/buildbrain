# デスクトップマスコット: 形式調査と .bdm 形式仕様

対象: braindesk2 (Brainux 再構築、PW-SH6: ARMv5 / RAM 128MB / GPU なし /
fbdev 800×480)。方針は「変換時に実機向け最適化を全て済ませ、実行時は
デコードもスケールもしない」。

## 1. 変換元の調査と比較

| 形式 | 実体 | 本機での扱い |
|---|---|---|
| **Shimeji / Shimeji-ee** | フォルダパック: `shime1.png`〜（透過 PNG、全身 128×128 が古典）＋ `conf/actions.xml`（Pose 列: 画像・アンカー・速度・長さ、Action 種別 Stay/Move/Animate/Sequence/Select/Embedded）＋ `conf/behaviors.xml`（Frequency 重み＋条件＋NextBehaviorList）。エンジンのティックは 40ms（25/s）。初音ミク等のキャラセットが大量に流通 | **変換元として採用**。行動モデル（落下・ドラッグ・投げ・床を歩く/座る）が本機のデスクトップと一致し、全て静的データなので完全バイナリ化できる |
| **Live2D (Cubism)** | .moc3 モデル＋モーション。現代の主流 | **直接実行は不採用**。理由: (1) Cubism Core は独自ライセンスで再配布不可、(2) レンダラは OpenGL シェーダ/FBO 前提で本機（GPU なし・fbdev）向けターゲットが存在しない、(3) メッシュ変形＋物理演算を ARMv5 のソフトウェア描画で 128MB に収めるのは現実的でない。取り込むなら「他環境でモーションをフレーム列に焼き、Shimeji 相当のスプライト列として変換」が唯一の現実路（= 本形式の入力として扱える） |
| スプライトシート単体 | 1枚絵＋フレーム矩形のみ | 行動情報（速度・アンカー・重み・必須アクション）を持たず、マスコットとして動かすには結局 Shimeji 相当のメタが要る。変換元の第一候補にはならない |

補足: Shimeji 形式には英語スキーマと**日本語ローカライズスキーマ**
（要素・属性・列挙値が日本語。流通している初音ミクのセットはこちら）
があり、コンバータは両対応（読み込み時に英語名へ正規化）。

## 2. .bdm 形式（独自形式、version 1）

全てリトルエンディアン。ファイルは mmap してそのまま使う
（実行時デコードなし）。オフセットはファイル先頭から。

### ヘッダ (80 バイト)

| off | 型 | 内容 |
|---|---|---|
| 0 | char[4] | magic `BDM1` |
| 4 | u16 | version = 1 |
| 6 | u16 | flags (bit0: アトラスあり) |
| 8 | u32 | ファイル総バイト数 |
| 12 | char[24] | キャラ名 (UTF-8, NUL 終端) |
| 36 | u16/u16 | 元キャンバスの union crop 幅/高さ |
| 40 | u16 | clip 数 |
| 42 | u16 | pool 件数 |
| 44 | u16 | 焼きサイズ数 |
| 48 | i16 ×4 | special clip: fall / drag / thrown / stand（無ければ -1） |
| 56 | u32 ×4 | セクションオフセット: clips / pool / sizes / strtab |

### clip メタ (16 バイト × clip 数)

name_off(u16, strtab 相対) / pose_count(u16) / total_min_ms(u16) /
total_max_ms(u16) / pose_start(u32, サイズ別ポーズ列への添字) /
type(u8: 0=Stay 1=Move 2=Animate) / border(u8: 0=None 1=Floor
2=Wall 3=Ceiling) / flags(u8: bit0=loop) / 予約(u8)

### pool (4 バイト × 件数)

clip(u16) / weight(u16)。床の上で抽選される行動の重み表。
コンバータが behaviors.xml から「床条件でゲートされた行動＋
その NextBehaviorList の床到達分」だけを残して生成する。

### サイズレコード (24 バイト × サイズ数)

height(u16) / atlas_w, atlas_h(u16) / frame_count(u16) /
frames_off(u32) / poses_off(u32) / atlas_off(u32) / scale_q8(u16)

- frame (12 バイト): x, y, w, h（アトラス内）, bearing bx, by
  （crop 内の表示オフセット。全フレーム共通 crop＋フレーム別
  トリムの差分を保持し、位置合わせを bearing で吸収）
- pose (12 バイト): frame(u16) / dur_ms(u16) / ax, ay(i16,
  **このサイズにスケール済み**のアンカー) / vx_q8, vy_q8(i16,
  px/tick の 256 倍)
- atlas: premultiplied **0xAARRGGBB**、幅 1024 シェルフパッキング

### 変換時最適化（実行時コストをゼロにするための前処理）

1. 全フレームの union crop＋フレーム別トリム（bearing で位置保持）
2. 焼きサイズ複数（既定 168/208/248px 高）を **Lanczos** で生成。
   実行時は要求高さに最も近い焼きサイズを選ぶだけ（拡大縮小なし）。
   ※ 128px ソースでは 208 は高品質アップスケールになる。表示高
   ~200px の要求を優先し、焼き側で済ませる（実行時スケールは
   どのみち行わない）
3. ピクセル同一フレームの重複排除（Shimeji 既定セット: 46 枚→
   43 フレーム）
4. ピクセルは premultiplied ARGB に事前変換（ツールキットの
   キャンバス内部形式と一致）。**形式選定は実測**: 同一スプライト
   でのブレンド処理は premult 105〜966 Mpx/s、straight RGBA
   52〜550、RGB565+alpha 27〜367（ホスト実測、スロットリングで
   幅があるが順序は全試行で不変）→ premult が 2〜8 倍速い。
   16bpp fb への転送は従来どおりダメージ矩形のみ（セッションの
   16bpp 会計に合流）
5. Sequence/Select は平坦化（Select は最初に解決できる分岐）、
   ActionReference の Duration 上書き式（`${500+Math.random()*1000}`
   等）は [min,max] 区間に評価してポーズ長へ按分
6. 条件（Condition）は「床のみモデル化」: 床ゲートは残し、
   壁・天井・ウィンドウ（IE）枠ゲートの分岐・行動・クリップは
   落とす。コード実行だけの Embedded（Look/Offset 等、Pose
   なし）も落とす

### ランタイムの行動モデル（src/mascot.c）

- 状態: FALL（重力 0.625px/tick²、上限 20px/tick）→ 着地 →
  IDLE/WALK（pool から重み抽選、Stay はデータの長さ、Move は
  端で反転しながら歩行）／DRAG（ドラッグ中、離すと投げ速度
  ±12px/tick で FALL）／REACT（タップ反応: pool の Animate を
  優先、無ければ Stand）
- 物理は 40ms 量子（元のエンジンと同一）。キャッチアップは
  最大 5 ステップ、余りは捨てる（スパイラル防止）
- 描画はダメージ矩形のみ: tick が「旧スプライト矩形＋新
  スプライト矩形」を返し、セッションが下層を再描画してから
  マスコットをクリップ付きでブレンドする。静止ポーズ中は
  ダメージ 0（セッションの「静かなフレームは転送 0 バイト」
  性質を維持）
- 表示ポリシー: デスクトップ表示中のみ。全画面ウィンドウが
  フォーカス中は隠す（brainreg `mascot/fullscreen=1` で常時
  表示に変更可）。ランチャー/QS 表示中も隠れる

### 設定（brainreg セクション `mascot`）

| キー | 既定 | 内容 |
|---|---|---|
| enabled | 1 | ON/OFF |
| pack | （探索順） | .bdm パス。探索: このキー → 環境変数 `BRAINUX_MASCOT_PACK` → `~/.local/share/brainux/mascots/mascot.bdm` → `/usr/share/brainux/mascots/mascot.bdm` |
| size | 208 | 表示高 px（最も近い焼きサイズが選ばれる） |
| fullscreen | 0 | 1 で全画面アプリの上にも表示 |

## 4. .bdm 形式 version 2（高精細・高 fps 用の拡張）

等身・高解像度のフレーム列（Live2D 焼き込み等、24〜30 fps）を
扱うための拡張。ヘッダの version=2 で区別し、ランタイムは
v1/v2 両対応（v1 パックは従来どおり読める）。変換は
`frames_to_bdm.py`（連番 PNG＋manifest.json → .bdm）。

設計判断: 全フレームをアトラスに持つ v1 方式は 320px・588
フレームで約 70MB になり不適。フレーム間差分を使うが、矩形
差分は全身の微振動でほぼ全面化して失敗した（実測: 差分 bbox
方式 112MB、行バンド方式 100.8MB）。最終方式は次の 3 点:

1. **許容誤差マスク**: 変化画素 = 再構成済みバッファとの
   premult 各チャンネル差が tol（既定 8）を超えた画素のみ。
   AA エッジの微小変化の大半が落ち、変化画素は全面積の
   0.5〜5% になる。パッチ画素自体は正確値で持つため、表示
   誤差は全画素・全時刻で tol/チャンネル以下に保証される
   （`--verify` が再構成して最大偏差を検証する）。
2. **スパースラン符号化**: 差分は矩形でなくスキャンライン
   ラン列 `(u16 skip, u16 len, len×u32 premult値)*`、終端
   (0,0) で持つ。ランタイムは合成バッファへ memcpy 級の
   適用のみで、伸長・復号は無い。
3. **ドロップパス**: 最大サイズで 1 回だけ、tol マスクの
   変化率が閾値未満のフレームを落とし、duration を直前の
   kept ポーズへ加算（kept リストは全サイズ共通）。遅い
   動きほど実効 fps が下がり、速い動きは原 fps を保つ。

### フレーム種別（v2）

| kind | 意味 |
|---|---|
| 0 FULL | バッファをクリアし α トリム矩形をアトラスからコピー。クリップ先頭と keyint（既定45）毎が必須 |
| 1 SPARSE | スパースランをバッファへ適用。ダメージ帯（最大8矩形）を持つ |
| 2 SAME | バッファ無変更。ダメージ 0 |

### サイズレコード v2 (32 バイト × サイズ数)

| off | 型 | 内容 |
|---|---|---|
| 0 | u16 | 表示高 px |
| 2 | u16 | アトラス幅（FULL フレーム専用） |
| 4 | u16 | アトラス高 |
| 6 | u16 | フレーム数 |
| 8 | u32 | フレーム表オフセット |
| 12 | u32 | パッチ（ダメージ帯）表オフセット |
| 16 | u32 | スパース節オフセット |
| 20 | u32 | ポーズ表オフセット |
| 24 | u32 | アトラスオフセット |
| 28 | u16 | scale Q8 |
| 30 | u16 | フレームレコード長（=20） |

サイズ毎の節順序は frames | patches | sparse | poses |
atlas。セクション境界は次セクションのオフセットで決まる。

### フレームレコード v2 (20 バイト)

| off | 型 | 内容 |
|---|---|---|
| 0 | u16 | アトラス x（FULL のみ） |
| 2 | u16 | アトラス y |
| 4 | u16 | 幅 |
| 6 | u16 | 高さ |
| 8 | i16 | 配置 bx（キャンバス座標） |
| 10 | i16 | 配置 by |
| 12 | u16 | kind |
| 14 | u16 | ダメージ帯の数（SPARSE のみ） |
| 16 | u32 | スパース節内バイトオフセット（SPARSE のみ） |

ダメージ帯はポーズ順にパッチ表へ連結されており、各フレー
ムの帯開始位置は nband の累積和で復元する（ランタイムが
ロード時に prefix-sum 配列を構築）。パッチレコードは v1 と
同じ 12 バイト (x, y, w, h, bx, by) で、SPARSE では x/y=0
（画素なし）、w/h/bx/by が帯矩形（キャンバス座標）。

ダメージ帯の生成: 行ごとの変化 x ランを、x 範囲が重なる間
縦にマージする（動いた輪郭の縁に沿う矩形群になる）。8 本を
超える場合は y 方向に隣接するペアのうち和集合の面積増加が
最小のものからマージする。全変化画素が必ず覆われる。

### ランタイム（v2）

- **合成キャンバス幅の定義（仕様として固定、2026-11-20）**:
  サイズ段の合成キャンバス幅は
  **round-half-even(crop_w × size_h / crop_h)**（有理数として
  正確に計算する）。スパースペイロードはこの幅に対する
  フラットな画素ストリームなので、幅の解釈が 1px でも
  ずれると全書き込みが斜めに剪断する。コンバータは従来
  この値（浮動小数の round）で焼いており、ランタイムが
  scale_q8 から近似した幅を使っていたのが Mao グリッチの
  根本原因（crop 829×1200 @320 で 221 対 220）。両側とも
  本定義に統一すること（v3 共通形式でも同じ定義を使う）。
- 描画（bd_mascot_paint）はクリップ矩形の和集合内でのみ
  描き、**各ピクセルは最大1回だけブレンドする**。ダメージ
  帯は設計上互いに重なるため、矩形ごとに描くと重なり部の
  半透明ピクセルが二重ブレンドされ、帯の縁に明暗の縁取り
  が出る（Mao グリッチの第2の原因）。行ごとに x スパンを
  マージしてから描く実装が正。
- 合成バッファ（crop_w_s × size_h × 4B、320px で約 130KB）
  を 1 枚持ち、mmap は読み取り専用のまま（ゼロコピー維持）。
- comp_sync: 同一クリップ内で前進する場合は中間フレームを
  逐次適用。巻き戻し・クリップ変更時は対象ポーズ以前の
  直近 FULL まで走査して再同期する。
- ダメージ: 矩形・向きが変わらなければ帯矩形のみを返す
  （最大8）。FULL が来た tick は全体矩形 1 つ。SAME は 0。
- 表示範囲（extent）は FULL 矩形と適用済み帯の和集合で
  維持し、描画・ヒットテストはその範囲で行う。
- メインループ: マスコットがアニメーション中はステップを
  33ms に詰める（`bd_mascot_animating()`）。静止時は従来
  どおり転送 0。

## 5b. .bdm 形式 version 3（WinCE .bmas との共通形式）

Brainux .bdm と WinCE .bmas を単一仕様に統合したもの。協議の
場は `~/workspace/mascot-shared/SHARED.md`。設計原則は両側共通:
**重い計算は変換時に終え、形式へ焼き込む。実行時は適用のみ。**

- コアは v2 そのもの（許容誤差マスク＋スパースラン、帯ダメー
  ジ、ドロップパス、誤差保証 verify）。Brainux ランタイムは
  v3 を v2 として読み、拡張節を検証だけして無視できる。
- サイズレコードは 48 バイト（v2 の 32 バイト＋ regions_off /
  regions_len / rgb565_off / rgb565_len、各 u32）。
- ヘッダ flags: bit0 premult atlas、bit1 delta、bit2 regions
  あり、bit3 rgb565 プロファイルあり、bit4 rgb565 節が
  スパース形式。
- **リージョン節**（サイズごと、ポーズ順の逐次ストリーム）:
  変換時に合成済みフレームから窓リージョン矩形列を導出して
  焼き込む（WinCE の「フレームごとリージョン事前計算」要求
  と同一物）。符号化はクリップ単位: 先頭ポーズは全リスト
  （ndel=0xFFFF センチネル＋ nadd 件の矩形）、以降は前ポー
  ズへの remove（u16 インデックス列）/ add（矩形列）デルタ。
  矩形は (x, y, w, h) 各 u16、キャンバス座標。WinCE 側は
  SetWindowRgn 用にそのまま適用でき、実行時のリージョン再
  構築は不要。
- **リージョン矩形列の定義（仕様として固定、2026-11-21 改訂）**:
  ポーズのリージョンリストは、合成済みフレームの
  **α ≥ 128 シルエット**を次の帯域化ラン和集合でタイリング
  したものと定義する。キャンバスを高さ B 行の水平帯に切り
  （最終帯は余りの高さ）、各帯についてシルエットを x 軸へ
  射影する（帯のいずれかの行にシルエット画素がある列を被覆
  列とする）。被覆列の極大ラン 1 つが矩形 1 つになり、矩形
  は帯の全高にわたる。リストの順序は帯の上から下、各帯内は
  x の昇順で、矩形は互いに相異なる。
  **帯高 B = clamp(round-half-even(H / 40), 4, 8)**（H は
  サイズ表示高。有理数として正確に計算する。H=320 で B=8、
  H=248 で B=6）。320 での 8 行が CE 側実証済みの基準値で、
  帯高を表示高に比例させるのは、小さいサイズでは同じ絶対
  ゆとりが相対的に重く締まりが悪化するため（248 で一律 8 行
  だと実測平均 1.163 で基準 1.15 を超過、比例帯では 1.119）。
  矩形数は全サイズで同程度（実測平均 75〜116）に収まる。
- **リージョン矩形数の上限（仕様として固定、2026-11-21
  追加）**: ポーズごとの矩形数には上限がある。CE 側の
  SetWindowRgn 適用コストは矩形数に超線形で、約 113 矩形
  では 66〜74ms/回とポーズ間隔を超過した（CE 側実測、
  p59）ため、締まりと並ぶ生成側の規律とする。上限は焼き
  込みパラメーター `--region-max-rects`（既定 100、0 で
  無制限。tol と同様にファイルへは格納しない）。導出手続き:
  (1) 上記の帯域化ラン和集合を作る。(2) 矩形数が上限以下
  ならそのまま確定する（上限以下のポーズのリストは帯域化
  ラン和集合そのもので、上限の導入は既存の適合パックを
  書き換えない）。(3) 超える場合は同一 (x, w) で縦に連続
  する矩形を統合する（和集合は不変）。(4) なお超える場合
  は、隣接ペア（縦に接する、または同一の (y, h) で横に
  並ぶ）のうち、bbox 化で新たに被覆される画素数が最小の
  ペアを繰り返し統合する（同点はリスト順の早いペアを採
  る。リストは (y, x) 順に保ち、統合で生じた重複矩形は
  除く）。隣接ペアが存在しない場合は bbox スラック最小
  のペアで代用する。(5) 上限以下になったら停止する。
  統合で被覆は広がるだけなので被覆条件は保存され、代償
  は締まりである。帯高比例式との関係: 帯高は基本タイリ
  ングの粗さ（全ポーズ一律）を決めるもので、上限はポー
  ズ単位の後処理であり、互いに独立である。ポーズごとに
  帯高を粗くする適応帯高方式は、実測で締まり平均が基準
  を超えた（ヒカリ @320 で 1.164）ため採用しなかった。
  実測（上限 100）: ヒカリ @320 は矩形数 平均 112.7・
  最大 123 → 99.8・最大 100、締まり平均 1.134 → 1.139・
  最大 1.147 → 1.155。@248 は 116.0・最大 128 → 99.9・
  最大 100、締まり 1.119 → 1.125・最大 1.136。ミク
  @320 は上限内のため無変更（バイト同一）。
  - 旧定義（α>0 マスクへの縦マージ＝ダメージ帯と同一導出）
    は、マージのたびに x 範囲が和集合へ拡張され、縦に長い
    形状で矩形がシルエットの bbox へ退化した（実測: 和集合
    /シルエットがミク 1.64×・ヒカリ 1.98×、α>0 基準）。
    被覆は正しかったため被覆のみの検証を素通りした。CE で
    はリージョンがそのまま窓形状になるため、余分な面積が
    キャラ周囲の黒露出になった。これが本改訂の理由である。
  - α 閾値 128 には、565 プロファイルのフリンジ輝点（低 α
    の直色復元で増幅された縁画素）を窓外へ落とす副次効果も
    ある。閾値未満の縁画素は窓の外になるのが本定義の意図で
    あり、被覆・締まりの判定は α ≥ 128 シルエットに対して
    行う。
- **リージョンリストの順序セマンティクス（仕様として固定、
  2026-11-20）**: デルタ適用後のリストは「前リストから削除
  インデックス分を除いた残り（元の順序を保持）に、追加矩形
  をストリーム順で末尾に足したもの」と定義する。削除イン
  デックスはこの順序に対する位置である。エンコーダは次デル
  タのインデックスを、焼いたばかりの幾何順序ではなくこの
  デコーダ再構成順序に対して計算しなければならない。両者
  がずれた実装（幾何順序で計算）では、2 回目のデルタ以降に
  誤った矩形が削除され、被覆が約9割のポーズで崩壊した実績
  がある（Mythra / ミク HD の実パックで再現・修正済み）。
  リスト内の矩形は互いに相異なること（同一矩形の重複なし）
  を前提とする。
- **RGB565 プロファイル節**（任意、サイズごと、ポーズ順）:
  ポーズごとのフルフレームを straight（非 premult）RGB565
  で格納。レコードは v1 フレームレコードと同じ 12 バイト
  (x=0, y=0, w, h, bx, by)＋ w*h*2 バイトのピクセル。WinCE
  側の「RGB565 原生・実行時デコード/スケールなし」要求に対
  応する。シルエット外ピクセルはリージョンで切り取られる
  前提で未定義でよい（変換では 0 埋め相当の値になる）。
- **RGB565 スパース形式**（flags bit4、2026-11-20 追加）:
  フルフレーム形式が HD 級で BMAS v3 総量の 3.8 倍に達し
  「従来形式より悪化しない」条件を満たさなかったため、
  WinCE 側対案に基づくスパース形式を併設する（bit4=0 の
  フル形式も引き続き有効）。節の内容はポーズ順のレコード
  列で、各レコードは u16 kind（0 FULL / 1 SPARSE / 2 SAME、
  コアと同値）から始まる。FULL は u16 w / u16 h / i16 bx /
  i16 by ＋ w*h 個の u16（α-bbox 矩形）、SPARSE は u32
  ペイロード長 ＋ コアと同じラン形式（u16 skip / u16 len /
  len 個の u16 値、(0,0) 終端。キャンバス幅に対するフラッ
  トストリーム）。ピクセル値は**ソースフレーム**（その
  サイズの premult キャンバス）を straight 化した RGB565:
  c_s = min(255, c_pm × 255 // max(a, 1))、量子化は最近傍
  レベルへの丸め（L = (c_s × maxlevel + 127) // 255、
  maxlevel は 31/63/31）— フル形式と同一の定義。2026-11-21
  の p61 で切り捨てから変更した（シルエット量子化 PSNR が
  ヒカリ +1.55 dB / ミク +1.93 dB。BMAS 側の同変更の実測と
  一致）。マスクは
  既定では 565 空間での完全不一致で取るため、CE 側の再構成
  は「ソースの 565 量子化」と完全一致する（verify は許容
  誤差でなく完全一致を要求する）。焼き込みパラメーター
  rgb565_tol > 0 の場合はコアと同じ有界誤差マスクになる:
  変更画素 = CE バッファの展開値（c = level × 255 //
  maxlevel）と目標の展開値のチャンネル差が tol を超えた
  画素のみ、保存値は正確値のため表示誤差は全時刻で tol
  以下に保証される（verify は同じ tol で照合する。tol は
  コアの tol と同様ファイルには格納しない焼き込みパラメー
  ター）。バッファはクリップ単位でリセットし、クリップ
  先頭ポーズは FULL（コアと同じシーク意味論）。
- **エッジ色ブリード（焼き込みパラメーター `--rgb565-bleed`、
  2026-11-21 p61 で追加）**: スパース形式の目標値は、量子化
  の後に「リージョン和集合に含まれシルエット（α ≥ 128）の
  外にある画素」を最も近いシルエット画素の 565 色で置き換
  えたものとする。リージョン帯は α-bbox の上下に最大で帯
  高分はみ出すため、ブリード有効時の FULL レコードの格納
  矩形は α-bbox とリージョン被覆 bbox の和集合とする（レ
  コードは矩形を明示保持するので形式変更なし、リーダ無変
  更）。CE では窓形状＝リージョンであり、帯ステップ内に露
  出する α=0 画素は straight 化で黒 (0) になり輪郭に沿った
  黒ダッシュとして表示されていた（BMAS が p56 から持つ
  bleed_colors と同じ処方）。実測（ヒカリ @320 Stand f0）:
  被覆内・シルエット外・輝度 < 64 の暗色画素 1,365 → 2。
  tol や region-max-rects と同じくファイルへは格納しない
  焼き込みパラメーターで、verify には同じフラグが要る。
- 合格条件（相互検証）: 共通テストパックを両側の復号系で読
  み、(1) スパース復号が元フレームと tol 以内、(2) リージョ
  ンが復号シルエット（α ≥ 128）を完全に覆い、かつ**締まり
  ＝ リージョン和集合面積 / シルエット面積のポーズ平均が
  1.15 以下**、(3) RGB565 プロファイルが復号フレームと量子
  化誤差（各チャンネル ≤9）以内で一致、(4) **全ポーズのリ
  ージョン矩形数が上限（既定 100）以下**、を全て満たすこ
  と。Brainux 側は `frames_to_bdm.py --verify` が
  (1)(2)(3)(4) を検査し（締まりと矩形数は平均に加えて最
  大値も報告する）、C ランタイムは
  `bd_mascot_regions_at()` でリージョン列を独立に復号する。
- プロファイルの選択は焼き込み側の自由: Brainux 専用パック
  はリージョン/RGB565 を付けなければ v2 と同容量。共通パッ
  クは両プロファイル入りで焼く。

## 5. 既知の制限（変換の割り切り）

- ChaseMouse はポインタ追尾として再現しない（Embedded のため
  クリップ化されない）。ドラッグ/タップ反応で代替
- ウィンドウ枠・壁・天井の行動は落とす（本機の「床」はメイン
  領域の下端＝Shelf の上面のみ）
- 分裂（SplitIntoTwo 等）は単体アニメーションとして再生
  （2 体にはならない）
- 吹き出し（dialogues）は未対応
