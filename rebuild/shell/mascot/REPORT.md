# デスクトップマスコット 実装レポート

ユーザー要求（2026-11-20）: 2D デスクトップマスコット対応。
現代のマスコットデータを独自形式へ変換して使えること、低品質化
ではなく実機向け最適化＆調整、初音ミク等の全身キャラを実機に
合わせた小さめサイズ（表示高 ~200px）で。

## 性能実測（ホスト実測。実機換算は未実施＝統合フェーズ）

bench_mascot、Shimeji パック、表示 208px、仮想 60 秒を 50ms
ステップで回した結果:

- ダメージ発生フレーム: 全ステップの **18%**（待機ポーズ中は
  ダメージ 0、セッションの静フレーム転送 0 を維持）
- ダメージ発生時の平均: 55,767 px/フレーム（≒ 旧＋新スプライト
  矩形 2 枚分）、全ステップ平均の転送量 **約 20.2 KB/step**
  （16bpp 会計）
- CPU: tick＋背景再描画＋ブレンドで **108〜243 µs/step**
  （ホスト共有 CPU、試行差あり）
- RSS: ロード時の増加 **約 0.36 MB**（17MB のパックを mmap
  するため）。60 秒の多彩なアニメーション後はタッチした
  アトラスページのキャッシュで +5.5〜6.6 MB（クリーンな
  ファイルページで回収可能。128MB 予算内）
- ブリット形式比較（同一スプライト、ホスト）: premultiplied
  ARGB が全試行で最速（straight RGBA の約 2〜3 倍、RGB565+
  alpha の約 4〜8 倍）→ .bdm のピクセル形式として採用

アニメーションの実効 FPS: 元データのポーズ長が 120〜250ms
中心のため待機 4〜8fps、歩行 8〜12fps 相当。25 ティック/秒の
物理は維持しつつ、再描画は変化した時だけ。

## 高精細化（2026-11-20 追加要求「もっとリアルに」）

ユーザー要求: ちびキャラ絵ではなく、等身寄りの全身＋滑らかな
動き＋大きめ・高精細表示。合格条件（ユーザー明示、優先）:
(1) GPU・専用ランタイム不要が本質（実行時は .bdm の焼き込み
フレームを貼るだけ）、(2) 品質バーは「人が見た時に違和感が
ない」（滑らかさ、透過・輪郭の綺麗さ）、(3) RAM 128MB・
i.MX28 級 CPU・fbdev の予算内を実測で示す。

### 方式比較と採否

| 方式 | 判定 | 根拠 |
|---|---|---|
| Live2D モーションを変換時にフレーム列へ焼き込む | **採用** | live2d-py 1.0.0（Cubism SDK 5-r.5 同梱 wheel）がこの VM で動作し、Xvfb＋Mesa ソフトウェア GL で描画成功。等身・30fps ネイティブモーション・高解像度ソースが得られる。Cubism Core は再配布不可ライセンスだが、使うのはホスト側変換時のみで端末には一切入らない |
| 等身の高解像度 Shimeji 系スプライトセット | 不採用 | 等身セットの流通が乏しく、フレーム数（コマ数）が少なく滑らかさで劣る。形式としては v1 のまま扱える |
| 実行時クロスフェードで補間 | **不採用** | Shimeji フレーム 35→36 の 50% ブレンドを実画像で確認: 動いた脚が二重の半透明像（ゴースト）として明確に見える。大きな動きではゴースト、小さな動きには 30fps 焼き込みで代替できるため不要 |
| フレーム間差分（矩形） | **不採用** | 実測で失敗: 全身の微振動により差分 bbox がほぼ全面化（差分 bbox 方式 112MB、行バンド方式 100.8MB）。代わりに許容誤差マスク＋スパースラン符号化を採用（下記） |

変換元モデル: Live2D 公式サンプル **Hiyori（桃瀬ひより）**
（CubismWebSamples 同梱、全身・等身寄り、キャンバス
2976×4175、Idle×9＋TapBody モーション）。公式の初音ミク
Live2D は Editor ソース（.cmo3/.can3）のみ配布でランタイム
形式が無く、ミクで焼くにはユーザー供給のランタイムモデル
が前提になる（限界として明記）。

### 変換パイプライン

1. `bake_live2d.py`（新規）: live2d-py でモデルを再生し、
   手続き的呼吸・瞬き（Stand）＋モーションクリップを
   30fps の PNG 連番＋manifest.json に焼く。ひより実績:
   855×1200 キャンバス、5 クリップ 588 フレーム
2. `frames_to_bdm.py`（新規）: 連番 PNG → .bdm v2。
   許容誤差マスク（再構成バッファとのチャンネル毎差 > tol=8）
   ＋スパースラン符号化＋ドロップパス。仕様は FORMAT.md §4

変換中に見つけて直した不具合: 当初のマスク計算はパック済み
ARGB のまま減算しており、チャンネル境界をまたぐ借りで誤差
を過大評価（容量増）し、病理的には実差分を見落とし得た。
チャンネル毎に展開してから差分を取る形に修正し、全数値を
修正後に取り直した（以下の実測は全て修正後のもの）。
`--verify` も同じチャンネル毎算術で検証する。

### 性能実測（ホスト実測、bench_mascot、仮想 120 秒）

| 構成 | 転送/step 平均 | 転送最大/step | CPU/step | RSS 増（ロード時／模擬後） |
|---|---|---|---|
| ちび v1 @208、50ms | 18,068 B | 166,860 B | 44 µs | +0.32 MB / +6.6 MB |
| ひより v1 @320、33ms（60 秒） | 77,637 B | 133,980 B | 423 µs | +0.24 MB / +56.5 MB |
| ひより v2 @248、33ms | **13,879 B** | 80,028 B | 89〜174 µs | +0.3〜0.4 MB / +6.2 MB |
| ひより v2 @320、33ms | **25,054 B**（≒0.76 MB/s） | 133,760 B | 180〜309 µs | +0.42 MB / +10.4 MB |

- CPU はホスト共有 CPU の競合（並行 QEMU ライン）で試行差が
  大きいため範囲で示す。i.MX28 換算は未実測（推定では
  2〜6 ms/step 級で 33ms 予算内だが、実機/QEMU 測定は
  統合フェーズの残件）
- v1 @320 の模擬後 RSS +56.5MB は、全フレームをアトラスに
  持つため触れるページがパックの大半に及ぶもの。v2 は
  +10.4MB（いずれもクリーンなファイルページで回収可能）
- v2 の常駐ヒープ増は合成バッファ 134,400 B（105×320×4、
  @320）＋マスコット構造体のみ。静止ポーズではダメージ 0
  （転送 0）を維持し、アニメーション中のみ 33ms 刻みになる
- ダメージ帯の平均面積 @320 は 14,742 px（行バンド方式
  16,513 px から削減。全面 26.7K px、v1 の旧＋新矩形
  ~53K px と比較）

### 合格条件への適合

1. **GPU・専用ランタイム不要**: 実行時は mmap した .bdm の
   スパースランを合成バッファへ memcpy 級に適用し、既存の
   ブレンドで貼るだけ。Live2D/Cubism はホスト変換時のみ ✓
2. **違和感がない**: 30fps 焼き込み（速い動きは原 fps 維持、
   ドロップは遅い動きのみ）、クロスフェード不採用（ゴースト
   実証済み）、誤差 ≤8/チャンネルを全フレーム検証、拡大撮影
   で輪郭を確認 ✓
3. **実機予算内**: 転送 25KB/step @320、常駐増 ~0.6MB 級、
   ページキャッシュは回収可能なクリーンページ。ただし
   **ARM 実機での CPU 実測は未実施**（ホスト実測＋推定のみ）
   △

### 正直な限界

- 表示サイズは 320px が上限級（画面高 480 の 2/3）。これ以上
  はデスクトップの実用領域を覆う。焼き込み自体はより大きい
  サイズも可能だが、転送・容量が比例して増える
- 色深度は最終的に fb の RGB565（16bpp）で量子化される。
  暗部の滑らかな階調はここで段になる
- 実効 fps: 原典 30fps のうち、ドロップパスで遅い動きは
  実効 12〜20fps 級まで落ちる設計（588→492 ポーズ）。
  速い動き（タップ反応等）は 30fps を保つ
- パック容量は 2 サイズで 13.9MB。キャラやクリップが増え
  れば比例して増える（SD 前提では許容範囲、eMMC には置か
  ない）
- ひよりのモーションに移動（Move）クリップが無いため、
  このパックのひよりは歩かない（待機・反応のみ）。歩行には
  移動モーションを持つモデルが要る
- 公式ミク Live2D のランタイム形式は入手不可（Editor
  ソースのみ）。ミクの高精細版はユーザー供給モデルが前提
- ARM 実機/QEMU での実測は未実施。CPU の実機換算は推定

## コピー/オーバーヘッド削減

- 実行時デコード・スケール・色変換は全てゼロ（変換時に完了）。
  ランタイムは mmap 上のメタを読み、ポーズのアンカー/速度は
  サイズ別に事前スケール済み
- 描画はダメージ矩形のみ＋完全透明/不透明ピクセルの早期分岐
- 物理は 40ms 固定量子で割り算なし（q8 固定小数点）

## キャッシュ/メモリ管理

- パックは mmap（ページキャッシュ共有、プロセス専有 RSS に
  乗らない）。予算外のヒープ確保はマスコット構造体 1 個のみ
- キャッシュ類は新設していない（アトラスはファイルそのものが
  キャッシュとして働き、上限はパックサイズで決まる）

## 実機の現実への対応

- パックは SD 上の通常ファイル。状態を持たない（位置・行動は
  セッションごとに再生成）ため、突然のリセットで壊れる永続
  状態がない。設定は brainreg（既存の原子的書換え経路）
- オフライン前提（変換はホスト側作業、端末側は完成パックを
  読むだけ）。日数ベースの有効期限なし

## 残件

- 設定アプリ（apps/settings、担当外）に [mascot] の ON/OFF と
  サイズの行を追加する配線（キーは enabled/size で確定済み、
  セッションは次回起動から反映。320px 段は size=320 を書けば
  v2 パックでそのまま効く）
- 実機/QEMU ゲストでの実測（特に v2 @320 の CPU 率・転送量の
  ARM 実測）と SD イメージへのパック同梱は統合フェーズ
- 吹き出し（dialogues.conf）の対応可否は未検討
