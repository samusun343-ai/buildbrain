## 3. .bdm 形式改良の実測比較

測定系: 本番プリミティブ（tol_mask / sparse_payload /
damage_bands / decide_kept）をそのまま使う実験スクリプトで、
Hiyori（Live2D 焼き込み）Stand クリップ @320・tol 8・
キーフレーム間隔45 を基準に各候補を実測した。数値はホスト
実測。基準（v2）: kept 47 ポーズ、sparse 238,780 B、帯 4,320 B、
FULL 258,560 B、合計 501,660 B、ダメージ 11,129 px/ポーズ。

| 候補 | 結果（対 v2 基準） | 判定 |
|---|---|---|
| (a) パラメーター表現（ピクセル合成） | WinCE 側の実測でブロック動き補償が容量 1/46 だが PSNR 20〜22dB で不採用確定済み。自側でも整数平行移動補償（mc-global）を実測: **節約 0 px、sparse は +90 B と微増**（呼吸・揺れは平行移動でなく変形のため、マスクが既に吸収） | **不採用**（ピクセル合成には使わない。タイミング/補間ヒントへの限定利用のみ v3 のドロップパスとして既存） |
| (b) パレット量子化 RGBA4444 | sparse 値 4→2 B で約 67,612 B 節約（sparse の 28%）だが、**追加誤差の実測最大 15** — tol=8 の誤差保証を単独で破る | **不採用** |
| (b') RGB565＋A8（3 B/値） | 節約 約 33,806 B（sparse の 14%）、追加誤差の実測最大 **4**（正しい最近傍量子化で測定。誤った丸め式では 11 と過大評価になることも確認） | 保留（保証が tol+4 に緩む。tol を上げる方が同じ保証緩和で効果が大きいため単独採用は見送り） |
| (c) フレーム間デルタ強化（動き補償） | mc-global で節約 0（上記）。帯単位補償は未完走（CPU 競合で打ち切り — 未検証と明記） | 不採用（global の実測が根拠。band は未検証） |
| (c'') 帯単位動き補償 mc-band（完走、Mythra Stand @320） | 帯ごとに ±6px の整数シフトを全探索した**上限**でも、一致して保存を省けるのは変更画素の 19.6%（298,775 px 中 58,501 px、値バイト換算で最大 約234KB ＝ スパース節の 3.9%）。シフト記録・ラン再構成・帯の重なり処理の実損を引けばさらに下がる | **不採用**（上限でこの値では新規ランタイム機構に見合わない。動き補償系は global / band / ブロックの全てが実測で否定され、これで完走） |
| (c') リージョン列のフレーム間デルタ | v3 リージョン節として実装（§4）。実容量は共通パック実測で報告 | **採用**（共通化のため） |

| (e) RGB565 スパース（CE プロファイル、§4/§5b） | ミク HD @320: フル形式 20,511,530 B → 完全一致スパース 7,616,978 B → **tol 8 スパース 4,055,980 B**。CE 関連合計 4,124,658 B で BMAS v3 総量 5,446,335 B を下回る。Mythra では @248 3,417,470 B / @320 5,322,118 B（tol 8） | **採用**（共通パックの CE プロファイルはスパース形式＋tol 8 を既定とする。完全一致版は誤差ゼロが必要な場合の選択肢として残す） |
| (d) keyint 45→90 | FULL 258,560→129,280 B、sparse +11,680 B、**合計 −23%**（このクリップ） | **採用候補**（シーク時再同期コストは最大90ポーズの前方適用。既定変更はパック生成側パラメーターで可能） |

| ペイロード LZ（zlib / lzma） | sparse 238,780 → 163,471 B（0.68×）/ 135,024 B（0.57×）。inflate は 239 KB を 2 ms（ホスト） | **不採用**（mmap ゼロコピーとランダムアクセスが壊れ、展開バッファ分の RAM を常時食う。SD 容量より RAM 128MB とゼロコピー原則を優先） |

パラメーター表現の結論: 「変換時に計算して形式へ焼き込む」
原則のもとでも、ピクセル合成型パラメーターは (1) 変形主体の
モーションでは節約ゼロ（mc-global 実測）、(2) ブロック補償は
PSNR 20〜22dB で違和感バーを割る（WinCE 側実測）ため、共通
形式では採用しない。パラメーターはドロップ判定・補間可否と
いったタイミング情報への限定利用に留める（現行 v2 のドロップ
パスがその実装）。

## 4. 共通形式 v3（.bdm / .bmas 統合）

WinCE 側との協議（`~/workspace/mascot-shared/SHARED.md`）を
経て、単一仕様 **.bdm version 3** を実装した。仕様の正本は
FORMAT.md §5b。

- コアは v2 のまま（tol マスク＋スパースラン、帯ダメージ、
  ドロップ、verify 誤差保証）。サイズレコード 48 B に拡張し、
  regions_off/len と rgb565_off/len を追加。flags bit2/bit3。
- リージョン節: 合成済みフレームの α シルエットを縦マージ
  矩形列へ分解し、クリップ単位で全リスト→デルタ符号化。
  ダメージ帯と同じマスク計算から一元導出（計算は1回）。
  WinCE の「フレームごとリージョン事前計算・実行時再構築
  300〜700ms の排除」という要求にそのまま応える。
- RGB565 プロファイル節（任意）: ポーズごとのフルフレームを
  straight RGB565 で格納し、CE 側の「RGB565 原生・実行時
  デコード/スケールなし」要求に対応。**追記（2026-11-20）**:
  フル形式はミク HD で 20.5MB と BMAS v3 を上回ったため、
  WinCE 対案のスパース形式（flags bit4、§3 (e)）を併設し、
  共通パックの既定にした。仕様は FORMAT.md §5b。
  あわせて、リージョン被覆の失敗（WinCE 実測 145 ポーズ）
  の原因がデルタのリスト順序の未定義にあることを特定し、
  エンコーダ側で修正した（§10、形式変更なし）。
- Brainux ランタイム（shell/src/mascot.c）: v3 を受理して
  v2 経路で再生（拡張節は境界検証のみ）。リージョン列の独立
  復号 API `bd_mascot_regions_at()` を追加。
- 相互検証: `frames_to_bdm.py --verify` が v3 に対し
  (1) スパース復号 ≤ tol、(2) リージョンのシルエット完全
  被覆、(3) RGB565 と復号フレームの一致（量子化誤差 ≤9)、
  および両ストリームの完全消費を検査する。
- テスト: test_mascot **89 checks / 0 failures**（従来58＋
  v3 新規20＋幅/二重ブレンド回帰11、§9）。シェル全体の
  `make check` も全スイート PASS（test_desktop 182 /
  test_shell 71 / test_iconcache 35 / test_wm 90 /
  test_backend 25 / test_assist 24 / test_greeter_auth 13 /
  test_greeter_font 6 / test_wifi 40 / test_session 102 /
  test_mascot 89）。なお `make check` の実行リストに
  test_mascot が含まれていなかったため追加した。
- 後方互換: v1/v2 パックは従来どおり読める。v3 は v2 コアを
  内包するため、Brainux 専用パックは節なしで v2 と同容量に
  でき、移行は「焼き直し時に --format v3 を付けるだけ」。

### 共通テストパック実測（ミク HD、2026-11-20 追記）

WinCE 側がステージングした同一フレーム列（miku_sample_t04
の Live2D 焼き込み 206 フレーム、@320 のみ、204 ポーズ）を

| コア（atlas＋sparse） | 2,617,344＋4,964,984 B | 同一（不変） |

## 5. コピー/オーバーヘッド削減

- 変換時に全ての重い計算を終える原則を 3D 経路でも徹底:
  レンダリング、マテリアル再構築、リージョン事前計算、
  デルタ符号化は全てホスト側。端末の実行時処理は v2 から
  増えていない（v3 の拡張節は Brainux では読まない）。
- マスク計算の一元化: tol マスク1回の計算からスパースラン・
  ダメージ帯・リージョン列の3つを導出（従来は側ごとに別計算
  だったものを単一パスへ）。
- LZ 圧縮を「容量は減るがゼロコピーが壊れる」ため不採用に
  したのもこの原則による（§3）。

## 6. キャッシュ/メモリ管理

- パックは従来どおり mmap で、実行時デコード・展開バッファ
  なし（LZ 不採用の理由）。リージョン復号のスクラッチは
  必要時にだけ確保し、bd_mascot 内に1つだけ保持（ポーズ間
  で再利用、複製しない）。
- 3D 焼き込みの中間物（フレーム PNG 列）は SD ではなくホスト
  の作業領域に置き、パック化後はフレーム列が正本として残る
  （再パック可能）。

## 7. 実機の現実への対応

- オフライン前提: モデル入手・変換は全てホスト側で完結し、
  端末はパックを読むだけ。時刻・日数ベースの有効期限は
  形式のどこにも無い。
- 突然のリセット: パックは読み取り専用 mmap で、実行時状態
  （合成バッファ・リージョンスクラッチ）は揮発のみ。書き込み
  途中の破損が入り込む場所が無い。
- WinCE 併用: eMMC には触れない。共通形式は SD 上のパック
  ファイル1つの話で、WinCE 側は自側プロファイル節だけを
  読めばよい。

## 9. Mao 表示グリッチの修正（ランタイム再構成バグ、優先対応）

キャラ追加ラインの切り分け（REPORT-characters.md §4）を受けて
対応。症状: Mao パック（248/320 両サイズ）で斜めストリーク＋
断片の二重表示。パックは `--verify` 合格。**根本原因は2件とも
ランタイム（shell/src/mascot.c）側**で、パックの再変換は不要
だった（キャラ追加ラインの結論どおり）。

### 原因1: 合成キャンバス幅の解釈差（主因）

- コンバータのキャンバス幅は `round(crop_w × (size_h/crop_h))`
  （浮動小数）。C ランタイムは `crop_w_s = (crop_w × scale_q8
  + 128) / 256` という q8 近似で、両者はサイズによって 1px
  ずれる。スパースペイロードはキャンバス幅に対するフラット
  ストリームなので、幅が 1px ずれると全書き込みが1行ごとに
  1px ずれて蓄積し、斜めの剪断になる。FULL フレームは矩形
  配置で無事なため、本体は正しく細い斜め構造（杖・帽子の縁）
  だけが崩れて見えた。
- 実測（幅の不一致 = 帯被覆チェックの不良と完全一致）:
  Mao crop 829×1200 は @248 で 171 対 172、@320 で 221 対 220
  と両サイズ不一致。Wanko は @248 のみ不一致（@320 は一致し
  正常だった事実と符合）。Hiyori は両サイズ一致で正常。
  Mythra（3D 焼き込み）も @320 で不一致だった（204 対 203）。
- `--verify` が合格した理由: 参照デコーダは Python 幅で再構成
  するため自己整合していた。**形式仕様に幅の式が無かった**
  ことが本質で、FORMAT.md §4 に
  round-half-even(crop_w × size_h / crop_h) と固定し、
  SHARED.md にも共通形式の仕様明確化として反映した。
- 修正: mascot.c の crop_w_s を有理数の正確な round-half-even
  で計算するよう変更（scale_q8 は他で使われていない）。

### 原因2: 重なるダメージ帯での二重ブレンド

- A/B ハーネス（ダメージ駆動描画 vs 全面描画）で幅修正後も
  帯の内側に小さな値差が残り、1ピクセル追跡で確定:
  `bd_mascot_paint` がクリップ矩形ごとに blit するため、
  **互いに重なる帯の交差部で半透明ピクセルが2回ブレンド**
  されていた（実測: A の値 = blend(comp, 旧表示値) と一致）。
  帯同士の重なりは設計上通常で、呼び出し側（セッションは
  キャンバスダメージ最大64件を渡す）の契約として paint 側
  が冪等でなければならない。
- 修正: クリップ描画を行ごとの x スパン和集合にマージして
  各ピクセル最大1回ブレンドする方式（blit_sprite_clipped）
  に変更。ブレンド式自体は blend_over() に共通化し不変。

### 検証

## 10. リージョン被覆バグの修正（v3 デルタのリスト順序、優先対応）

WinCE 側の共通テストパック実測で「verify の (2) リージョン
被覆が 145/204 ポーズで失敗」と報告された件。Brainux 側で
再現・特定・修正した。

### 再現と原因

- Mythra フレームから v3 を生成すると @248 で 155/168、
  @320 で 147/168 ポーズが被覆失敗（同現象）。
- 切り分けハーネスで、エンコーダの帳簿リストとデコーダ
  再構成をポーズごとに比較: **クリップ 0 のポーズ 2
  （2 回目のデルタ）で発散開始**。矩形数は同じ 251 なのに
  中身が違う。
- 根本原因: エンコーダが削除インデックスを「焼いたばかり
  の幾何順序（damage_bands の返却順）」に対して計算して
  いたが、デコーダ（Python verify と C の
  `bd_mascot_regions_at()` の両方）は「前リストの残存分
  （順序保持）＋追加分の末尾追加」で再構成する。インデッ
  クは位置依存なので、1 回デルタが入った時点で両者の
  リスト順がずれ、以降は誤った矩形が削除され続けた。
  WinCE 側の仮説（α 閾値/フレーム対応の定義差）ではなく、
  順序セマンティクスの未定義が本質 — §9 の幅の式と同じく
  「仕様に定義が無い解釈依存パラメーター」の同型バグ。

### 修正

- エンコーダの帳簿をデコーダ再構成そのものに変更
  （`prev := survivors + adds`）。**形式変更なし**、
  リージョン節のバイト数は不変（Mythra 128,060/185,816 B、
  ミク HD 68,678 B は修正前と同値）。
- 仕様化: FORMAT.md §5b に「デルタ適用後のリスト順序」
  の定義を明記（削除インデックスはこの順序に対する位置、
  リスト内の矩形は相異なることが前提）。
- 回帰テスト: test_mascot に test_v3_region_order を追加
  （3 矩形の全リスト→追加分を指す削除を含む 2 段デルタで
  デコーダ順序を固定）。test_mascot **95 checks / 0
  failures**、シェル `make check` 全スイート PASS。

### 検証（修正後、自分の実行）

- 実パック verify: Mythra（両サイズ）とミク HD 共通
  パックの両方で**被覆失敗 0**、ストリーム完全消費。
- C/Python 相互検証: 両パック・全ポーズで
  `bd_mascot_regions_at()` と Python デコーダが完全一致。
