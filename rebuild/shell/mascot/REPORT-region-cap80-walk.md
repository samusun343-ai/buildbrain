# .bdm 生成側の残件2件: (A) 矩形数上限 ~80 の確定、(B) Walk の速度・向き

前弾: REPORT-region-cap.md（上限 100 の両立）。本レポートは
区切りごとに追記する。

## 0. 申し送りの内容

### (A) 矩形数上限 ~80（CE 側 p60 実測が発端）
- p60（CE 側ゲスト実測）: 矩形数→リージョン適用 ms は超線形
  （80 矩形 ≈33ms、100 ≈51ms、113 ≈69ms）。上限 100 では
  適用フレーム単体が 51ms で 33ms のポーズ間隔を超過する。
  間隔に収めるには上限 ~80 級が必要だが、締まりとの
  トレードオフは生成側の判断事項として申し送られた。
- 生成側の合格条件は形式どおり **締まり平均 ≤ 1.15**。
  満たす場合のみ本採用とし、基準を緩めて採用しない。

### (B) Walk の速度・向き（SHARED.md 2026-11-20 の申し送り）
- .bdm の Walk は 1 クリップのみで vx_q8 が全ポーズ 0
  （CE 側がミク・ヒカリ両パックで実測）。CE 側は Move 型に
  既定速度を与えているが、左行区間でキャラの向きが反転
  しない。向き別クリップか vx 符号の焼き込みがデータ側で
  可能なら検討されたい、という依頼。

## 1. (B) 調査結果（先行実施分）

### 1.1 パック実物の実測（自作ダンパで全ポーズ走査）
- mythra_v3.bdm: Walk（Move 型）30 ポーズ、vx_q8 は両サイズ
  とも全ポーズ 0（CE 側実測と一致）。
- miku-hd-v3.bdm（現行共通テストパック）: **Move 型クリップ
  自体が存在しない**（Idle=Stay / Tap=Animate / Flick=Animate
  のみ）。CE 側の「両パック」は少なくともミクについては
  Walk の不在が正確な実態。
- 対照（Shimeji 由来パック、convert_shimeji.py 経路）:
  ピカチュウ 歩く vx_q8=−672（scale 336 → 元データ −2 px/tick）、
  走る −4、猛ダッシュ −8 px/tick 相当。Shimeji の actions XML
  の Velocity 属性がそのまま焼かれており、**形式とランタイム
  は実 vx を問題なく扱える**。vx が 0 なのはフレーム列経路
  （frames_to_bdm.py）のパックだけである。

### 1.2 フレーム列経路で vx が 0 になる理由
- frames_to_bdm.py はポーズを `struct.pack('<HHhhhh', fi, d,
  ax, ay, 0, 0)` とし、vx_q8 / vy_q8 を **0 で固定** している。
  マニフェスト（manifest.json）に速度の概念自体がない
  （anchor とクリップ種別のみ）。
- convert_shimeji.py は対照的に Pose ごとに Velocity を保持し
  `vx_q8 = round(vx × scale × 256)` で焼く。

### 1.3 変換元データに速度・向き情報があるか
- **ヒカリ（3D 手続きモーション、~/mascot-3d-work/scripts/
  bake_3d.py の pose_walk）**: 腿・脛・足・腕の回転と
  arm.location.z（上下動 0.011）のみで、アーマチュアの水平
  位置は全フレーム (0,0,0)（reset_pose で毎フレーム初期化、
  pose_walk は location.x/y を一切触らない）。**その場歩行**
  であり、対地速度パラメーターはスクリプト内のどこにも
  存在しない。実測の裏付け: Walk 30 フレームの α≥128
  シルエット重心 x は 163.7〜170.8（腕振りの揺れ）の範囲で、
  開始→終了のネットドリフトは +1.7 px のみ。
  向きについても、レンダリングは正面固定カメラで、Walk
  フレームは **正面像**（f0000.png を目視確認）。左右の
  側面歩行クリップは元データに存在しない。
- **ミク（Live2D miku_sample_t04）**: モーションは 8 本
  （miku_01〜08.motion3.json）全てループする待機系で、
  カーブ対象は角度・体角度・呼吸・目・口等のパラメーター
  26 種のみ。**移動（並進）を表すパラメーターは無く、
  歩行モーション自体が存在しない**（ステージ済みフレームの
  クリップ構成 Idle/Tap/Flick と一致）。

### 1.4 Brainux ランタイムのセマンティクス（shell/src/mascot.c、読み取りのみ）
- WALK/IDLE/REACT 状態で 40ms 量子ごとに
  `vx = look_right ? -pose.vx_q8 : pose.vx_q8` をアンカーへ
  加算する。つまり **データの vx は「画像の正向き（左向き）
  での速度」** と定義され、右向き時はランタイムが符号反転
  と画像の鏡像化（blit の sx 反転）を担う。Shimeji 由来
  パックの vx が全て負値（左向き移動）であることと整合。
- したがってデータ側に必要なのは「正向きでの vx 符号付き
  速度」だけであり、向き別クリップは形式上不要（ランタイム
  の鏡像が前提）。ただしこれは速度の実データが存在する
  場合の話で、本件の両パックにはその実データが無い。
- CE 側ランタイム（p56work/src/mascot.c、読み取りのみ）も
  同じ前提で実装されている: ロード時にクリップの最初の
  非ゼロ vx_q8 を px/tick へ変換してクリップの符号付き vx
  とし、Move 型で vx=0 の場合にだけ既定値 +1 を与える。
  歩行中の方向は g_walkDir 状態で符号を反転する（画像の
  鏡像化は行わず、「片脚で向きが合わない」ことは p58 で
  CE 側の既知の割り切りとして記録済み）。つまり **実データ
  さえあれば、単一 Walk クリップへの符号付き vx 焼き込みが
  両ランタイムの既存セマンティクスと整合する** ことも確認
  できた。不足しているのはランタイムでも形式でもなく、
  変換元の速度データそのものである。

### 1.5 (B) 結論
- 両パックとも **変換元データに速度・向き情報は存在しない**
  （ヒカリ=その場歩行の手続きモーションで対地速度の定義
  自体が無い、ミク=歩行モーション自体が無い）。よって
  焼き込むべき実データは無く、vx_q8 = 0 は現データの忠実な
  表現である。推測で速度を捏造しない。
- 提案（未実施）: 将来ヒカリに歩行速度を持たせるなら、
  それは新規の創作データ（例: bake_3d.py に歩幅×ケイデンス
  から決める対地速度を著作者が定義する）であり、その場合
  は frames_to_bdm.py のマニフェストにクリップ単位の任意
  フィールド（例 `velocity: [vx, vy]`、元 px/tick）を追加し、
  Shimeji 経路と同じ整数スケーリングで vx_q8 へ焼く小さな
  拡張で足りる。形式（.bdm）の変更は不要。これは CE 側との
  共通仕様には触れない生成側マニフェストの拡張だが、
  実データが無い現時点では実装しない（検証する実データが
  無いため）。

## 3. (A) 試し焼き実測（cap 80、ヒカリ）

同一フレーム・同一パラメーター（--format v3 --rgb565-sparse
--rgb565-tol 8 --sizes 248,320）で上限だけを変えて試し焼きし、
verify（--region-max-rects 80）で実測した:

| サイズ | 矩形数 mean/max | 締まり mean/max | 判定（平均 ≤1.15） |
|---|---|---|---|
| @248 | 80.0 / 80 | **1.142** / 1.156 | 平均は基準内 |
| @320 | 80.0 / 80 | **1.156** / 1.173 | **平均が基準超過** |

- 被覆失敗 0、コア偏差 ≤ tol 8、565 失敗 0、両ストリーム
  完全消費（verify の他項目は全て合格。verify 全体の exit は
  @320 の締まり超過により不合格）。
- 矩形数 mean が両サイズとも 80.0 ちょうどなのは、全 168
  ポーズが上限適用を受けたため（基本タイリングの最小ポーズ
  でも 80 を超える）。
- **中間結論: cap 80 は CE が使う @320 で形式の合格条件
  （締まり平均 ≤1.15）を満たさない。** 曲線を完成させるため
  cap 85 も実測する（§4 で最終結論）。
- 副次観測: 試し焼き（cap 80）と現行パック（cap 100）の
  節単位照合では、コアのピクセル節（frames/patches/sparse/
  poses/atlas）は両サイズともバイト同一だったが、**rgb565
  節が +25,160 B（@248）/+31,888 B（@320）と増えた**。
  切り分けは §3.1。

### 3.1 副次観測: 現行コンバータの 565 量子化セマンティクス変化

- 現行パック（ミク・ヒカリとも）を現行コンバータで verify
  すると、リージョン系の全項目（被覆 0・締まり・矩形数・
  ストリーム完全消費）とコア偏差は合格するが、**rgb565
  スパース項目だけが全ポーズ不合格（最悪偏差 17 > tol 8）**
  になる。一方、現行コンバータで新規に焼いたパックは
  同項目を合格する（最悪偏差 8）。
- 原因の同定（対照焼きで実証）: 現行コンバータで cap 100
  の対照焼きを行うと、現行パックと **リージョン節を含む
  全節がバイト同一** になり、rgb565 節だけが両サイズとも
  +25,160/+31,888 B で異なる（cap 80 の試し焼きでも 565 節
  は対照焼きとバイト同一 = 565 は上限に依存しない）。
  現行コンバータの to565() は量子化を「最も近いレベルへ
  丸め（(c×maxlevel+127)//255）」に変えているが、FORMAT.md
  §5b の仕様は「切り捨て」。出荷済みパックは切り捨て時代
  の焼き込みであり、丸めで再計算する現行 verify と全ポーズ
  で最大 17 の偏差になる。並行する p61（画質改善）ライン
  の変更とみられる。
- 本タスクへの影響: **なし**。(A) の判定はリージョン系の
  実測（被覆・締まり・矩形数）のみに基づき、それらは
  565 量子化に依存しない。(A) が不採用結論の場合、再生成
  自体が発生しないため、この変化は本タスクでは扱わない。
  p61 ライン側で仕様（FORMAT.md）と実装のどちらへ寄せるか
  の判断が要る事項として記録に留める。

### 3.2 ミクの cap 80 実測（現行パックの verify）

- miku-hd-v3.bdm を --region-max-rects 80 で verify:
  矩形数 mean 75.5 / **max 80 ≤ 80**、締まり 1.057/1.060、
  被覆失敗 0。**全ポーズが上限 80 以下であることを実測で
  確認**した。ミクは cap 80 でも無変更で適合する
  （565 項目の不合格は §3.1 の別件）。

## 4. (A) 最終結論: cap 80 は不採用、上限 100 を維持する

cap 85 の試し焼き＋verify 実測（同一条件）:

| サイズ | 矩形数 mean/max | 締まり mean/max | 判定 |
|---|---|---|---|
| @248 | 85.0 / 85 | 1.137 / 1.150 | 平均は基準内 |
| @320 | 85.0 / 85 | **1.151** / 1.168 | **平均が基準超過** |

ヒカリ @320 のトレードオフ曲線（締まり平均。前弾 §7 の
90/100/110/∞ と本弾の 80/85 を統合）:

| 上限 | 90 | **100（現行）** | 110 | ∞ |
|---|---|---|---|---|
| 締まり平均 @320 | 1.146 | 1.139 | 1.135 | 1.134 |

| 上限 | 80 | 85 |
|---|---|---|
| 締まり平均 @320 | 1.156 ✗ | 1.151 ✗ |

- 境界は 85 と 90 の間にある。@248 は cap 80 でも平均
  1.142 で基準内だが、**CE が実際に使う @320 では cap 80
  （1.156）も cap 85（1.151）も形式の合格条件「締まり平均
  ≤ 1.15」を満たさない**。
- よって **cap 80 は採用しない。既定の上限 100 を維持し、
  パックの再生成は行わない**（現行パックは p60 で CE 側
  検証済みのものがそのまま残る。CE 側の差し替えも不要）。
  基準を緩めての採用はしない、という本タスクの規律どおり
  の結論である。
- 付記: 基準を満たす最も厳しい上限は @320 で cap 90
  （平均 1.146）だが、CE 側実測の曲線（80≈33ms / 100≈51ms /
  113≈69ms）では 33ms 間隔に届くのは ~80 級であり、90 では
  間隔適合は得られない。矩形数削減だけでは「締まり基準内
  かつ 33ms 間隔内」は両立しない、というのが実測の結論。
  間隔超過の残りは CE 側の適用側（間引き規則・適用頻度）
  で吸収する領域になる。
- 本タスクではコンバータ・形式・パックのいずれも変更して
  いないため、再生成パック向けの検証一式（復号一致・A/B
  ハーネス・test_mascot）は適用対象外。現行パックについて
  は本タスクの verify でリージョン系全項目の合格を再確認
  済み（§3.1 の 565 項目の件は p61 ラインのコンバータ変更
  に起因する別件で、本タスクの判定には無関係）。
