# REPORT — GUI ライブラリ機能比較（libbrainui2 vs SDL / GTK / Qt / LVGL / FLTK 他）

- 日付: 2026-11-21
- 目的: 自作 GUI ライブラリ libbrainui2 と既存 GUI ライブラリ群を、実機条件の下で正面から比較し、「採用 / 部分利用 / 不採用」の判定と根拠を残す。これまで実施していたのは Android Material 3 / WinUI との見た目・振る舞いの同等化監査と、OS 側ライブラリのサイズ・互換判定であり、本レポートが初の正面比較である。
- コードへの変更は行っていない（比較と実測のみ）。実測用のサンプルとツールチェーンは作業用スクラッチ（`~/workspace/buildbrain-work/guicmp-scratch/`、測定後に削除）に置き、対象 rootfs へ一時追加したファイルは測定後に全て除去した。

## 1. 比較の前提（実機条件）

| 項目 | 値 |
|---|---|
| CPU | i.MX28 / ARM926EJ-S（ARMv5TE）、シングルコア、GPU 無し |
| RAM | 128MB（OS・全アプリ共有） |
| 表示 | フレームバッファ RGB565、854×480、ソフトウェア描画のみ |
| 入力 | 抵抗膜タッチ（1本指）＋物理キーボード（48キー） |
| 表示基盤 | X / Wayland を前提にしない（fbdev + evdev が実経路） |
| ネットワーク | オフライン既定 |
| 当方の追加要求 | (i) Android / WinUI の2モード同等化（トークン・部品・振る舞い） (ii) 実機寸法への適合（179ppi・タッチフロア等） (iii) 既存アプリがそのまま動くこと (iv) 日本語入力（libbrainime + OSK）との統合 |

## 2. 方法

1. **Web 調査**: 各候補の公式ドキュメント・公式リポジトリ・Debian パッケージ情報を一次情報として取得し、出典 URL と取得日（すべて 2026-11-21）を §9 に残す。記憶だけで書かない。
2. **実測**: armel 向けに最小サンプルをビルドし、qemu-arm-static（ユーザーモード、対象 rootfs = image-work/rootfs を sysroot とする）で実行して、バイナリ/ライブラリサイズとピーク RSS を測った。クロスコンパイラは Debian trixie の gcc-14-arm-linux-gnueabi を .deb 展開して使用（`-mcpu=arm926ej-s -O2`）。実測できなかった項目は「未実測」と明記し、理由を付ける。
3. **サイズの物差し**: (a) ライブラリ .so の実ファイルサイズ、(b) `readelf` の NEEDED を辿った依存閉包の実ファイル合計（対象 rootfs 内で解決）、(c) Debian trixie armel の Installed-Size（パッケージ索引から取得）。
4. **RSS の測り方と限界**: qemu プロセスの ru_maxrss を測り、何もしないサンプル（sleep のみ）の値 11.2 MiB をベースラインとして差分も示す。qemu ユーザーモードの RSS には TCG 変換キャッシュ等のエミュレーション上乗せが含まれ、実機の常駐量と同一視はできない。ただし同一条件で測った候補間の相対比較、および桁の判断には使える。ファイル backed なコード/フォントのページは実機では共有・追い出し可能であり、その点でも実機の私用コストは測定値より小さくなる。逆に、実機でしか分からないコスト（X サーバ自体の常駐など）は測定外であり、該当箇所に明記する。

## 4. 候補ごとの調査

### 4.1 SDL2（+ SDL_ttf / SDL_image 等）

- **正体**: 公式導入文書の定義どおり「オーディオ、キーボード、マウス、ジョイスティック、グラフィックスハードウェアへの低レベルアクセス」を提供するメディア/プラットフォーム層であり、**ウィジェットツールキットではない**（ボタン・メニュー・テキスト編集等の部品は存在しない）。2D レンダラ API（ソフトウェアフォールバックあり）とイベントキューが中核。
- **動く形**: Debian trixie armel に 2.32.4 が実在し、対象 rootfs にも収載済み（現行イメージで使用中）。ただし rootfs 収載ビルドのビデオドライバは **kmsdrm / x11 / wayland / offscreen / dummy のみで、fbcon（fbdev 直接）は無い**（.so の strings で確認。SDL2 では fbcon は削除済み）。実機で使うなら、カーネル側に DRM tiny ドライバ（brain.c）があるため kmsdrm 経由が経路になる。rootfs には SDL 1.2 もあるが（fbcon を持つ）、上流終了済みの旧世代であり候補にしない。
- **描画**: 全面サーフェスモデルが基本。ウィンドウサーフェスについては `SDL_UpdateWindowSurfaceRects` で矩形単位の部分更新が可能だが、部品レベルのダメージ管理はアプリ側の仕事になる。
- **テキスト**: 本体にテキスト描画は無い。**SDL_ttf が FreeType + HarfBuzz のラッパ**であり（公式 README）、合字・カーニング・方向を含む本格整形をサーフェス描画として提供する。SDL_ttf の .so 実体は 66,824 B と小さい（依存する FreeType/HarfBuzz は別途必要）。
- **IME**: SDL は TEXTINPUT / TEXTEDITING イベントでプラットフォーム IME と接続する設計だが、fbdev/kmsdrm 環境には接続先のプラットフォーム IME が存在しないため、日本語変換はどのみち自前（libbrainime）になる。現状の COMPOSITION 受け口と役割は同じ。
- **サイズ/メモリ**: libSDL2-2.0.so.0 実体 1,681 KiB。対象 rootfs での依存閉包は **32 ライブラリ・10.8 MiB**（Debian のフル機能ビルドで、X11/Wayland/ALSA/PulseAudio/systemd 等の経路を含む。用途を絞った自前ビルドなら大幅に削れる）。RSS 実測は §5（Δ+10.7 MiB、dummy ドライバ＋SDL_ttf で日本語テキスト描画）。
- **ライセンス**: zlib（SDL_ttf も zlib。本体が使う FreeType は FTL、HarfBuzz は MIT）。
- **当方要求への適合**: 2モード部品・実機寸法・日本語入力のいずれも SDL 単体では満たさない（部品が無いため）。プラットフォーム層（入力/描画の受け口）としては実績があるが、当方は fbdev/evdev バックエンドを既に持ち、置き換える利得は薄い。

### 4.2 GTK 3

- **動く形**: Debian trixie armel に 3.24.49 が実在し、対象 rootfs にも収載済み（現行 Brainux のアプリが使用）。ただし GDK バックエンドは公式文書どおり **x11 / wayland / broadway / quartz / win32 のみで、フレームバッファバックエンドは存在しない**。つまり当方の前提（X/Wayland を前提にしない）では表示できず、動かすには X サーバか Wayland コンポジタが別途必要（現行 Brainux は X 経由で動かしているのが現状）。
- **部品・機能**: デスクトップ級の全域を持つ。モデル/ビュー分離の TreeView、TextView/TextBuffer、CSS テーマ、IM モジュール（IBus/Fcitx 接続）、印刷、DnD、アクセシビリティ（ATK）、gettext の i18n 基盤まで標準装備。44部品マトリクスの範囲はほぼ全て覆い、さらに上回る。
- **テキスト**: Pango + HarfBuzz。合字・禁則（UAX #14）・bidi（FriBidi）・フォントフォールバックまで含む、候補中最強の整形系。
- **サイズ/メモリ**: libgtk-3.so.0 実体 7,495 KiB。対象 rootfs での依存閉包は **64 ライブラリ・27.3 MiB**。RSS 実測は §5: ホスト Xvfb への X11 接続で最小ウィンドウ（ラベル/入力/ボタン/チェック/スライダ/リスト）を表示し、ピーク **129〜130 MiB**（rootfs の全フォント使用時）、フォントを同梱サブセットだけに絞った条件でも **110.9 MiB**。qemu の上乗せを差し引いても、128MB の実機で OS と同居する規模ではない。フォント条件で約 19 MiB 動くことも分かった（フォント mmap の寄与）。
- **ライセンス**: LGPL-2.1 以降。
- **当方要求への適合**: 部品・整形・IME 接続は最強だが、前提（表示基盤）とメモリで不適合。2モード同等化は CSS とカスタム描画の作り込みになり、GTK の標準見た目を使う利点と両立しない。

### 4.3 GTK 4

- **動く形**: Debian trixie armel に 4.18.6 が実在（libgtk-4-1 Installed-Size 10,297 KiB）。しかし GSK のレンダラは GL（ngl、GL 3.3 級を要求）/ Vulkan が本線で、cairo レンダラは公式に「最終フォールバック」の位置づけ。旧 GL レンダラは 4.18 で削除された。GDK バックエンドも x11 / wayland / broadway 系で、フレームバッファバックエンドは無い。GPU 無し・fbdev 前提の当方では二重に前提外。
- **部品・機能**: GTK 3 と同等の広さ（TreeView は ListView/GridView のモデルベースへ置換）。テキストは GTK 3 と同じ Pango 系。
- **サイズ**: 依存閉包（rtlibs + rootfs で解決）**66 ライブラリ・31.8 MiB**。RSS は未実測（rootfs に GTK 4 の実行一式が無く、前提外のため優先度を下げた）。
- **ライセンス**: LGPL-2.1 以降。
- **判定材料**: 設計の中心が GPU デスクトップであり、当方の実機条件と最も遠い。

### 4.4 Qt 5（Widgets / Quick）

- **動く形**: **候補中で唯一、fbdev に直接出せる本格デスクトップツールキット**。公式「Qt for Embedded Linux」文書に LinuxFB プラグイン（フレームバッファへ直接描画、ソフトウェア描画のみ）があり、fbdev の代替として DRM dumb buffer モード（`QT_QPA_FB_DRM`、ページ
...[truncated 17179 chars]フリッピングで vsync 対応）もある。Qt Quick は linuxfb ではソフトウェアシーングラフバックエンド（`QT_QUICK_BACKEND=software`）が必須。
- **部品・機能**: デスクトップ級の全域（Widgets）。テキストは Qt 独自のテキストスタックで、フォントフォールバック・禁則・双方向を含むデスクトップ級の処理を持つ。IME はプラットフォーム入力コンテキスト経由で、自前エンジンとの統合は作り込みになる。
- **サイズ**: Widgets/Gui/Core の .so 合計だけでも約 17 MiB 級。依存閉包（rtlibs + rootfs で解決）は **23 ライブラリ・61.8 MiB** で、うち **ICU データ（libicudata.so.76）が 30.4 MiB** を占める（Debian ビルドはシステム ICU にリンクする。小規模 ICU での自前ビルドという軽減策はあるが、それ自体が再構築プロジェクトになる）。
- **メモリ**: RSS は**未実測**。理由: 実機経路の linuxfb は /dev/fb0 を必要とし、qemu ユーザーモードでは再現できない。xcb 経由の代替測定は別プラグインの測定になり、数値の意味が変わるため行わなかった。
- **ライセンス**: LGPL-3.0 / GPL-3.0（オープンソース版）。GTK の LGPL-2.1 よりコピーレフトが強い。
- **当方要求への適合**: 2モード同等化は QStyle/スタイルシートの全面作り込みになり、Qt の標準見た目を使う利点が消える。既存アプリ（libbrainui2 前提の自作アプリ群）との互換はゼロ。C++ と moc 等のツールチェーンも新規に抱える。

### 4.5 Qt 6

- **動く形**: Debian trixie armel に 6.8.2 のビルド自体は存在する（libqt6widgets6 / libqt6gui6 / libqt6core6t64 を索引で確認）。しかし Qt 公式のサポートプラットフォーム（Qt 6.12 の公式ページ）では Linux は x86_64 / arm64 のみ、組み込みの参照ターゲットも Cortex-A 級のみで、**ARMv5 / armel は公式サポート構成に存在しない**（「一覧に無い構成は公式サポート外」と明記されている）。Debian の独自ポートに乗る形になる。
- **サイズ**: 依存閉包 **37 ライブラリ・68.1 MiB**（ICU データ 30.4 MiB を含む）。Qt 5 より重い。
- **その他**: C++17 必須。Qt Quick は QML/JS エンジン込みでさらに重量級。RSS 未実測（理由は Qt 5 と同じ）。
- **判定材料**: Qt 5 の問題（重量・ライセンス・互換ゼロ）に、公式サポート外というリスクが加わる。

### 4.6 LVGL

- **動く形**: 組み込み向けに設計された C ライブラリで、実機条件への適合は候補中最高。ソース配布が正規形態（Debian パッケージは無い）。ツリー内に **Linux フレームバッファ表示ドライバ（src/drivers/display/fb）と DRM ドライバ、evdev 入力ドライバ（src/drivers/evdev）を同梱**することを v9.2.2 のソースで確認した。X/Wayland 不要。
- **要件**: 公式ドキュメントでは最小構成 約32KB RAM / 約128KB Flash 級、表示バッファは画面の 1/10 程度から。保持モードのオブジェクトツリー、Flex/Grid レイアウト、状態・パート別のスタイルプロパティ、テーマ、アニメーション、ダメージ（無効領域）ベースの部分描画を持つ。libbrainui2 と設計思想が最も近い。
- **部品**: src/widgets に 32 種のウィジェット（ボタン、ラベル、スライダ、チェックボックス、ドロップダウン、テキストエリア、キーボード、リスト、メニュー、タブビュー、カレンダー、チャート等。ソースツリーで数えた）。
- **テキスト**: **ビットマップフォントが基本**（サイズ別に事前変換する lv_font_conv 方式）。実行時 TTF は FreeType / TinyTTF 連携が別途ある。整形はグリフ単位で HarfBuzz 級の合字整形は無く、複合スクリプトの結合は公式ドキュメントでも「限定的」と明記。bidi は独自実装（LV_USE_BIDI）がある。CJK は左書きで素直に扱えるが、同梱 CJK フォントは約1,000字のみで、日本語の実用には自前変換フォントが各サイズ必要になる。
- **IME**: 公式の IME は **中国語 Pinyin 専用（lv_ime_pinyin）のみ**。日本語変換は libbrainime を LVGL のキーボード/テキストエリアに統合する作り込みが必要で、composition（未確定文字列）の表示モデルも自前になる。
- **テキスト編集**: テキストエリアは基本編集（カーソル、パスワードモード等）の範囲で、Undo/Redo や書記素単位の編集を持つ textcore 級の編集コアは無い。
- **サイズ/メモリ（実測）**: §5。全ウィジェット有効の標準構成で静的リンクしたサンプルが strip 後 **526,288 B**、RSS 増分は測定限界以下（Δ+0.1 MiB）。候補中で圧倒的に軽い。
- **ライセンス**: MIT。
- **当方要求への適合**: 軽さと fbdev 適合は満点だが、(i) 44部品×2モードの同等化作り込みは LVGL のテーマ機構の上でも自前になる、(ii) 日本語（フォント・整形・IME・編集コア）は自前部分が大きく、現行の libbrainime/textcore 資産が活きない、(iii) 既存アプリ互換ゼロ（全アプリ書き直し）。「軽い汎用基盤」としては最良だが、「当方の要求を満たす完成品」にはならない。

### 4.7 FLTK

- **動く形**: 1.4 の Linux 対応は **Wayland / X11 のハイブリッド**が公式形態（公式 README.Wayland.txt）。描画は Cairo、テキストは Pango（整形は良好）、CJK 入力はプラットフォームの入力メソッド経由。**フレームバッファバックエンドは無い**ため、当方の前提では X サーバか Wayland コンポジタが別途必要になる。
- **部品**: 数十種のウィジェットクラス（1.4 で Fl_Flex / Fl_Grid のレイアウトも追加）。Fl_Text_Editor（Undo 付き）もある。テーマはスキーム選択の範囲で、プラットフォーム別のトークン同等化の仕組みは無い。
- **サイズ/メモリ**: libfltk.so.1.4 実体 1,290 KiB と本体は小さいが、Debian ビルドの依存閉包は **52 ライブラリ・19.9 MiB**（X11 + Pango + cairo スタックを含む）。RSS 実測は §5（Xvfb 経由で Δ+28.6 MiB。実機では X サーバ自体の常駐が上乗せされ、それは測定外）。
- **ライセンス**: LGPL-2.0 + 静的リンク例外（FLTK ライセンス）。
- **当方要求への適合**: 前提（表示基盤）で不適合。本体の小ささは魅力だが、動かすための前提が当方の設計と相容れない。

### 4.8 その他（簡潔に）

- **AWTK**（ZLG）: Linux フレームバッファビルド（`LINUX_FB=true`）を持ち、ダーティ矩形更新や入力法モジュールもある、実在の組み込み向け候補。LGPL-2.1。ただしドキュメントとエコシステムは中国語中心で、日本語整形・IME の実績情報が乏しく、検証コストが高い。実測は未実施（未実測）。2モード作り込みと既存互換の問題は LVGL と同じ。
- **MiniGUI**（FMSoft）: fbdev 前提の老舗で部品も多いが、現行版は **GPLv3 + 商用デュアルライセンス**。OS イメージ全体を配る当方の形態ではライセンスが重い。Win32 風 API の作法も当方の設計と無関係。実測は未実施（未実測）。
- **Nuklear / Dear ImGui 系**: 即時モード。プロジェクトの設計判断（DESIGN-toolkit-v2.md §1）で、ダメージ描画と IME composition のような持続状態との相性から保持モードを選び即時モードを採らないと決定済みであり、その判断は今回も変わらない。
- **GTK 2**: trixie armel に残存するが上流終了済み。対象外。
- **DirectFB**: Debian trixie にパッケージ自体が無く（削除済み）、上流も終了。対象外。

## 7. 判定

| 候補 | 判定 | 理由（要約） |
|---|---|---|
| SDL2 | **ツールキットとしては不採用**（部品が存在しない）。プラットフォーム層としての置換も見送り | fbdev/evdev バックエンドは既に自前で持ち、kmsdrm 化の利得より移行コストが大きい。ただし SDL_ttf が示す「HarfBuzz 整形の取り込み」は下記の部分利用として価値がある |
| GTK 3 | **不採用** | fb バックエンドが無く前提と相容れない。実測 RSS がフォントを絞っても 110 MiB 級で 128MB 環境に同居できない。現行 Brainux が X + GTK で動いているのは「作り直し対象の現状」であって、採用理由にはならない |
| GTK 4 | **不採用** | GL/Vulkan 中心の設計で GPU 無し環境と最も遠い。fb バックエンドも無い |
| Qt 5 Widgets | **不採用** | linuxfb で前提は満たす唯一の本格ツールキットだが、閉包 61.8 MiB（ICU 30.4 MiB）、LGPL-3、2モード作り込みで標準見た目の利点が消え、既存アプリ互換ゼロ。費用対効果が合わない |
| Qt 6 | **不採用** | Qt 5 の問題に加え、ARMv5 が公式サポート外（Debian 独自ポート頼み）、閉包 68.1 MiB |
| LVGL | **全面採用は不採用。ただし「軽量さの物差し（ベンチマーク）」として正式に採用** | 実機適合と軽さは実測で最良（静的 514 KiB、RSS 増分ほぼゼロ）。しかし日本語（ビットマップフォント前提・合字整形なし・IME は Pinyin のみ・編集コアが弱い）と 44部品×2モードの作り込み、既存アプリ互換ゼロを考えると、乗り換えても自前部分が減らない。設計が近いため部品単位のコード移植利得も小さい。今後の libbrainui2 のメモリ/描画最適化（特に部分バッファ方式とスクロール blit）は LVGL を参照値にする |
| FLTK | **不採用** | X/Wayland 必須で前提外。本体の小ささ（1.3 MiB）は、動かすための表示基盤の重さで相殺される |
| AWTK | **不採用** | fbdev 適合はあるが、日本語まわりの検証情報が乏しく検証コストが高い。LVGL に対して優位な材料が無い |
| MiniGUI | **不採用** | GPLv3 デュアルライセンスが配布形態と合わない |
| Nuklear 等（即時モード） | **不採用** | 保持モードの設計判断（DESIGN-toolkit-v2.md §1）を維持する |

### 部分利用（サブシステム単位の取り込み）— ここが本比較の実利

libbrainui2 の自己申告された最大の弱点は「テキスト整形がグリフ単位で、合字・bidi・UAX #14 が無い」ことであり、これはツールキットを乗り換えなくても部品単位で直せる。優先順に:

1. **HarfBuzz（整形）+ FreeType（ラスタライズ/計測）の取り込み — 採用推奨**。どちらも対象 rootfs に既に存在する実績ある実装で、libharfbuzz.so.0 = 1,346 KiB、libfreetype.so.6 = 705 KiB。HarfBuzz で合字・カーニング・グリフ配置を正しくし、ラスタライズは stb_truetype のまま（グリフ ID 指定で描ける）でも、FreeType に寄せてもよい。textcore と描画層の計測・配置段に差し込む形で、部品・テーマ・既存アプリには影響しない。SDL_ttf はこの組み合わせのラッパだが、SDL 本体を抱える分だけ重いので、直接利用を推奨する。
2. **FriBidi（bidi、UAX #9）— 条件付き採用**。libfribidi.so.0 = 109 KiB と小さく、HarfBuzz と対で入れるのが定石。日本語 UI では bidi の必要度は低いが、混植（英数字・記号列）や将来の多言語で効く。HarfBuzz 取り込みと同時に入れるかは実装時の判断でよい。
3. **Pango（レイアウト一式）— 見送り（HarfBuzz で不足した場合の次善策）**。行分割（UAX #14・禁則）まで含む完成品だが、libpango 450 KiB の裏で glib（1,282 KiB）と fontconfig を引き連れ、フォント選択の主導権も Pango 側に移る。当方の禁則実装が既にある現状では、HarfBuzz 単体より費用対効果が劣る。
4. **画像デコードの差し替え — 見送り**。SDL_image / GdkPixbuf は対応形式の広さが利点だが、当方の stb_image + JPEG スケールデコードで実用範囲を覆っており、利得が小さい。
5. **cairo の取り込み — 見送り**。ベクター描画の品質は上がるが、当方のキャンバスは RGB565 とダメージ転送に最適化されており、cairo（1,220 KiB、32bpp 前提）に寄せると実機向け最適化と衝突する。
6. **LVGL の方式参照 — 採用（コードではなく設計の部分利用）**。部分バッファ描画（画面の 1/10 単位）とフォント圧縮形式は、libbrainui2 の全面キャンバス方式・スクロール最適化の改善時に参照する。MIT ライセンスなので必要ならコード参照も妨げられない。

## 8. 本比較の観点メモ（コピー/オーバーヘッド、メモリ管理、実機の現実）

- 比較はすべて「128MB 共有・単一コア・ソフトウェア描画・オフライン」の実条件で行い、デスクトップ前提の公開値（GPU 前提の描画性能など）は判定材料から外した。
- メモリは「ライブラリ単体」ではなく依存閉包と RSS 増分の両方で見た。単体が小さく見える候補（FLTK、SDL）も、動かすための前提（X サーバ、プラットフォームスタック）まで含めると順位が変わることが実測で確認できた。
- 本レポート自体はコード変更を伴わない。§7 の部分利用（HarfBuzz 等）を実施するかどうかは統合フェーズの判断事項であり、実施する場合は「コピー/オーバーヘッド削減」「キャッシュ/メモリ管理」「実機の現実への対応」を各実装レポートに含めること。
