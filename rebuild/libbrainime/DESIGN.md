Brainux 用日本語変換エンジン。既存資産は BIDF v2 辞書データのみで
変換エンジンが存在しなかったため、本ライブラリを新規作成した。
設計の正本は `~/workspace/research_notes/brainux-ime-design-20261119/report.md`
(lattice + Viterbi、インプロセス利用 + 薄い fcitx5 アドオン)。

## 構成

```
include/brainime.h   公開 API (C)
src/dict.c           BIDF v2 ローダ (LOUDS trie + bitvec rank/select)
src/conn.c           接続コストモデル (辞書 conn 部が全ゼロのため自前)
src/engine.c         lattice 構築 + Viterbi + 結果/セッション
tools/bi.c           CLI (convert / lookup / forced / bench)
tests/               回帰コーパス・辞書等価性・セッション API テスト
```

## 辞書ロード (dict.c)

- BIDF v2 (1,944,229 B、180,000 エントリ / 116,292 読み / 151,878 表記)
  を `mmap(MAP_SHARED)` で開く。常駐メモリを増やさないことが要件:
  ページは共有され、カーネルが回収可能。
- LOUDS 読み trie / 表記 trie は bitvec の rank/select で辿る
  (rank は 512 bit 毎、select は 256 毎にサンプル索引)。
- トークン列 (読みグループ毎の 表記id・品詞・コスト) はロード時に
  一度だけ RAM 上の索引へ展開する (約 180k × 6 B ≒ 1.1 MB)。
  これが mmap 以外で唯一の大きな常駐分。
- 表記文字列は必要時に表記 trie を葉→根へ辿って実体化する
  (全表記を RAM に展開しない)。
- 辞書引きの正しさは元の `bidict_lookup2` と 15 読みで完全一致を
  回帰テストで確認している (tests/check_lookup.py)。

## 変換 (engine.c)

1. 入力正規化: カタカナ→ひらがな。UTF-8 コードポイント列に分解。
2. Lattice 構築: 各開始位置で読み trie を前方歩行し、一致する
   読みグループの単語ノードを置く (lattice 用は 1 グループ最大
   16 トークン; 候補列挙時は最大 32 まで再読込)。
3. 未登録語ノード: ひらがな/カタカナ連続 (基本 + 45/字、最大 6 字)、
   ASCII 連続 (英字・記号は品詞 81)、数字列 (品詞 8。漢数字の
   位取り表記バリアントと全角数字バリアントを併置)。
4. Viterbi: ノード毎に k-best (K=16) を保持し、
   単語コスト + 接続コスト + 文節数ペナルティ (既定 260、環境変数
   `BI_SEG_PEN` で調整可) の総和最小を選ぶ。同点近傍では文節数が
   少ない経路を優先するタイブレークを持つ。
5. 結果: 最良経路の文節列 + 文節毎の候補 (選択中を先頭、残りは
   コスト順、かな形を付加) + 重複除去済み n-best 文字列。

活用形は辞書にほぼ無い (かきました 等は未登録) ため、語幹 +
助動詞の合成で成立させる設計: かき(書き) + まし + た。
助詞・助動詞側の部品はコスト 0 で辞書に存在する。

### 強制境界 (文節区切り変更の土台)

`bi_convert_forced` は文字位置の境界リストを受け取り、境界を
跨ぐノードを lattice から除外して再変換する。OSK の文節伸縮は
これで実装できる (セッション API の `bi_session_resize` が内部で
使用: 対象文節より前の区切りは保持し、対象文節の終端だけ動かす)。

## コストモデル (conn.c)

辞書の conn 部 (256×256) は全ゼロで出荷されているため、接続
コストは自前モデルで供給する (`bi_engine_stats.conn_from_dict`
が将来辞書が実マトリクスを持てば 1 になる)。

- スケール: 単語コスト = 辞書コストバイト × 16 (0..4080)。
  接続は 良好 120–350 / 不利 600–1000 / 稀 1500–2500 /
  ほぼ禁止 3500–6000 (有限値に留め、経路が消えないようにする)。
- 品詞 52 クラスを約 31 の振る舞いグループに束ね、グループ間の
  行列 + 例外テーブルで構成する。
- 助詞→内容語は一律値にせず、助詞の表記毎 (が/を/に/へ/と/で/
  から/まで/より) にプロファイルを持つ。一律 2600 にした初期版は
  「は」が「葉」へ逃げる等の破綻を起こしたため廃止した。
- 助詞同士は 10×10 のサブタイプ表 (格助詞・係助詞・接続助詞…)。
- 活用の接続 (て/で/た/だ/ます/たい/ない 等) は、左ノードの読み
  末尾のかな行と動詞クラス (五段連用=イ段/っ/ん、未然=ア段;
  一段・サ変・カ変は語幹末尾 イ/エ段; 形容詞連用=く) から
  要求形を復元して判定する (form_adjust)。
- 文頭/文末 (BOS/EOS) コストもここで定義する。

根拠と既知の限界は conn.c 冒頭コメントに集約してある。要点:
mozc は 3,019 の語彙化された接続クラスを持つのに対し本モデルは
52 クラスしかなく、単語 bigram も無い。文脈依存の同音異義の
解消能力はここが上限になる (REPORT-m1.md の失敗分類参照)。
この上限が M2 の動機であり、下記のサイドカーで置き換えた。
conn.c のルールモデルはサイドカーが無い場合のフォールバック
として残す。

### M2: 語彙化接続コスト (サイドカー .bisc)

BIDF v2 のエントリは ID 情報を持たないため、mozc の接続行列
(2,672×2,672) をサイドカー表 `data/brainux2.bisc` として
併置する (`tools/gen_sidecar.py` が生成。入手元・ライセンス・
検証方法は REPORT-m2.md)。

- 対応付け: BIDF を作った `convert_mozc.py` の dedup を再演
  する。各 BIDF トークンについて、同一 (読み, 表記) かつ
  `classify(lid)` が BIDF クラスと一致する mozc 生エントリの
  うち最小コストのものを源泉とし、その mozc コストを BIDF の
  量子化式で再量子化してトークンのコストバイトと一致する
  ことを全数検証する (180,000 件全件一致、未対応 0 件)。
- 同点 (最小コスト同点で lid が割れる) グループは 294 件。
  行列の列平均 (左文脈としての付きやすさ) + 行 25 パーセン
  タイルで決める。行平均は語幹のような「少数の後続にだけ
  安く付く」ID を不当に罰し、辞書出現数による頻度重みは
  助動詞・助詞の出現数が少なすぎて機能しない (どちらも実測
  で確認した失敗)。
- .bisc 形式 (LE): 64B ヘッダ ("BISC" v1) + トークン毎の
  lid/rid u16 プレーン×2 + クラス代表 (未知ノード用に
  クラス毎の最頻 lid/rid) + 行列 u8[2672×2672]
  (生コスト / 64 に量子化)。7,860,672 バイト。
- 実行時: 辞書と並べて mmap (ゼロコピー)。接続コスト =
  格納値 × 64 × scale/1000 (scale 既定 200 = 単語コスト
  バイト×16 とのバランスを調整コーパスで決定)。BOS は
  rid 0、EOS は lid 0 として行列を引く。サイドカー有効時は
  conn.c のルールモデルと form_adjust は丸ごとバイパスし、
  単語コスト側の surface_penalty のみ併用する。
- 配置: `$BI_SIDECAR`、無ければ辞書パス + ".bisc"。
  `$BI_NO_SIDECAR=1` で M1 モデルに強制 (A/B 比較用)。

### M2: 音便合成 (engine.c `add_onbin_virtuals`)

mozc は音便語幹を独立エントリとして持ち行列もそれを知るが、
BIDF の 180k 選定で脱落した語幹が 1,047 件あり、脱落すると
て形全体が壊れる。合成が要るのは語幹末尾が変わる促音便 (っ)
と撥音便 (ん) のみ (イ音便・サ行は語幹がそのまま合成できる)。
入力中に っ/ん + て/た (で/だ) を見つけたら、候補となる
連用形の読み (接頭辞 + 可能な語幹末尾かな) を完全一致検索し、
五段 (クラス 20) で表記末尾がそのかなに一致するエントリから、
語幹+て/た を 1 ノードとして合成する (合成ペナルティ既定
400、辞書合成が実在すればそちらが勝つ)。lid は元の動詞、
rid はクラス 63 代表 (出側は完成した て形として振る舞う)。
連濁は合成不要 (手紙等の読み自体が辞書に登録されている)。

## セッション API (OSK / ツールキット v2 との接続点)

候補 UI が必要とする 4 操作を `bi_session` として定義した
(include/brainime.h のドキュメントコメントが契約):

1. 候補一覧: `bi_session_result` → 文節毎の候補列挙。
2. 再変換なしの候補選択: `bi_session_choose` (文節の表記だけ差替)。
3. 文節伸縮して再変換: `bi_session_resize`。
4. 先頭文節を確定して継続: `bi_session_commit_first`
   (確定文字列を返し、残りを preedit として再変換)。

M2 で修正済み: `bi_session_commit_first` は確定した文節の
品詞・lid/rid・読み末尾を左文脈 (`bi_leftctx`) として保持し、
残りの再変換では文頭ノードの接続を BOS ではなくその文脈
から計算する (例: 手紙を確定した残り をかきました が
を書きました に正しく変換される。M1 では ヲか気ました に
劣化)。新しい preedit を設定すると文脈は破棄される。

resize の意味論も M2 で強化した: 強制境界だけでは「その
位置に区切りがある」ことしか保証できず、文節内部に別の
区切りが入る場合がある。resize 時は対象文節の区間を
no-cut zone として lattice に渡し、区間内に開始/終了する
ノードを禁止することで、文節がちょうど新しい長さの
1 ノードに再変換されることを保証する。

### M2: 学習 (最小実装)

`bi_engine_enable_learning(e, path)` で有効化。確定のたびに
(読み, 確定表記) を数え、TSV ファイルへ即時書き戻す
(再起動を跨いで永続)。変換時は単語コストから
1 回あたり 100、上限 10 回分 (最大 1000) を差し引く。
設計上の位置づけ: 接続コスト (文脈) はサイドカーが担い、
学習は個人の語彙選好だけを担う。頻度による接続コストの
再推定やランキング学習は行わない (データ量に対して過学習
リスクが大きく、M2 の範囲外)。

## fcitx5 アドオン (M1 では設計メモのみ)

- 位置づけ: 既存アプリ (X 経路) への入力は薄い fcitx5 アドオン
  経由、libbrainui アプリとグリーターは libbrainime を
  インプロセスで直接使う (調査レポートの決定通り)。
- アドオン本体は C++ の薄いラッパ: fcitx5 の InputMethodEngine
  インターフェース実装 + preedit/候補リストの橋渡しのみを持ち、
  変換・候補・文節操作は全て libbrainime のセッション API に委譲。
- 候補 UI は fcitx5 標準の候補リスト表示を使い、独自描画はしない。
- anthy は回帰テストが合格するまでフォールバックとして残す
  (調査レポートの決定)。切替は fcitx5 の IM 切替で利用者選択。
- M1 では未実装。M2 でも対象外 (本メモの更新のみ) とし、
  実装は次マイルストーン。M2 でセッション API 側の前提は
  揃った: 左文脈の引き継ぎと学習はセッション/エンジン内部で
  完結するため、アドオン側は M1 設計通り薄い橋渡しのままで
  よい (確定イベントの追加配線は不要)。

## 性能設計

- 辞書は mmap 共有で常駐を増やさない。エンジンの作業メモリは
  入力長に比例する lattice のみ (通常文で数十 KB)。
- 実測は REPORT-m1.md / REPORT-m2.md: M2 はロード約 12 ms、
  変換平均は M1 と同等 (ホスト実測で悪化なし)、ピーク RSS は
  行列ページの常駐分だけ増えて約 12.6 MB。ARM (i.MX283、
  単コア・低クロック) では桁違いに遅くなる前提で、ゲスト
  実測は引き続き合格条件 (M2 ではホスト実測のみ)。

## M3: BIDF v3・補完語彙・bigram・学習型リランカー

詳細と実測は REPORT-m3.md が正本。ここには構造だけを記す。

- **BIDF v3 (`.bid3`)**: 辞書+接続+補完+bigram+重みを単一ファイル化
  (7,755,000 B、旧2ファイル合計 9,804,901 B から −20.9%)。144 B
  ヘッダ+ (id, off, len, crc32) ディレクトリ+8 セクション。全セク
  ションを mmap 上で直接参照し、ロード時の展開コピーはしない。
  open 時に全セクション CRC32 検証 (不一致は拒否)。DICT セクショ
  ンは BIDF v2 そのもので、v2 ローダを base 付きで再利用する。
- **CONN**: mozc 行列を頻度順に ID 順列+4 ビット線形量子化
  (3,569,828 B)。ニブルはマッピング上で直接読む。
- **SUPP**: NEologd 35,000 件+SudachiDict 112 件の補完語彙。読みは
  1 バイトかな符号化、カタカナ形表記はフラグ化 (1,257,170 B)。
  ノードの表記はマッピング内ポインタ (zsurf) でゼロコピー。
- **BIGR**: Tatoeba 由来の単語 bigram を FNV-1a ハッシュテーブル
  化 (18,738 対、262,152 B)。その場で探査する。
- **リランカー**: Viterbi 上位候補 (コスト窓 400 以内) に対する
  14 特徴の線形モデル。重みは RNK セクションの float32×14 を
  ポインタ参照。学習はホスト側構造化パーセプトロン
  (tools/train_rerank.c + patch_rerank.py)。初期重み (w0=1,
  他 0) = M2 の順序と等価。
- **表面キャッシュ**: 唯一のプロセス側キャッシュ。直接マップ型
  ハッシュ、上限は BI_SURF_CACHE (既定 1024) 件数。線形スキャン
  LRU は実測で逆効果だったため不採用。
- **学習の永続化 (M3 で方式変更)**: 追記ジャーナル (1 コミット=
  1 行+fsync) + 件数予算超過時に tmp+rename で原子的圧縮。破損行
  はロード時に読み飛ばす。辞書ファイル自体は書かない。配置は
  microSD 上の Brainux 領域前提 (eMMC には置かない・書かない)。

## M7: 表記 prior (PRIO セクション)

詳細と実測は REPORT-m7.md が正本。構造だけを記す。

- **PRIO (section id 9, 任意)**: トークン毎の表記 prior デルタ
  (コストバイト単位の int8、u32 ntok ヘッダ付き、180,004 B)。
  ローダがトークン索引の展開時に tok_cost へ加算する (0..255 に
  クランプ)。節は open 時に CRC 検証する群。欠落時は無変更で、
  M3〜M6 の辞書がそのまま読める。適用件数は bi_stats.n_prior。
- **prior の中身**: コーパス頻度から得た読み内表記選好
  Δ = −λ·(ln p̂(s|r) − Σp̂ ln p̂) (読み内で中心化、読み間の
  バランスは mozc に委ねる)。生成は m7work/gen_prior.py、
  ビルダーは --prior で受けて PRIO 出力 + SUPP バイト調整を行う。
- **attested-only が必須の教訓**: 同一読みでコーパス実証のない
  表記を α 床で降格してはならない。教師 (Sudachi) と辞書
  (mozc) の読み割り当て不一致 (例: 私は わたくし 読み) で
  標準表記が誤って最大降格を受ける。実証のある表記同士でのみ
  競争させる (--attested-min 1)。
- 採用構成 (M7): λ=200、attested-min=1、中心化 plain 形、
  対象 796 読み・2,436 (読み,表記)・4,185 トークン。
