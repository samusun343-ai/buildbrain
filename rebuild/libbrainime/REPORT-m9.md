## 1. 残存エラーの再分析（完了）

現行辞書で dev 系（dev_big 2,000 + dev500 500 = 2,500 文）を再ダンプし
（m9work/dump.py → dump_dev_big.jsonl / dump_dev500.jsonl）、top-1 ミス
1,065 件（dev 合算 top-1 = 57.4%）を再分類した（m9work/classify.py）。
分類は best パスの分割に対する gold の DP パースで「同一分割か」を
厳密に判定し、表記選択をさらに細分した。

### 1.1 分類表（ミス 1,065 件に対する割合）

| 分類 | 件数 | 割合 | 内容 |
|---|---|---|---|
| S-kanakanji | 515 | 48.4% | 同一分割、かな↔漢字のレジスタ選択ミス |
| S-kanji | 270 | 25.4% | 同一分割、漢字同士の同音異字選択ミス |
| S-fold | 30 | 2.8% | カナ畳みで一致（カタカナ/ひらがな形のみ相違） |

| D | 71 | 6.7% | 分割相違だが gold が n-best@16 内（順位負け） |

M7 連続性指標（dev 合算）: n-best@16 内 609 (57.2%)、@16 外 456

### 1.2 表記選択の「回収可能性」に対する証拠（S 818 件、最初の相違セグメントで測定）

| 証拠 | 割合 | 解釈 |
|---|---|---|
| コーパス unigram 頻度が gold を支持 | 26.7% | 頻度だけでは 1/4 しか救えない |
| 同点（両方同頻度。両方 0 を含む） | 11.2% | |
| gold 表記がその読みでコーパス未実証 (count=0) | 20.8% | 頻度系の手法では原理的に到達不能 |
| 左文脈 bigram が gold を支持 | 26.2% | |
| 右文脈 bigram が gold を支持 | 23.2% | |
| 左右どちらかの文脈が gold を支持 | 35.6% | 文脈系の上限の目安 |
| 文脈証拠が両表記とも皆無 | 24.9% | |

かな↔漢字の方向（最初の相違セグメント、535 件）: gold=かな
（モデルが漢字に過変換）330 件 vs gold=漢字（モデルがかなのまま）
205 件で、**過変換側が約 1.6 倍**。コーパス（Tatoeba 系）の書き手
分散が大きく、同一読み内でも train 側の頻度多数派と dev gold が
一致しないケースが常態であることが、unigram 支持率の低さ
（26.7%）に表れている。

### 1.3 次に効く軸の特定（証拠ベース）

1. **表記選択は依然として支配的（76.8%）だが、その回収可能分は
   構造的に bounded**。頻度証拠（unigram＋両側文脈）が gold を
   支持するのは S の最大でも ~45%（重なりを除くと 35.6% が文脈、
   26.7% が unigram で、両者は部分的に重なる）、20.8% は gold が
   未実証で頻度系では到達不能、残りは書き手分散。M8 で SBGR と
   エイリアス束ねがどちらも実らなかったのはこの上限と整合する。
   → 実験A（右文脈＋共線性解消）は「文脈が支持する 35.6%」の
   取り分を狙う bounded な試行として位置づける（期待値は低め）。
2. **最大の細分類はレジスタ（かな↔漢字、48.4%）で、過変換への
   偏りがある**。→ 実験B（レジスタ保存型 prior）はこの偏りを
   「他読みの頻度をそのまま使う」形を避けて狙う。
3. **分割・カバレッジ（23.2%）が第2の軸**。X の実例には
   「おせっかい→お節介」のように gold 表記自体は辞書にあっても
   gold の分割が n-best に届かない型と、一夜漬け/太刀打ち等の
   長尾語彙型が混在する。これは順位付けではなくラティス/辞書側の
   問題で、prior/bigram 系とは別の手（剪定の多様性、未知語処理。
   M7 §7-2 の継続課題）が要る。M9 の実験対象ではないが、表記選択
   系の実験が頭打ちになった後の主戦場として記録する。

## 2. 実験A: SBGR 改良（右文脈＋共線性解消）— 実装完了、学習中

実験ツリー m9work/v5sb（m8work/v4sb のコピーに改修）。M8 §次への
申し送り 1 の (a)(b) を実施し、(c) min-count 緩和は行わない
（bounded の範囲を (a)(b) に限定）。

### 2.1 設計（feat_ver 5、BI_RERANK_NFEAT 30 → 32）

- 新セクション RBGR（id 11）: SBGR と同レイアウトのハッシュ表、
  キー =（読み， 表記， 後続表記）、値は右文脈 lift
  ln P(s | r, 次表記) − ln q(s | r)（nats×256 の int16）。
  生成器 m9work/gen_rbgr.py（gen_sbgr.py の鏡像、α=10、min-count 2、
  競合読みのみ）: 17,894 トリプル、セクション 262,152 B。
- 特徴の再設計:
  - 26 = 左 lift の内容語境界のみの和（v4 の 27）
  - 27 = 左 lift の全境界平均（v4 の 28）
  - 28 = 左 lift の内容語境界の最小（v4 の 29）
  - 29 = 右 lift の内容語セグメントの和
  - 30 = 右 lift のセグメント平均
  - 31 = 右 lift の内容語セグメントの最小
  - **v4 の特徴 26（全境界の和）は廃止**。これは特徴 28（平均）と
    （セグメント数+1）倍の関係にあり完全共線だった（M8 §3.1 の
    解釈 (b) への対処）。内容語和と平均は別集計のため残した。
- 辞書（M7 prior + SBGR + RBGR、未学習）: 8,983,872 B
  （M7 比 +786,504 = SBGR 524,296 + RBGR 262,152 + 増分）。

### 2.2 実装時の発見と配管検証

- **ローダーの潜在バグを踏んだ**: v3_parse のディレクトリ解析に
  `id > 10` の拒否条件があり、RBGR（id 11）付き辞書が
  "cannot open dictionary" になった。M8 が拡張したのは CRC 検証
  ループと配列側で、この上限は SBGR 追加時（9→10）に続いて
  今回 11 へ引き上げが必要だった。dict.c の該当条件と CRC
  ループ3箇所を 11 に統一して解消。
- 等価性検証（M8 と同一手続き）: M7 未学習辞書（brainux3-att）の
  RNK 重み 26 個に 0 を 6 個足した重みを v5 辞書へ埋め込み、
  dev500 の best を att 辞書と比較 → **0/500 件の不一致**。
  特徴 26〜31 のゼロ重み条件下で従来動作と完全一致し、新セクション
  と特徴再配置の配管が正しいことを実証した。
- v5sb ツリーでの crc_test: 0 failures（RBGR 節の破損が変換時
  拒否になることを含む）。

## 3. 実験B: レジスタ保存型 prior — 生成器と未学習 A/B

生成器 m9work/gen_prior_m9.py（gen_prior_m8.py に2モード追加）。
回帰確認: --pool none は M7 の prior_l200att.tsv と**バイト一致**
（796 読み調整、M8 §0.1 の無プーリング時カバレッジと一致）。
条件は M8 と同一（λ=200、attested-min 1、cmin=30、cap=48 bytes）。

変種（どちらも「他読みの頻度をそのまま使う」形の回避）:
- **cap**: full pooling の転送量に上限（--cap-transfer 100）。
  M8 の失敗例では（わたし, 私）に 7,192 件が流入したが、上限付き
  では最大 100 件までしか借りられない。cmin=30 の約3倍で、借用
  表記が競争に参加するには十分だが読み固有のレジスタを
  覆すには小さい、という水準に置いた（1値のみ、掃引はしない）。
- **kanafree**: かな表記を prior の競争集合から完全に除外
  （delta 常に 0）。競争は漢字表記同士でのみ、漢字側のカウントは
  full pooling を使う。プーリング証拠が読みのかな/漢字バランスを
  動かす経路を構造的に断つ形。

辞書はどちらも M7 と同寸（cap 8,197,360 B / kanafree 8,197,368 B、
PRIO 節のみ差し替え）。

### 3.2 学習済み A/B と判定

（train_rerank_ck = §0 で tools/ に取り込んだ正本。train_m5
42,650 件 × 3 エポック、M7/M8 と同一レシピ）

| 候補 | dev_big | dev500 | tuning | sentences | heldout(手) | 合議 |
|---|---|---|---|---|---|---|
| M7 attt（基準） | 58.2 (1164) | 54.2 (271) | 87.9 (51) | 87.9 (51) | 79.3 (46) | 1486 |
| capt（cap 学習済み） | 57.8 (1155) | 54.4 (272) | 89.7 (52) | 89.7 (52) | 81.0 (47) | 1479 |
| kft（kanafree 学習済み） | 57.0 (1139) | 54.6 (273) | 89.7 (52) | 89.7 (52) | 79.3 (46) | 1464 |

McNemar:
- capt: dev_big は M7-only 20 / capt-only 11、net −9、χ²=2.1
  （有意ではないが負方向）。dev500 は net +1、χ²=0.0。
- kft: dev_big は M7-only 57 / kft-only 32、net −25、
  **χ²=6.5 で有意に悪化**。dev500 は net +2、χ²=0.1。

**両変種とも不採用。**
- cap は M8 full pooling の有意な悪化（net −17、χ²=6.6）を
  「有意でない負方向」（net −9、χ²=2.1）にまで緩和したが、
  改善には届かなかった。転送量を絞っても、他読みの頻度が
  dev の正解方向を向かないという §1.2 の証拠（unigram が gold を
  支持するのは 26.7%）がそのまま効いている。
- kanafree は有意に悪化した。かな表記を競争から外すと、M7 prior が
  かな側で果たしていた調整（レジスタの微調整を含む）まで失われ、
  漢字側だけのプーリング証拠では補えなかった。「レジスタ保存」の
  名目で prior の仕事そのものを止める形は逆効果という結果。
- 学習時 ckpt dev は capt 59.3 / kft 58.2（M7 attt 59.7）。
  辞書サイズは両変種とも M7 と同寸（8,197,360 / 8,197,368 B）で、
  不採用の理由はサイズではなく精度である。

**M9 の実験はいずれも不採用。現行辞書（M7 採用、
data/brainux3.bid3、8,197,368 B、md5 83efffa7…、M9 では無変更）が

| 項目 | 判定 | 根拠（実測） |
|---|---|---|
| 0. 基盤整備（trainer tools/ 取り込み） | **完了・採用** | 等価性検証で重みバイト一致。陳腐バイナリ2件を解消。make test / test3 / crc_test 全緑 |

DESIGN.md の形式節は無変更（採用された形式変更がないため）。
辞書サイズ・RSS: 無変更（8,197,368 B / RSS 13,476 kB は M7 実測）。
テスト（§0.3 で再実行）: make test exit 0、make test3 exit 0

### M9 を通じた結論

表記選択への3方向の攻撃（文脈 lift の左右両側化、転送の上限付き
プーリング、かな除外プーリング）が全て実らなかったことと、
§1 の回収可能性の証拠（頻度・文脈が gold を支持するのは S ミスの
最大 ~45%、20.8% は gold 自体が未実証、過変換への偏り 330:205）は
整合している。**コーパス頻度に基づく表記選択の改善は、現行
コーパスと現行の特徴設計の範囲では頭打ち**と判断する。残る
レバーは §1.3-3 の分割・カバレッジ側（23.2%）と、コーパス自体の
増量・質の改善（M7 §7-4 の継続課題）である。
