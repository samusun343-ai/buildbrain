## 1. n-best 内包の微減の回復

### 1.1 原因の特定（証拠）

dev500 で M2 構成に入って M3 構成で落ちた文を全件抽出し（4件）、失敗分類と突き合わせた。原因は単一ではなく3つあった:

1. **補完候補の価格スケール不一致による finals 独占**（実測例: せんしゅうのどようびいらいずっとあめです）。SUPP の NEologd 由来カタカナ形エントリ「せんしゅう→センシュウ」が百分位正規化で cost byte 15 になり、正規の辞書語「先週」より経路合計で **739 単位安く**（9291 対 10030）、その変種（依頼/以来×雨/天/アメ/飴…）が n-best 8枠を全て占有し、正解経路は finals に存在しながら 9位以下に押し出されていた。`BI_NO_SUPP=1` で正解が top-1 に戻ることを確認。
2. **リランカーの swap による追い出し**。M3 の昇格は finals[0] と finals[besti] の交換で、Viterbi 最良の文字列が位置 besti（窓の外）へ移動し、リストから消える場合があった（dev500 の集計で NORERANK との差 ±1件として観測）。
3. **k-best 剪定**。ノード毎 BI_KBEST=16 の枠を、SUPP ノード追加で増えた近接変種の部分経路が奪い、正解の部分経路が境界で剪定される（dev A/B: KBEST 16→24 で n-best +2件、32 では +1件止まり）。

なお dev500 の集計では M3 構成の n-best は M2 構成比で微増（74.6% 対 74.2%）であり、held-out の −0.4pt/−1.7pt は上記メカニズムによる数件の落下と統計的揺らぎの合算だった。

### 1.2 修正と測定（dev500、M3 辞書）

| 構成 | top-1 | n-best@8 | n-best@16 |
|---|---|---|---|
| M3 エンジン（変更前） | 269 (53.8%) | 373 (74.6%) | — |
| M4 エンジン（下記 a–d） | **270 (54.0%)** | **374 (74.8%)** | **393 (78.6%)** |

- a. **SUPP カタカナ形ペナルティ**: `add_supp_nodes` で is_kata の補完ノードに一律 +24 cost byte（環境変数 `BI_SUPP_KATA_PEN` で調整可）。実測例ではセンシュウ経路が 9291→9675 となり、正解がリランカー昇格で top-1 に復帰した。SUPP 自体の集計寄与は元々 ±1件規模で、無効化はしていない（候補としての価値は §2 で活かす）。
- b. **リランカー昇格を swap から挿入へ**: 追い出されるのは末尾の限界的な文字列だけになる。
- c. **BI_KBEST 16→24**（32 は追加利得 +1件に対し遅延増が読み取れたため不採用。中間の 24 を選択）。
- d. **BI_NBEST 8→16**（製品の n-best リスト長の変更として明示する。リスト長 8 に揃えた比較でも 373→374 と回復しており、回復はリスト長だけに依存していない）。

### 1.3 測って捨てた案: n-best 多様化パス

「既出と2文節以上異なる finals を優先する」多様化収集を実装して測ったところ、対象の混雑ケース（それより今日の家事当番はわたしだったっけ）は救えたが、dev500 の n-best は **78.6% → 72.0%（−6.6 pt）** に悪化した（多様だが高コストの finals が中位の正解経路を追い出す）。測定結果をもって撤回した。この種の混雑（同音異義の直積変種による占有）は残件として残る。

## 2. 補完候補（SUPP）の候補リスト統合

- **欠落の実証**: 「さわらをたべました」では変換器が SUPP ノード「佐和良」を選択するのに、文節候補には辞書語（触ら/早良/佐原/鰆/椹…）しか並ばず、同じ読みのもう1つの SUPP 表記「佐波良」が候補に現れなかった（SUPP は格子には入るが候補列挙が辞書グループしか見ていなかった）。
- **修正**: `build_result` の文節候補生成で、辞書グループの後にそのスパンの SUPP ヒットを列挙して追加する（重複排除、上限は候補枠 +8）。セッション候補も同じリストを使うため OSK 側もそのまま直る。
- **回帰テスト**: session_test に v3 辞書時のケースを追加（「佐波良」が候補に存在し、選択すると「佐波良を食べました」になる）。`make test3` で PASS。v2 辞書では自動スキップ。

## 3. bigram 文脈拡張とリランカー v2

### 3.1 特徴量 v2（feat_ver=2、14→24 特徴）

M3 の特徴は文全体の bigram 合計1本に潰れていて「証拠がどの境界にあるか」を区別できなかった。v2 は文節境界をまたぐ文脈を境界位置と**前文節のクラス/表記**で分解した（端末推論は従来通り内積のみ、RNK は 64 B → 104 B）:

- 14: BOS bigram スコア /256、15: EOS bigram スコア /256、16: bigram ヒット件数
- 17: 前文節が機能クラス（助詞・助動詞等）のペアの bigram 合計、18: 前文節が内容クラスのペアの bigram 合計
- 19: 機能→内容の遷移数（文節の開始）、20: 内容→機能の遷移数（文節の接着）
- 21: 漢字を含む文節数、22: 表記総文字数、23: 前文節の表記が全てかなである文節数

ついでに発見したビルダーのバグも直した: `build_bidict3.py` の RNK ヘッダは (nfeat, feat_ver) の順で書いており、ローダと patch スクリプトの期待する (feat_ver, nfeat) と逆だった（M3 では patch 工程が上書きしていたため顕在化しなかった）。ビルダーをローダ側に合わせて修正。

### 3.2 学習と窓の決定

- 学習は構造化パーセプトロン（従来通り）。dev500 を除いた train_m4（4,660件）で学習したモデルの dev500: trainer 内評価で Viterbi 48.4% → リランク 55.6%、エンジン実測（窓400）で **top-1 54.8%**（M3 重み+M4 エンジンの 54.0% から +0.8 pt）。
- **権限窓は 400 のまま維持**。窓1000/無制限は dev500 では 55.8% と良く見えたが、手作り58文が 89.7%→81.0%、手作り held-out が 77.6%→67.2% に崩れた（コーパス学習の暴走を窓が止めるという M3 の設計意図を再確認）。コーパス dev だけを見て広げないことにした。
- 出荷重みは同じレシピ（8エポック、窓400）で train_mix 全量（5,160件）から再学習したもの。14エポック版の実験は実行環境のリスタートで中断し、結果が残らなかったため採用していない（未検証のものを混ぜない）。

### 3.3 held-out 結果

top-1 **56.3%**（M3 55.9% から +0.4 pt）、n-best@8 **81.6%**（同 +1.0 pt）、手作り tuning 89.7%（+1.7 pt）、手作り held-out 75.9%（同等）。

### 3.4 60% に届かなかったボトルネック内訳（正直な報告）

- **候補プールの天井**: リランカーが選べるのは Viterbi 上位24経路（collect プール）の中だけ。プールに正解が含まれる割合は train で 84.0%（4332/5160）、dev で 79.2%（396/500）。top-1 の上限はここで決まる。
- **順位付けの負け**: §4 の通り、候補外91件のうち78件は「全ての単語が格子内に存在するのに経路の順位で負けた」もの。接続コスト（4ビット量子化済み行列）と単語コストの較正不足が主因で、特徴量の追加だけでは吸収しきれなかった。
- 次のレバー（M5 候補）: collect プールの多様化/拡大による学習カバレッジ向上、クラス bigram の辞書内蔵（現 BIGR は表記ペアのみ）、接続コストの再較正。いずれも未実施。

## 4. 候補外 89件の精査

M3 分類の「候補外 89件」を、M4 エンジン（最終重み適用前）で再計算すると両構成とも n-best@8 に無いものは **91件**だった（エンジン変更で出入りがあり +2）。DP による整列可能性解析（読みに沿って辞書+SUPP のペアで正解表記を組み立てられるか）で内訳を分けた:

| 分類 | 件数 | 内容 |
|---|---|---|
| 表記揺れで救える | 6 | 正解と n-best 内の文字列が、長音・促音・小書きかな・カタカナ/ひらがなの正規化で一致（コーシャ食品/バター/ベティ等の外来語・固有名の表記選択差） |
| 格子内に全単語があるのに順位で負け | 78 | 辞書追加は不要。コストモデル側の問題（§3.4） |
| TOKENS_PER_SPAN=16 の上限で落ち | 3 | 否決（ひけつ）・渡辺は私の姓です・金切り声 — 必要な表記が読みグループの17番目以降 |
| 辞書追加で救える | 4 | 不足ペアが各1つだけ（下記） |

- **表記揺れ 6件**は評価上の差であり、エンジン出力の表記を正規化で寄せる変更はしない（正解側の表記が常に正しいとは限らないため）。件数の実測のみ報告する。
- **上限で落ちた 3件**: TOKENS_PER_SPAN を 24/32 に上げる A/B を dev500 で実施したが top-1/n-best とも不変で遅延だけ増えたため、16 のまま維持した（held-out の3件を追って全体を遅くしない）。
- **辞書追加 4件**: 不足ペアは (いらいら, 苛々)、(ままはは, 継母)、(ちょうじり, 帳尻)、(とんぼがえり, トンボ返り)。いずれも **SudachiDict core（Apache-2.0）に普通名詞として実在することを SudachiPy で確認**してから SUPP に追加した（cls=1、cost byte=180、source=sudachi — M3 §1 の台帳方式を維持。BIDF 本体・コーパス unigram・mozc 全量リストのいずれにも無いことを先に確認済み）。追加後の実測: トンボ返り・帳尻の2件は top-1 完全一致まで回復。継母は表記が生成されるようになったが文単位では別の曖昧性（じしょ→地所/辞書）で不一致。苛々はペア追加後もカタカナ形（イライラ）が top-1 で、候補到達のみ改善。
- **サイズ相殺**: 追加4件で SUPP は +88 B、§3 の RNK 拡張 +40 B、合計 **+128 B**。v3 の予算（M2 構成の総量 9,804,901 B を上限とする M3 以来の枠）に対し残り余裕は約 2.05 MB あり、相殺のための削除は不要だった。

## 5. ロード時間: CRC32 遅延検証

### 5.1 方式

M3 は open 時に全セクション（7.75 MB）の CRC32 を検証し、ロード増の主因になっていた。M4 の方式:

- **open 時検証（従来通り）**: ローダ自身が open 中に解析する DICT（1,944,229 B）と、小さい制御セクション CLSREP/RNK/META。破損は open 失敗として従来通り拒否される。
- **遅延検証**: TOKID/CONN/SUPP/BIGR（計 5,809,242 B）は、エンジンの変換入口（`bi_convert` 系・セッション再変換・trainer の collect）と各アクセサ（conn_raw/supp/bigram）の初回利用前に `bi_dict_verify_pending` が検証する。不一致なら辞書を broken とし、変換は失敗する。
- `BI_CRC_FULL=1` で M3 の「open 時に全検証」に戻せる。

### 5.2 保証が落ちていないことの根拠と検証

遅延されるのは「検証のタイミング」だけで、**未検証のバイトが変換結果に使われる経路は存在しない**（検証は格子構築より前に完了し、失敗時は変換自体が失敗する）。DICT を open 時検証に残したのは、ローダが open 中に DICT を解析して使うためで、ここを遅延させると保証が実質落ちるので対象外にした（タスクの例示より保守的な線引き）。

`tests/crc_test.sh`（`make test3` に組込）: 全8セクションに1バイトずつ破損を入れ、open 時検証の4セクションは open 拒否、遅延の4セクションは open 成功→初回変換が拒否、無傷ファイルは正常変換、を全て確認（0 failures）。

### 5.3 実測

- open 時 CRC 対象: 7,755,000 B → **1,945,989 B（−75%）**。
- ロード時間（同一セッションで交互測定した中央値）: 全検証 27.8 ms → 遅延検証 **18.6 ms（−9.2 ms）**。最終ファイル単体では中央値 13.9 ms（ホストは他ラインの QEMU 作業と共有しており絶対値はセッション間で揺れる。同セッション A/B の差分を正とする）。
- 代償: 初回変換が遅延分の CRC（5.8 MB）を1回だけ払う。2回目以降は検証済みフラグの参照のみで、変換遅延への影響は測定誤差内。

## 6. UBSan 指摘（engine.c:1892）への対応

他ラインの UBSan ビルド OSK テストで `libbrainime/src/engine.c:1892` に「nonnull 属性の引数への NULL 渡し」1件の指摘があった（テスト自体は全 PASS）。M4 側で確認・判定・修正した。

- **再現**: libbrainime 単体を `-fsanitize=undefined` でビルドし session_test を v3 辞書で実行 → `src/engine.c:1892:2: runtime error: null pointer passed as argument 1, which is declared to never be null` を同一行で再現した。
- **該当箇所**: `session_set_bounds()` の `memcpy(s->bounds, b, nb * sizeof(int))`（引数1 = コピー先 `s->bounds` が NULL）。
- **NULL が流れる経路（実在する）**: `bi_session_new` は calloc で `bounds=NULL, cap_bounds=0`。境界のないセッションで `bi_session_commit_first` を呼ぶと、残り境界が 0 件のため `session_set_bounds(s, nb, 0)` が呼ばれ、realloc も走らず `memcpy(NULL, b, 0)` になる。OSK の通常フロー（リサイズなしの文節確定）がそのまま該当する。つまり「属性の付け間違い」ではなく、実際に NULL が流れうる呼び出しである。
- **実害判定: 現行環境では実害なし**。コピー長 0 のため何も読み書きされず、glibc の memcpy はそのまま返る（全テスト PASS と整合）。ただし nonnull 属性付き関数への NULL 引数は C 標準上は未定義動作で、コンパイラ最適化や環境が変われば保証はないため、修正した。
- **同所で見つけた潜在バグ（指摘とは別）**: 旧コードは realloc 失敗時に `bounds=NULL` のまま `cap_bounds` だけを増やし、`nb>0` の memcpy で実際にクラッシュしうる経路があった。
- **修正**（`session_set_bounds`）: (1) `nb>0` のときだけ memcpy する。(2) realloc 失敗時は旧 bounds/cap/n_bounds を保持して早期 return する。
- **修正後検証**: 同じ UBSan ビルドで session_test を実行し、runtime error 0 件・全 PASS を確認した。

## 7. 恒常原則への適合と残件

- **ゼロコピー/mmap**: 辞書再構築後も全セクションをマッピング内直接参照する構造は不変。§5 の遅延検証もコピーを生まない（検証は読み取りのみ）。§2 の候補追加は文節毎の小さな文字列コピー（候補リストの所有仕様通り、従来と同じ場所）。
- **キャッシュ**: 変更なし。表記キャッシュ（上限つき直接マップ）の実測ヒット率は bench 読み物494件で **72.3%**（172,738 hits / 238,895 回）。
- **永続化**: 学習ジャーナルの原子的保存・回復仕様は M3 から変更なし。辞書ファイル自体は読み取り専用前提で、配置は microSD の Brainux 領域、eMMC には触れない。
- **期限**: 件数・容量ベースのみ（本マイルストーンで時間ベースの要素は追加していない）。
- **残件**: (1) top-1 60% 未達 — §3.4 のレバー3点。(2) 同音異義の直積変種による n-best 占有（§1.3）。(3) TOKENS_PER_SPAN 上限で落ちる3件（全体の遅延と引き換えになるため見送り）。(4) 14エポック学習の再実験（環境リスタートで中断したまま）。
