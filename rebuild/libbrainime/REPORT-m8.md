## 0. 予備分析（実測）

### 0.1 エイリアス束ね（候補2）の構造

- プーリングの恒等式: 読み r のエイリアス群（表記を共有する読みの
連結成分）に対する C(G(r), s) は、「表記 s を登録する全ての読み」
に対する c(r', s) の和と等しい（s を共有する読みは定義により
同一群に属す）。union-find を回す必要はなく、表記ごとの全読み
合計で厳密に計算できる。
- カバレッジ（cmin=30・attested≥1 の M7 基準、m8work/alias_probe.py）:
プーリングなし 796 読み / 2,500 (読み,表記) → 全プーリング
1,107 読み / 4,129。POS ゲート付き（後述）1,028 読み / 3,584
deltas（gen_prior_m8.py 実測）。
- 動機の実例: （わたし, 私）コーパス頻度 0 に対し、全読み合計は
7,192（全て わたくし 配下）。Sudachi の読み割り当てが mozc 登録と
割れる高頻度語で、M7 の attested-only は安全だが対象外だった。
- 副作用の実例と対策: 無条件プーリングでは（し, 私）（pos 50、
私立等の拘束形）に代名詞（わたくし, 私）（pos 12）の 7,192 件が
流入する。対策として **POS ゲート**: 転送元 (r', s) と転送先
(r, s) の登録 POS が交わる場合のみ転送する。（し, 私）pos 50 vs
（わたくし, 私）pos 12 → 不一致で遮断。（かみ, 紙）pos 1/2/3 vs
（し, 紙）pos 9 → 遮断。（あした/あす/みょうにち, 明日）は全て
pos 13 → 転送可。判別が構造的に効くことを実データで確認した。

### 0.2 表記ペア bigram（候補1）の密度分析

- 現行 BIGR のキー (pr, ps, cr, cs) を (ps, cr, cs) に周辺化しても
distinct 数は 140,402 → 140,073 とほぼ減らない。前読みは前表記
からほぼ決定されるためで、キー周辺化は密度対策にならない。
効くのは (a) スコアの条件付き化（生頻度 48·log2(n) →
lift = ln P(s|前表記, 読み) − ln P(s|読み)）、(b) 対象を競合の
ある読み（コーパス実証表記 ≥2 の読み 3,093 件）に絞った
テーブル設計、の2点と判断した。
- SBGR テーブル（m8work/gen_sbgr.py、α=10 バックオフ、min-count 2、
競合読みのみ）: 20,290 トリプル、セクション 524,296 B
（65,536 スロット×8B、BIGR と同寸）。

## 3. 候補1（SBGR）の実装（実験ツリー m8work/v4sb）

- 新セクション SBGR（id 10）: BIGR と同レイアウトのハッシュ表、
キー = (前表記, 読み, 表記)、値は lift（nats×256 の int16）。
- ローダ（dict.c）: セクション id 上限 9→10、v3_sec 配列 [10]→[16]、
遅延 CRC 検証ループを id 10 まで拡張、SBGR アクセサ
bi_dict_surfbigram() を追加。crc_test.sh の convfail 群に id 10
を追加。
- リランカー feat_ver 4（BI_RERANK_NFEAT 26→30）: 特徴 26 = SBGR
lift の全境界和、27 = 内容語境界のみの和、28 = 境界あたり平均、
29 = 内容語境界の最小 lift（ミスは 0 として扱う）。
※ M6 の実験ツリー feat v4（特徴26/27 がカタカナ形/かな同一の
bigram 和）とは別物。本ツリーの v4 は本節の定義が正本。
- 辞書（M7 prior + SBGR、未学習）: 8,721,696 B（M7 比 +524,328 =
SBGR 節 524,296＋ヘッダ/RNK 増分）。
- 配管の等価性検証: SBGR 重み 0 の v4sb エンジンは M7 未学習辞書と
dev500 で best が 0/500 件一致 — 特徴 26〜29 の追加自体は
ベースラインを一切乱さないことを実証済み。

## 4. 事故・記録

1. **m5work/train_rerank_ck は陳腐化した M5 時代のバイナリで、
PRIO 付き辞書を開けない**（"cannot open dictionary" で即死。
data/brainux3.bid3 でも再現）。M7 が実際に使ったのは
m7work/train_rerank_ck。M8 の学習は全てそちらを使う。
M7 §7-5 の「チェックポイント版 trainer の tools/ 取り込み」は
未実施のままで、本件がその実害である。
2. alias_probe.py 初版は union-find＋集合再構築で非効率だったため
停止し、§0.1 の恒等式による高速版に書き換えた（所要 21 秒）。
3. **ランタイム再起動で学習ジョブ2件（full / SBGR）が epoch 1 の
途中で死亡**（チェックポイント重みは未書出、成果物の欠落なし。
M7 §6-2 と同型の事故）。3件の学習を逐次チェーンで再投入して
復旧した。
4. **2回目のランタイム再起動で SBGR 学習が epoch 3 の途中で死亡**
（再投入チェーンの full / pos は完了済みで無事）。チェック
ポイント設計どおり epoch 2 までの平均化重み（w_sbgr.bin、
ckpt dev 59.9%）は保存されていた。epoch 3 の更新は喪失。
標準レシピ（3エポック）の重みで再投入し、並行して epoch 2
重みの先行評価を行う。

data/brainux3.bid3、8,197,368 B）がそのまま残る。60% 目標は

|---|---|---|
| 2. エイリアス束ね prior（full） | 不採用 | dev_big で有意に悪化（net −17、χ²=6.6）。合議 1471 < 1486 |

held-out 494 文について: **M8 では採点していない。** 最終辞書が
M7 で採点済みのバイト列と同一（無変更）である以上、再採点は

1回だけの規律に従い実施しなかった。M7 の測定値 58.7%
（290/494）が現行辞書の held-out 成績として引き続き有効。
（M8 の全スクリプトが eval_pairs.tsv を参照していないことは
grep で確認済み。手作り heldout 58 文は従来どおり使用した。）

主ツリーへの変更: **なし**（全実験は m8work/ 内で完結。
DESIGN.md の形式節も無変更 — 採用された形式変更がないため）。
テスト（2026-11-20、現行辞書・主ツリーで再実行）:
make test exit 0（session_test PASS。v2 辞書 check の FAIL は
Makefile が (ignored) とする既存仕様で M8 の変更起因ではない）、

### 次への申し送り（M9 候補）

1. SBGR の改良余地は (a) 右文脈（後続表記）の追加、(b) f26/f28
共線性の解消（平均のみ残す等）、(c) min-count 緩和とテーブル
拡大、にある。ただし v1 の転移ゼロを見ると期待値は低め。

train 分布（Sudachi 分割の癖）を拾っている疑いがある。

「他読みの頻度をそのまま使う」形が否定された。レジスタを
壊さない形（例: 転送量に上限、かな表記を競争集合から除外）
は未検証だが、full/pos の劣化幅を見ると優先度は低い。
3. チェックポイント版 trainer の tools/ 取り込み（M7 §7-5）は
依然未実施。M8 では m7work/train_rerank_ck を使わざるを得ず、
§4-1 の事故がその実害。次期着手時に最初に行うべき小作業。
