## 2. BIDF v3 形式仕様（`.bid3`）

- 単一ファイル、**little-endian**、ヘッダ 144 B: magic `"BID3"`、version u32（=3）、セクション数 u32（=8）、以降 16 B × 8 のディレクトリ（id u32, offset u32, length u32, **crc32 u32**）。
- 整合性: ローダは全セクションの CRC32（IEEE、slicing-by-8 実装）を open 時に検証し、不一致ならファイル全体を拒否する（実測: CONN 内 1 バイト反転で open 失敗を確認）。辞書は読み取り専用前提で、実行時に一切書き込まない。
- バージョニング: 形式 version が 3 でないファイルは拒否。セクション ID は固定（1=DICT, 2=TOKID, 3=CLSREP, 4=CONN, 5=SUPP, 6=BIGR, 7=RNK, 8=META）。未知の必須セクション欠落は拒否、RNK の特徴量バージョン（feat_ver=1）と特徴数（14）は RNK セクション内に保持し、エンジン側の定数と一致しない場合はリランカーを無効化して Viterbi 順で動く（辞書自体は使える）。
- セクション:
  - **DICT** (1,944,229 B): BIDF v2 イメージをそのまま内包。v2 ローダを base オフセット付きで再利用（v2 ファイル単体も従来通り開ける。切替可能）。
  - **TOKID** (720,004 B): 全 180,000 トークンの mozc lid/rid を u16 平面 ×2（lid 平面、rid 平面）。旧 .bisc の同等物。
  - **CLSREP** (1,024 B): 品詞クラス 256 × (lid, rid) 代表値。
  - **CONN** (3,569,828 B): 接続行列。§3 の圧縮を参照。
  - **SUPP** (1,257,170 B): 補完語彙 35,112 件。レコードは「読みを 1 バイトかな符号（ひらがな U+3041–3096 → 0–85、ー=86、ゝ=87、ゞ=88）に符号化したバイト列」でソートし、u32 オフセット配列で二分探索する。表記の 58% は「読みのカタカナ形」と一致するためフラグ 1 ビットで表しバイト列を持たない（SUPP はこの2工夫で 2.96 MB → 1.26 MB）。レコード: rlen u8, flags u8（bit0=カタカナ形）, cls u8, cost u8, 読み符号列, （非カタカナ時のみ slen u8 + 表記バイト列）。
  - **BIGR** (262,152 B): bigram ハッシュテーブル。§4。
  - **RNK** (64 B): feat_ver u32, 特徴数 u32, float32 重み ×14。ローダはポインタを張るだけ（コピーなし）。
  - **META** (368 B): 生成元・版・ライセンス帰属のテキスト（provenance）。
- ビルダー: `tools/build_bidict3.py`。生成物: `data/brainux3.bid3`（7,755,000 B）。

## 3. 接続行列の圧縮（実データで方式選定）

mozc 行列 2,672×2,672（u8 で 7,139,584 B）に対し、実エンジンで精度を測って選んだ:

- **量子化**: 4 ビット線形量子化（16 段階、LUT = round(238·i/15)、/64 ドメイン）が heldout58 39/58・sentences58 48/58 で無劣化（u8 原本は 39/58・47/58）。対数量子化・ブロック min+4bit は劣化したため不採用。エントロピー符号化（zlib 全体で 1.21 MB まで縮む）は「ロード時展開＝コピー発生」のためゼロコピー原則で不採用。
- **ID 順列（参照局所性）**: mozc の左右 ID を「コーパス unigram 頻度 ×64 + (255 − コストバイト)」の熱さ順に並べ替えた。熱い ID 同士の接続がファイル先頭側に集まり、短い入力では CONN の先頭ページだけが常駐し、冷たい行はほぼフォールトインしない（常駐ページの実測は §7）。

結果として CONN は 7,139,584 B → 3,569,828 B（§2 のセクションサイズ）になり、精度は無劣化だった。

## 4. 単語 bigram（統計的言語モデル）

- Tatoeba 日本語文 248,989 文（CC BY 2.0 FR、台帳は §1）をホスト側教師 SudachiPy（SudachiDict core）で形態素解析し、単語 bigram **18,738 対**を抽出した。文そのものは辞書に収録せず、統計だけを取り込む。
- 格納は BIGR セクション（262,152 B、§2）: FNV-1a ハッシュテーブル（オープンアドレス法）をファイル内に持ち、エンジンはマッピング上で直接探査する。ロード時の展開やコピーはしない。
- 用途は §5 のリランカーの特徴量の材料で、文節境界をまたぐ語の連接の自然さを表す。

## 5. 学習型リランカー

### 5.1 方式

- Viterbi の上位候補（finals）に対し、**14 特徴の線形モデル**で再スコアリングする。重みは RNK セクションの float32 ×14（= 56 B）をローダがポインタ参照するだけで、コピーは生じない。これが端末側に置く全「学習成果物」である。
- 特徴計算は中間文字列を作らず、マッピング内の表記ポインタから直接計算する。端末側の推論は内積のみ。
- 初期重み（w0=1、他 0）は M2 の順序と等価で、リランカー無効時は Viterbi 順のまま動く（§2 の RNK バージョニング規則）。

### 5.2 学習

- 学習はホスト側の構造化パーセプトロン（平均化）で行う（`tools/train_rerank.c`）。エンジンの収集する特徴ベクトルそのものを使って学習するため、学習時と推論時で特徴の定義がずれない。
- 学習ペアは Tatoeba 由来の **4,000 件**に、手作り tuning 58 文を **×20 で混合**した。コーパスだけでは手作りセット側の性質が埋もれるための措置で、効果は §5.3 の通り。
- 学習した重みは `tools/patch_rerank.py` で RNK セクションへ書き込む（セクション CRC の更新込み）。

### 5.3 権限窓と A/B 測定、棄却した変種

- リランカーの寄与は A/B 測定で **+8.3 pt**（top-1）。
- ただしリランカーを無制限に適用すると手作りセットが壊れた。そこで昇格できる候補を「Viterbi 最良からコスト **400 以内**」に限る**権限窓**を導入し、コーパス側の利得と手作り側の安定を両立させた（この窓の設計意図は M4 §3.2 でも再確認されている）。
- 実測して棄却したもの: 学習の更新符号を逆にした構成は発散し、train top-1 が **0.1%** に崩壊した（符号の意味は `tools/train_rerank.c` のコメントにも記録）。特徴量の変種も、悪化したものは実測をもって棄却した。

### 5.4 ニューラル端末推論を採らない理由

- 端末は ARMv5・単コア・RAM 128 MB で、ニューラル推論のランタイム常駐と計算コストが見合わない。一方で線形モデルなら重み 56 B・推論は内積のみで、§5.3 の通り実測で +8.3 pt の寄与が得られた。
- 方針として、重い処理（学習）は全てホストで済ませ、端末には成果物（重み）だけを置く。AI 技術の活用は、この形（統計 LM の内蔵＋学習型リランカー）で実施した。

## 6. 評価の内訳と失敗分類

held-out の採点結果は §0 の表の通り。コーパス held-out 494 文について M2 構成と M3 構成を突き合わせた失敗分類（`m3work/classify.py`）:

| 分類 | 件数 |
|---|---|
| M3 が修正した | 50 |
| M3 が壊した | 13 |
| 両方誤り・正解が候補内 | 116 |
| 両方誤り・正解が候補外 | 89 |

- 候補外 89 件は辞書カバレッジの天井にあたる（表記揺れで正解が一意に定まらない文を含む）。
- 候補内 116 件は順位付けの問題で、リランカーの過剰昇格を含む。

## 7. 性能実測

- **変換速度**: M2 と同帯域で回帰なし（§0）。交互実行3ラウンドの中央値で M2 13.1 ms / M3 11.4 ms、bench の長時間ループでは M2 6.53 ms / M3 7.14 ms。ホスト VM のスロットリングで絶対値は不安定なため、順序の入れ替わりうる同帯域と判定した。
- **ロード時間**: ~12–14 ms（M2）→ ~20–26 ms（M3）、**+約10 ms**。全セクション CRC32 検証分である。CRC の当初のバイト単位実装は 106 ms かかったため棄却し、slicing-by-8 化した（§2）。
- **ピーク RSS**: 14,072 kB → **12,412 kB**（−1,660 kB、−11.8%）。
- **常駐ページ**: §3 の ID 順列により、接続行列の常駐は **1,744 → 873 ページ**に減った。

## 8. 追加原則への対応

- **ゼロコピー**: 全セクションを mmap で直接参照する。DICT は v2 ローダの再利用、CONN はニブル＋LUT をその場で読む、SUPP ノードの表記はマッピング内ポインタで保持、RNK はポインタを張るだけ、BIGR はマッピング上で直接探査する。リランカーの特徴計算も中間文字列を作らない。
- **キャッシュ**: プロセス側キャッシュは表面キャッシュ **1つだけ**（直接マップ型ハッシュ、上限は件数で 1,024 件 = `BI_SURF_CACHE` 既定値）。実測ヒット率 **72.3%**、変換は約 25–50% 高速化した。当初実装した線形スキャン LRU は実測で逆効果（9.2 ms 対 6.8 ms）だったため、直接マップ型に作り替えた。
- **永続化と実機の現実**: 学習データの保存を「毎回全書換え」から、**追記ジャーナル（1コミット=1行+fsync）＋件数予算超過時に tmp+rename で原子的圧縮**する方式に変更した。破損行・寸断された末尾はロード時に読み飛ばして回復する（実測で確認済み）。辞書ファイル自体は読み取り専用で、CRC で破損を検出し、実行時に一切書き込まない。配置は microSD 上の Brainux 領域を前提とし、**eMMC には置かない・書かない**。追い出しや上限は全て件数・容量ベースで、時刻ベースの要素は無い。

## 11. 再現手順

1. **コーパス準備**: Tatoeba 日本語文を取得し、`m3work/prep_corpus.py` で SudachiPy を教師に読み・形態素列を生成する（学習ペア 4,000 件、評価ペア 494 件、unigram / bigram 統計）。
2. **補完語彙の抽出**: `m3work/extract_supp.py` で NEologd seed と SudachiDict から SUPP 候補を抽出する（重複排除とコスト正規化は §1 の規則）→ `m3work/supp.tsv`。
3. **辞書ビルド**: `tools/build_bidict3.py` で `data/brainux3.bid3` を生成する（RNK は初期重み w0=1、他 0 で出荷される）。
4. **リランカー学習**: `tools/train_rerank.c`（ビルド済み `tools/train_rerank`）で学習ペアから重みを学習し、`tools/patch_rerank.py` で RNK へ書き込む（CRC 更新込み）。
5. **評価とテスト**: `m3work/classify.py` で M2 / M3 両構成を評価ペアに走らせ §6 の失敗分類を得る。テストは `make test` / `make test3`。

## 12. 残件

- **ARM ゲスト実測**: M1 / M2 から継続の合格条件だが、M3 でもホスト実測のみで未実施。
- **n-best 内包の微減**: コーパス −0.4 pt、手作り −1.7 pt（§0）。悪化として記録し、回復は次マイルストーンの課題とした。
- **補完候補の候補リスト統合**: SUPP は格子には入るが、セッションの候補提示への統合が未完。
- **bigram の文脈拡張**: M3 の bigram 特徴は文全体の合計として潰れており、文節境界の位置情報を持たない。
