## 1. 前任の残置物の検証（鵜呑みにしない）

前任（初期段階で結果なしに終了）の m5work/ を全点検した:

- `new_pairs.tsv`（40,000件）: gen_pairs.py は M3 のフィルタと SudachiPy 教師解析を再現し、Tatoeba の未使用スライス（seed-42 シャッフルの index ≥24500）から生成。除外ガード（既存 train/dev/eval と手作り2セットの (読み, 正解) 一致を排除）が効いており、実際に6件が落とされていた。独自に再検証: eval 494文の正解表記は train_big の正解として **0件** しか現れない（表記単位でも漏洩なし）。
- `train_big.tsv`（44,650行）: = new_pairs 40,000 + train_m4 の dev500 除外分 4,650行（手作り tuning の ×20 重み付け重複を含む）。集合としては一意 43,548 件。dev500 / eval / 手作り held-out との (読み,正解) 重なりは全て 0 を実測。
- `base.bid3` = 現行辞書の RNK を初期重み（w0=1）にリセットしたもの、`base_w.bid3` = 現行辞書の完全コピー、`e0.bid3` = `w_m4recipe.bin` の重みを入れたもの。セクション CRC の全数比較で同定した（DICT〜META は RNK 以外全て現行と一致）。
- `new_unigram.tsv`: 新規40,000文の単語頻度（19,577 エントリ）。§4 の単語コスト再較正の材料として用意されていたもの（今回は §4 の通り見送り、理由を記録）。

## 3. コストモデル較正の試行（攻めどころ a の後半）— 測って捨てた2件

### 3.1 グローバル scalar のスイープ（dev_big、Viterbi のみ）

- BI_CONN_SCALE_PM（接続コストの全体倍率）: 150→40.5% / 200（現行）→46.9% / 250→47.2% / 300→47.0% / 343→45.8% / 400→44.8% / 500→41.5%。200〜300 は平坦で、250 の +0.3pt はノイズ（σ≈1.1pt）以内。
- BI_SEG_PEN（文節ペナルティ）: 180〜340 で 46.7〜47.0%、無反応。

→ 大域的な倍率・ペナルティは既に最適域。較正不足は「文ごとに異なる局所的な誤差」であり、scalar では直らない。

### 3.2 CONN 量子化 LUT の最適化 — 実測で棄却

仮説: CONN の 4ビット線形量子化（ステップ ~15.9、/64 単位）の誤差（境界あたり最大 ±8 /64単位 ≈ ±102 エンジン単位）が順位負けの一因、というもの。検証:

- 現行リニア LUT の RMS 誤差: 一様重み 4.46 / 使用頻度（hotness）重み 4.52（/64 単位）
- Lloyd-Max 最適 16 レベル: 4.07 / 4.23 — **わずか −8%**

値の分布が広くほぼ一様なため、線形量子化は既にほぼ最適だった。量子化はボトルネックではない（RMS ~4.5 /64単位 ≈ 58 エンジン単位/境界は残るが、これは mozc 行列自体の /64 解像度に由来し、LUT では消えない）。**棄却**（解析スクリプトは m5work/lut_opt.py、候補 LUT は m5work/lut_candidates.json に保存）。

### 3.3 単語コスト再較正（コーパス頻度の反映）— 見送り

単語コスト byte は mozc コストの百分位正規化（M2 世代の convert_mozc.py）で、コーパス頻度は mozc コスト自体に織り込み済み。新規 unigram（40,000文）で上書きする設計は、(1) mozc の dictionary_oss 原データがワークスペースに無く DICT 再生成パイプラインを完全には再現できない、(2) 頻度の二重計上になる、ため見送った。代わりに §4 の特徴量 v3（コスト分解）で、学習器が word/conn の効き方を文脈特徴と合わせて調整できる経路を選んだ。

## 4. 順位付けの強化（攻めどころ b）

### 4.1 特徴量 v3（feat_ver=3、24→26 特徴）: コスト分解

M4 の分析（順位負けの主因は接続コストと単語コストの較正不足）に対し、特徴 0 は総コストに word と conn が固定比率で混ざっており、学習器はその比率を動かせなかった。v3 で分解した:

- 24: 単語コスト合計 / 1000
- 25: 接続コスト合計 / 1000（BOS〜EOS、conn_pct 適用済み、seg_pen は含まない。path_features 内で Viterbi と同じ conn() を使って再計算し、f0 との整合を保つ）

端末推論は従来通り内積のみ（特徴が2本増えても 26 回の積和）。RNK セクションは 104 B → 112 B。

健全性チェック（train_m4 4,660件・1エポック、KBEST48/MP64）: dev500 の trainer 内評価で Viterbi 48.4% → リランク **55.6%**（M4 の v2 特徴・8エポック相当の水準に1エポックで到達）、dev500 カバレッジは 83.6%（プール 24 の 79.2% から +4.4pt）。学習された f25 の重みは +4.29 で、モデルが接続コスト側の重みを自律的に引き上げた（較正が実際に起きている証拠）。

### 4.2 学習の大規模化

学習データは train_m5 = 42,650行（一意 41,548件 + 手作り tuning の ×20 重み付け重複）。M4 の 5,160行から 8.3 倍。dev_big・dev500・eval・手作り held-out との重なりは全て 0（§1）。

- 構造化パーセプトロン（平均化）3エポック。trainer 内 dev_big（窓なし）top-1 はエポック 1/2/3 で 57.3 / 57.2 / 57.2% と初回で収束した（M4 の「エポックを増やしても train top-1 が振動するだけ」という観測と整合。大規模化の利得はエポック数ではなくデータ量から来ている）。
- 学習された重みでは f24（単語コスト）に +1.08、f25（接続コスト）に +3.82 が乗り、f0 と合わせて接続コスト側の実効重みが単語側より大きくなった。固定比率（conn_scale_pm=200）では到達できない較正が学習で実現したことが、dev_big で Viterbi 46.9% → 56.1% という伸びの主因。
- **事故と対策（正直な記録）**: 最初の学習実行（4エポック計画）はホスト側のプロセス整理で約35 CPU-分経過時点で kill され、重みが終了時にしか書かれない設計のため全損した。再実行では trainer にエポック毎のチェックポイント保存＋dev 評価を追加した改変版（m5work/train_rerank_ck.c）を使い、3エポックで完走した。今後の長時間学習はこの版を使うこと。

### 4.3 窓の再決定 — 400 を維持

新モデルでも窓を広げる実験をした（dev_big、エンジン実測）:

| 窓 | dev_big | dev500 | hand tuning | hand held-out |
|---|---|---|---|---|
| 400（現行） | 56.0% | 54.8% | 86.2% | 77.6% |
| 500 | — | — | 77.6% | 65.5% |
| 600 | 56.9% | — | 75.9% | 67.2% |
| 1000 | 58.2% | 57.4% | 77.6% | 69.0% |
| 無制限 | 58.4% | 57.6% | 77.6% | 69.0% |

コーパス dev では +2.4pt 伸びるが、手作り2セットが 500 の時点で既に崩れる（M4 と同じ構図）。コーパス（Tatoeba＋Sudachi 教師）の表記・語彙分布が人手の日常文とずれていて、窓を広げるとコーパス流の上書きが日常文を壊す。**窓は 400 を維持**する（M4 の設計意図を新モデルで再検証した）。

### 4.4 微調整（warm start）— 測って不採用

hand tuning の低下（§5.4）への対処として、最終重みから warm start し「手作り tuning ×20（シェア 18.8%）+ コーパス 5,000件」で2エポック微調整した。結果: tuning 86.2→87.9%（+1件）だが dev_big 56.0→55.4%（−12件）、hand held-out は不変。便益がノイズ域で代償が系統的なため**不採用**とし、単段学習の重みを出荷した。

## 5. 最終評価

### 5.1 KBEST の A/B（同じ重み・同セッション）

| 構成 | dev_big top-1 | bench 平均 | ピーク RSS |
|---|---|---|---|
| KBEST 32 / MAXPATH 64 | **56.1%** | **7.91 ms** | **12,832 kB** |
| KBEST 48 / MAXPATH 64 | 56.0% | 13.26 ms | 13,852 kB |

KBEST 48 の含有率優位（+1.3pt）は top-1 に結びつかなかった（追加される finals は近接変種が大半）。**KBEST=32 を採用**。対 M4 構成（KBEST 24）の同セッション A/B では平均変換 +3.8%、RSS +412 kB に収まった。

### 5.2 held-out 最終採点（1回のみ、単一パス）

top-1 **283/494 = 57.3%**、n-best@8 **406 = 82.2%**、n-best@16 **419 = 84.8%**（§0 の表）。dev 推定（dev_big 56.1% / dev500 54.8%）と整合し、held-out 固有の過学習はない。

### 5.3 プール含有率（事後分析）

eval 494文での含有率は @64 で **86.8%**（429件、平均プール 31.6）。M4 時点の @24 = 79.2%（dev500）から天井は大きく上がった。

### 5.4 手作り tuning の −2件について

tuning 58文は学習データに ×20 で含まれるにもかかわらず 52→50件に下がった。原因は希釈: M4 では tuning の学習シェアが 22.5%（1,160/5,160）あったが、M5 では 2.7%（1,160/42,650）になり、コーパス分布への引力が相対的に強まった。held-out 側の手作り（学習に含まない）は 44→45件と改善しており、汎化性能としての手作り文の扱いは悪化していない。§4.4 の微調整はこの差を埋めきれなかったため、次段（M6）では学習データ側の配合（コーパス 4万件に対する手作り・日常文コーパスの増量）を課題とする。

### 5.5 ボトルネック内訳の更新（held-out ミス 211件、ダンプからの事後分類）

| 分類 | 件数 | 備考 |
|---|---|---|
| プール外（@64 に正解なし） | 65 | 部分経路の剪定・TOKENS_PER_SPAN・未知の分割 |
| プール内だが n-best@16 にも無い | 10 | 窓・順位の複合 |
| n-best@16 内にあるが top-1 でない（順位負け） | 136 | 線形モデル＋窓で取り切れる範囲はほぼ到達 |
| 文節候補から組み立て不能（辞書・分割の欠落） | 36 | 辞書側の課題 |
| （重複集計）表記選択の差: カナ表記を畳むと正解と一致する表記が n-best 内に存在 | **144** | ミス全体の 68%。ユミコ/ゆみこ、こと/コト、こちら/コチラ 等、意味は合っているが表記が違う |

次のレバー（M6 候補）: (1) BIGR の増強 — 現行 BIGR は M3 の 20k 文由来 18,738 対のまま。新規 40k 文を加えた ~65k 文から再抽出すれば文脈証拠が増える（スロット倍増でも +256 KB 程度、予算内）。(2) 表記選択のモデル化（かな/漢字の表記嗜好を特徴に）。(3) プール外 65件への対処（剪定の多様性、未知語の扱い）。

### 5.6 テストフィクスチャの変更（M3 の前例に倣う）

session_test の学習デモ対象を 神 → 紙 に変更し、コミット回数を 6 → 10 にした。理由: M5 のリランカーが「神を書きました」を自力で top-1 にするようになり、「神は非ベースライン」という前提が崩れた（M3 が 髪→神 に変えたのと同型）。紙 は M2（ベースライン 上）・M5（ベースライン 神）の両構成で非ベースラインであることを実測して選んだ。回数増は v2 構成で紙への反転に必要な学習ボーナス（600 では不足、1000 = 上限で反転）を実測で確認したため。変更後、make test / make test3 の両方で session_test PASS。

### 5.7 ロールアウト時に踏んだバグ（記録）

特徴量 v3 の辞書（feat_ver=3）を最初にエンジンで評価した際、top-1 が Viterbi と完全一致した。原因は dict.c のローダが feat_ver 1/2 のみを許可し、3 を「未知の版」として無効化していたこと（builder と patch スクリプトだけ更新し、ローダの版ゲートを見落とした）。ゲートを 1..3 に広げて解消。本ツリーにも同じ修正が入っている。数字が「良すぎる/悪すぎる」ではなく「ベースラインと完全一致」だったことが検出の手がかりになった。

## 6. 恒常原則への適合

- **ゼロコピー/mmap**: 辞書の全セクションをマッピング内直接参照する構造は不変。特徴 24/25 の計算も中間文字列を作らない（ノードの数値フィールドと conn() の再計算のみ）。
- **キャッシュ**: 変更なし（表記キャッシュは上限つき直接マップのまま）。
- **永続化**: 学習ジャーナルの原子的保存・回復仕様は不変。辞書は読み取り専用、配置は microSD の Brainux 領域、eMMC ノータッチ。
- **期限**: 件数・容量ベースのみ（時間ベースの要素は追加していない）。
- **ロード時間**: 遅延 CRC の経路・対象は M4 から不変で、ファイルは +8 B のみ。絶対値はホスト競合で単発比較が不能なため、M4 の 18.6 ms を基準値として据え置く（悪化要因は構造上ない）。
- **辞書サイズ**: 7,755,136 B（予算 9.80 MB に対し余裕 2.05 MB）。
