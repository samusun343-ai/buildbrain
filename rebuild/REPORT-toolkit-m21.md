## 2. green 化の処置方針

ユーザーの確定基準: 既定は「一致させる」。例外は Brain 実機への
適合に具体的な必要性を数値・実測で示せる箇所だけ。

- **完成させる**（ピンを根拠付きで更新）: #1、#3、#4、#5、#6、
  #7、#8、#10。いずれも記録済みの参照換算値への一致であり、
  実機適合上の必要性（タッチフロア等）は箱・グリフではなく
  行高・操作領域で満たされるため、例外には当たらない。
  - #6 のトークン値（18dp / 8dp）は §16.2 の記録に基づく。
    test_tk17 のヘッダには RadioButtonTokens icon 20dp との
    併記があり記録間に不整合があるため、実コード突き合わせ
    フェーズで material3 の実トークンを再取得して再検証する
    （§5 で扱う）。
- **戻す**: #2。理由: (a-5) の Slider 形は §16.2 が明記するとおり
  「ピル型ハンドル化のユーザー判断を先取りしない」分離項目で、
  トラックだけ 19px にしても Expressive 形（ピルハンドル前提）
  でもクラシック形（4dp トラック）でもない中途の形になる。
  無印・無記録の変更でもあり、M20-fix 時点の 16px に戻す。
  Slider 形そのものの扱いは従来どおり判断待ちのまま。
- **部分的に完成させる**: #9。Android モード（style 1）は
  参照換算 37px に一致させる。WinUI / classic は第一者 Chip が
  無く（WinUI #16 A の ◐ 根拠は部品の不在）、tk7 がピンする
  共有形 40px を維持する。存在しない「AUDIT §19」への引用は
  本レポートと AUDIT §19（M21 記録、新設）で実体化する。
- #11 は実測で帯の本数を確認してから判定する（次節）。

方法: 同一ツリーでラベルを実文/空白に差し替えた

  container_high が全て 565 値 0x2965 に collapse。
  surface_alt / container_low / layer /
  control_fill3 / control_fill_dis / sys_attn_bg が
  0x2945 に collapse。border 系は 0x3186。
  → カードや subtle 塗りは面との差が消え、境界線
  だけでしか見えない。既知の「WinUI ボトムバーの
  subtle 塗りがほぼ不可視」（light 側）と同型の
  問題が dark では面全体に広がる。
- **WinUI light の状態塗り**: control_fill2
  （hover 系）/ control_fill3（pressed 系）/
  control_fill_dis / sys_attn_bg が 0xf7be に
  collapse し、bg からは 1ステップ。ただしこれは
  24bit 時点で既に 1〜2/255 しか離れていない
  Fluent トークン固有の性質で、参照側でもほぼ
  見分けがつかない。**参照固有として記録し、
  調整は提案しない**。
- M3 light: inverse_on_surface と container_mid が
  collapse（0xf77e）。用途文脈が別（スナックバーの
  文字色とアプリバーの容器色）で、並んで比較される
  場面が無い。記録のみ。
- M3 dark: desktop_bg と smoke（スクリム）が
  collapse（0x1062）。スクリムはアプリ内容の上に
  描かれるため実害は限定的。記録のみ。
- classic: collapse なし（1ステップ差が3組、
  いずれも近接グレー同士）。

**処置方針**: WinUI dark のラダーだけは実害が
あるが、直すには Fluent の逐語値から意図的に
離れる必要があり、(a) と同種の判断事項になる。
寸法の再前提（§8）と合わせて親の段階判断に
委ね、本弾ではトークンを変更しない。調整する
場合の方向: dark の面ラダーの段差を 565 の
1ステップ（緑で約4/255）以上に広げる。適用時に
プローブをテスト化して固定する。

### 9.2 グラデーションのバンディング

ライブラリにグラデーション描画は存在しない
（include/・src/ に gradient の実装なし）。影は
単段の α シルエット（黒25%を1回ブレンド）で
ランプではない。角丸の AA も 1px の中間調のみ。
→ ツールキットの描画に関する限りバンディングの
発生面はほぼ無く、ディザリングは不要と判断する。
写真・JPEG サムネイル側（部品 #44 の画像経路）は
565 階調の影響を受け得るが、それは画像パイプ
ライン側の観察事項で、ツールキットの欠陥では
ない。

- よって **視野角・コントラスト・ガンマ・応答

### 9.4 抵抗膜タッチの実特性

- 入力源: i.MX28 LRADC の4線式抵抗膜
  （imx28-brain.dtsi: lradc status okay、
  fsl,lradc-touchscreen-wires = <4>、
  **fsl,ave-ctrl = <4> / ave-delay = <2> /
  settling = <10>** — ドライバ側でサンプル
  平均化が設定されている）。I2C の SX8650 は
  status = "disabled" で不使用。
- ツールキット側（src/tk_evdev.c）: ABS を
  `value × screen / (raw_max + 1)` の線形写像
  （raw_max 既定 4095）。追加の平滑化・デッド
  ゾーンは無い。ジッタ対策は LRADC の平均化が
  源泉で担う構成。
- ドラッグ系への含意: スライダーのつまみは
  Ø28px（M3）/ Ø24〜26px（WinUI）あり、値の
  刻みに対して十分大きい。スクロールは内容
  シフト方式。現時点で不足は認めないが、
  実機ドラッグ時の座標ノイズ実測は統合
  フェーズの evtest 項目（必要ならドラッグ中
  の微小デルタ無視を後付けする）。
- ホバー: 物理的に無い。既存の扱い（押下・
  フォーカス状態層で代替、§2.4 の記録）を
  再確認し、変更なし。

### 9.5 アニメーションと残像

- パネル応答速度が未確認（§9.3）のため、
  数値での照合はできない。設計上の点検として:
  ツールキットのアニメーションは参照どおりの
  短い補間（Fluent 83/167/250ms、M3 標準域）で、
  全画面の高速移動はスクロール以外に無い。
  スクロールの残像はこの種のパネルでは参照
  プラットフォームでも起こる性質のもので、
  こちらだけの欠陥とはしない。
- 残る確認: シートのスライド等の大きな移動を
  伴う遷移が実機で読めるかは、統合フェーズの
  実機確認項目とする。
