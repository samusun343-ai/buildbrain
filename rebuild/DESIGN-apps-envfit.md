## 1. なぜ前の形（UI v2 展開版）がこの環境に合っていなかったか

現行コード（apps/files/bd_files.c、apps/notes/bd_notes.c、apps/player/bd_player.c の構築部）と撮影 v2_09/v2_10/v2_13 の実数:

### 1.1 同時露出の量が「詰め込み」そのもの

| アプリ | 常時見えている操作要素（コードから数えた実数） |
|---|---|
| files | ナビ行: 戻る/進む/上へ＋パンくず区間ボタン群＋パス入力 = 4+α。操作行（OverflowBar）: 開く/新規フォルダ/貼付/新規ファイル/コピー/切取/名前変更/削除/復元/情報 = 10。設定行: 検索欄＋検索＋並び替えコンボ＋グループコンボ＋降順チェック＋隠しチェック＋表示切替 = 7。サイドバー: 場所7行＋空き容量。選択時はさらにアクションバー7ボタン。**合計 約28要素＋リスト** |
| notes | 3ペイン同時表示（フォルダ一覧/ノート一覧/編集）。ノートペイン下に 新規/ピン/削除/復元 = 4、編集側に 検索＋書式バー9ボタン（見出し/太字/斜体/下線/取消/箇条書き/番号/チェック/添付）。編集ペイン幅は 800 − フォルダ160 − ノート224 − 間隙 ≒ **約390px（画面の半分以下）** |
| player | ビュー行: ビュー切替5＋検索欄＋戻る＋再スキャン = 8。コマンド行: 次に再生/後で再生/キュー表示/シャッフル/リピート切替＋状態ラベル = 6。プレイリスト行: 名前欄＋作成/追加/リスト削除/名前変更 = 5。再生バー: 前へ/再生/次へ＋音量＋残りチェック = 5。**合計 約24要素＋リスト** |

5.5型 854×480 に 24〜28 個の操作要素を常時出すのは、デスクトップ/スマホ UI の「全部見せる」情報設計の縮小コピーであり、1本指・抵抗膜（静電式より粗い）では誤タップの温床になる。参照製品（§2）はどれも「1画面で同時に出す操作は数個」に抑え、残りを階層・メニュー・文脈バーへ逃がしている。

### 1.2 見た目が参照（One UI / Material You / ChromeOS）と違う

- 現行の既定ボタン描画（src/tk_widgets.c の通常ボタン）は「面の塗り＋細い輪郭線」で、v2 展開ではほぼ全ボタンがこの輪郭線ピルになった。主要/副次の区別はほぼ無い。
- 参照の姿は逆: **強調は塗りで作る**。Material 3 のボタン階層は filled（primary 塗り）＞ filled tonal（secondaryContainer 塗り）＞ outlined ＞ text の順で、輪郭線は中強調の1バリアントに過ぎない（出典 §2.1）。One UI の My Files 画面下部の主ボタンも塗り（淡青の filled）で、アイコン＋ラベル構成（出典 §2.2 実画像）。
- テキストのみボタンが支配的で、参照が多用する「アイコン＋ラベル」「アイコンのみ（ヘッダ）」の形がほぼ無い。

### 1.3 寸法が実寸基準で決まっていない

- 179.2ppi（§3.1）では 48px = 6.8mm しかない。Material の最小タップ対象 48dp = 7.62mm はこの画面では **54px** に相当する。現行は control_h 48px を多用し、抵抗膜の粗さを考えると一次操作には小さい。
- 行・余白・文字の規定が「デスクトップ基準の dp 感覚」のままで、実寸（mm）での裏付けがなかった。

## 2. 実物 UI 調査（アプリごと、出典付き）

### 2.1 共通基盤: Material 3 のコンポーネント階層

出典（今回検索で確認）:
- m3.material.io の icon buttons / buttons 仕様を要約した資料（GitHub `iChintanSoni/skills-master` の m3-icon-buttons SKILL、原典として m3.material.io/components/icon-buttons/overview と developer.android.com を引用）: アイコンボタンは standard（無地）/ filled（primary 塗り、最も強い）/ filled tonal（secondaryContainer 塗り、中間）/ outlined の4種。**タッチ対象は最低 48×48dp、容器 40dp にアイコン 24dp** が既定。
- developer.android.com の FilledTonalIconButton API リファレンス（検索結果で本文確認）: 「filled tonal は filled と outlined の中間の強調」「内部アイコンは通常 24×24dp、最小タッチ対象 48×48dp」。
- Material 3 ボタンのサイズ表（KMP 向け M3 コンポーネント参照、検索結果）: 高さ S=32 / M=40 / L=48 / XL=56dp。強調順位 filled ＞ tonal ＞ outlined ＞ text、filled=primary/onPrimary、tonal=secondaryContainer/onSecondaryContainer。

→ 採用判断: 本環境のボタン文法はこの階層をそのまま使う。**「全ボタン輪郭線ピル」は仕様違反**であり、(a) 主操作1つだけ filled（accent 塗り）、(b) 副次は tonal 塗り、(c) ヘッダ内は無地アイコンのみ、(d) 輪郭線は「面の区別が要る場面」だけに限定する。

### 2.3 notes: Samsung Notes（One UI）

出典（実画像を取得し目視）:
- **Samsung Notes「All notes」（Galaxy Note20 紹介画像）** `https://i.simpalsmedia.com/marketplace/richmedia/0bcb002405159ab3922c6e531c1a27e1.png`（取得・目視）。構成: 大きなタイトル「All notes」＋件数キャプション。その下のツール行は ハンバーガー/表示切替/検索/⋮ の**アイコンのみ**。ノートはタイトル＋日付＋本文プレビューを持つ大きな角丸カード。右下に赤い円形 **FAB（＋）**。テキストボタンは皆無。フォルダはハンバーガー側（ドロワー）にあり、一覧と同時表示しない。

→ notes への採用判断:
1. **2画面構成**: 「ノート一覧」画面と「編集」画面を分離し、ドリルダウンで行き来する（現行の3ペイン同時表示を廃止）。一覧はタイトル＋プレビューの全幅カード行、ヘッダはタイトル＋件数＋検索/フォルダのアイコンだけ。
2. 新規作成は一覧画面の主操作として**塗りの主ボタン**（My Files 下部ボタン型: アイコン＋ラベル「新規ノート」）を下部に置く。FAB はツールキットに浮動配置の仕組みが無く（メニュー/ダイアログ以外の汎用オーバーレイ API が無い — §6 の基盤要求）、基盤側で FAB が用意されれば差し替え可能な形にしておく。
3. フォルダ切替は独立した「フォルダ」画面（すべてのノート/各フォルダ/最近削除の全幅行）へドリルダウン。編集画面は戻る＋検索＋⋮ のみで、ピン/削除/復元/添付は ⋮ メニュー、書式は編集画面下部の**アイコン書式バー**（見出し/太字/斜体/下線/取消/箇条書き/番号/チェック = グリフアイコンのトグル群）に置く。

## 3. 環境適合の寸法規程（実寸）

### 3.1 前提の計算

（M23 再導出: 本節は旧前提（5型 800×480・187ppi）で書かれていたものを、確定した実機値で全面再導出した。前提の正本は AUDIT-toolkit.md §20。）

- 5.5型 854×480、表示域 121.1×68.0mm（シャープ公式仕様。カーネル DTS は 121×68mm）→ 約 **179.2ppi**（横 179.1 / 縦 179.3）。1px = 25.4/179.2 = **0.1417mm**。
- 換算: 48px = 6.8mm / 54px = 7.7mm / 64px = 9.1mm / 72px = 10.2mm / 96px = 13.6mm。
- Android の換算は 1dp = 179.2/160 = **1.12px**。Material の 48dp（160dpi で 7.62mm）は本画面では 53.8px → **54px** に相当する。これを一次タップ対象の基準（タッチフロア）にする（抵抗膜は静電式より粗いので、dp 基準を下回らない）。ツールキットには M22 で適用済み（tk_theme_v2 系の control_h / row_h = 54）。
- WinUI の換算は錨方式で ×1.344（AUDIT §20）。

### 3.2 寸法表（規定値）

| カード角丸 | テーマ既定（radius_card 24） | — | v2 テーマのトークンを尊重（不変） |
| 主ボタン（FAB 代替の下部主ボタン含む） | 高さ 54px、accent 塗り、画面に1つ | 7.7mm | M3 filled / One UI 下部主ボタン。高さはタッチフロア |

### 3.3 情報設計の規定（同時露出の上限）

1. **1画面1仕事**。画面は「選ぶ（一覧）」「読む/編集する（詳細）」「操作する（再生中）」のどれか1つ。
2. ヘッダに出す操作は **アイコン最大3つ＋⋮** まで。それ以外は ⋮ メニューかドリルダウン先へ。
3. 下部バーに出す文脈操作は **最大4つ＋⋮**。常設の主ボタンは画面に1つだけ。
4. 階層はペインではなくドリルダウン（進む=行タップ、戻る=ヘッダの戻る）。パンくずは「タイトル＋パスキャプション」のテキスト表示に限定し、区間ボタン群は置かない。
5. 状態表示（件数・空き容量・再生位置など）はキャプション1行に集約し、操作要素と混ぜない。
6. 480×272（アプリ main の実寸）・480×800（テスト）でも破綻しないこと: 固定幅ペイン禁止、高さは flex で吸収する。

| 一次タップ対象 | ≥56px | ≥54px | フロア連動 |

## 4. コンポーネント外観規定

| 役割 | 形 | 実装上の対応（現行ツールキットで可能な範囲） |
|---|---|---|
| 主操作（画面に1つ） | accent 塗り、輪郭なし、アイコン＋ラベル | `tk_button_set_accent`（塗り＋輪郭なしは実装済み）。ただし現行の accent 描画はアイコンを描かない（§6 要求） |
| 副次操作 | tonal 塗り（面色）、輪郭なし | flat ＋ face 指定で再現可能（実装済みの経路） |

| 下部バーのセル | アイコン（上）＋ラベル（下）、選択/主は tonal 塗り | アイコンセル形式のボタン（実装済み）＋ face |
| 一覧 | 角丸カード面の上に全幅行、選択は inset ピルのトーナル塗り | ListView は v2 でこの形に実装済み（残る問題は周囲の chrome だった） |
| メニュー/ダイアログ | 浮動カード＋影のシルエット | backdrop（実装済み） |
| アイコン | アプリ/場所は同梱 Papirus 由来セット、操作グリフは単色シンボリック | §4.1 |

### 4.1 アイコンの供給（実測した制約）

- 同梱 Papirus 由来セット（assets/app、NOTICE で確認）は **アプリ用17枚のみ**（settings/files/tasks/notes/clock/calc/player/recorder/web/devices/pkg/dict/terminal/home/brightness/volume/trash）。戻る/検索/再生等の**アクションアイコンは同梱にもシステムにも存在しない**（`find /` で Papirus ディレクトリ自体が無いことを確認）。
- 参照 UI（M3/One UI）のアクションアイコンは元々**単色シンボリックグリフ**である。よって操作グリフは、同梱サブセットフォントに収録済みの文字（fonts/build_subset.py の BASE_RANGES: 矢印 U+2190–21FF、幾何学図形 U+25A0–25FF、記号 U+2600–266F、数学 U+2200–22FF、および補完フォントのメディア記号 ⏭ U+23ED / ⏮ U+23EE / ⏸ U+23F8）をキャンバスへ描いてアイコン化する。製品コードでの使用実績も確認済み（← → ↑ ↓ ⇄ ⏭ ⏮ ⏸ ♪ ★ › ＋ ✓）。
- ファイル種別アイコンは現行の描画アイコン（Papirus の精神で描かれたフォルダ/文書/画像/音声/動画/テキストの6種）を継続使用する。

## 5. 実装時に守る契約（コード調査で確定したもの）

基盤確定後の実装ラインが壊してはいけない、現行テストの駆動契約:

### 5.1 files（apps/files/tests/test_files_ui.c）
- 駆動は files_app_* アクション関数が中心。加えて `tk_child_at(top, 0)` の子0（ヘッダの最初の子）を実クリックする → **ヘッダの最初の子は戻るボタン**であること。
- 「D: damage presentation」: プログラム的変更（イベントなし）でも damage・転送・ピクセル変化が出ること → セッタは自動 invalidate しない前提で、アプリ側が明示 invalidate ＋ レイアウト確定（tk_root_layout）を行う現行方式を維持する。
- 480×800（テスト）と 800×480（撮影）の両寸法で成立すること。

### 5.2 player（apps/player/tests/test_player_ui.c）
- ウィジェットアクセサ経由の実クリックで駆動される: ビューボタン×5、play/next/prev、repeat ボタン、queue later/next、プレイリスト名フィールド、create/add ボタン。
- ラベル完全一致: 再生ボタンは再生中「⏸ 一時停止」/停止時「▶ 再生」。リピートラベルは「全て」「1曲」「なし」を含む文字列。
- **プレイリスト作成＋追加だけは画面遷移の変更に合わせてテスト側の駆動手順の改訂が必要**（現行は曲ビュー表示中に名前欄＋作成＋追加が常時見えている前提。新設計では「文脈バーの追加ボタン→ダイアログ→作成→追加」の順になる）。チェック項目・件数は不変とし、駆動順のみ新フローに合わせる（設定アプリ作り直し時の前例と同種の改訂）。この改訂は実装時に明示すること。
- queue later/next は「曲を選択した直後」にクリックされる → 選択連動の文脈バーは、`tk_listview_select` が on_select を発火すること（実装確認済み）を利用し、表示切替直後にレイアウトを確定させてクリック座標を有効に保つこと。

### 5.3 notes（apps/notes/tests/test_notes.c）
- 主にモデルテスト＋ `notes_ime_test()`（bd_notes.c 内）: 480×800・OSK 付きで構築 → notes_app_select → エディタへフォーカス → OSK＋libbrainime で composition→確定→自動保存。新設計では **notes_app_select が編集画面への遷移を含む**ことでこの流れが成立する（OSK は編集画面側に置く）。

## 6. 基盤（GUI ライブラリ）への要求 — アプリ設計から見た不足

アプリ側を作り直す前に基盤で固めてほしい点（現行ツールキットの実コードで確認した不足）:

1. **塗りボタンのバリアントを第一級 API に**: 現行は通常=輪郭線ピル、accent=塗り（ただしアイコンを描画しない）、tonal=flat＋face の裏技的指定。M3 の filled / tonal / outlined / text を明示バリアントとして持ち、**filled でもアイコン＋ラベルが描ける**こと。
2. **横並びアイコン＋ラベルのボタン形式**: 現行は「アイコン上＋ラベル下」のセル形式と「アイコンのみ」しかない。下部主ボタンやダイアログの主操作には横並び形式が要る。
3. **FAB / 汎用オーバーレイ配置**: 現行の overlay はメニューとダイアログ専用。Samsung Notes 型 FAB を置ける汎用の浮動ウィジェット配置が要る（無ければ下部主ボタンで代替する設計にしてある）。
4. **タブ（インジケータ付きテキストタブ）**: player のビュー切替に使う。現行は汎用ボタンの流用で、選択表示は各アプリが indicator を手で付け替えている。
5. **下部バー（文脈バー/ミニプレイヤー）の定型**: 面（backdrop）＋アイコンセルの並び＋表示切替時のレイアウト確定までを定型化してほしい（各アプリが box＋backdrop＋invalidate を手書きしている）。
6. **メニューのアイコン対応**（任意）: 現行 tk_menu はテキスト項目のみ。場所メニュー等でアイコン＋ラベル行にできると参照への一致度が上がる。
