## 1. やったこと

1. **libnsfb brain サーフェスに `target=shm` を追加**
   （`libnsfb/src/surface/brain.c`）。パラメータ
   `target=shm;shmptr=0x…;shmstride=<bytes>;input=none` で、シェル WM が
   memfd で渡す共有バッファを描画先にし、fbdev/evdev を開かない。
   ダブルバッファ切替は `nsfb_set_parameters` の再送で `nsfb->ptr` を
   張り替える（DESIGN §1.1 の指定どおり）。埋め込み側が所有する
   バッファは finalise で解放しない。fbdev 経路は従来挙動を維持
   （要求形式＝デバイス形式のときだけ直接描画、それ以外はシャドウ）。
2. **frontends/brain を新規実装**。単一バッファ合成モデル:
   libnsfb プロッタ（ページ）とツールキット（クローム）が同じ
   XRGB8888 バッファへ描く。tk のピクセルパッキングと nsfb の形式が
   一致するため変換コピーはゼロ。ページ領域はカスタムウィジェット
   （pageview）が占有し、tk 側はその中身を塗らない（DESIGN §1.1）。
   - WM モード: シェル WM クライアントとして接続し、厳密交互の
     ダブルバッファに対して「バッファ別ダメージジャーナル」
     （そのバッファが最後に present されて以降の累積ダメージを
     ポインタキーで保持）で COMMIT 矩形を組み立てる。
   - 単独モード: brain サーフェス fbdev 直接（fake fbdev ファイルで
     描画を実証）。
3. **クローム**: タブ帯 40px + ツールバー 56px + 進捗 6px（読込中のみ）
   + ページ残り。ピル型 URL 欄、アイコンボタン 48×48（戻る/進む/
   再読込⇔停止/ホーム/メニュー ⋮）、タブは最大 2 枚（上限到達時は
   LRU 背景タブを破棄して空ける）、「+」は帯の右端固定。
   ステータスはページ左下のオーバーレイバブル（Chrome 式、常設バー
   なし）。進捗はコアに率 API が無いため不定進捗（throbber 連動）。
4. **メニュー/ダイアログ**: メニュー（新規タブ、ブックマーク追加⇔
   削除＝現在ページで切替、ブックマーク…、履歴…、ホーム、設定…、
   タブを閉じる、終了）、ブックマーク一覧（コア hotlist を列挙）、
   履歴一覧（urldb を列挙、直近 200 件上限）、設定（JavaScript /
   画像表示の即時反映）。
5. **brainreg 接続**（DESIGN §5）: 起動時に `browser.*` を nsoption へ
   流し込み、終了時に書き戻す。予算導出は M0 のコア側仕組みを維持
   （budget 56MB → llcache 実効上限 11,010,048B、画像キャッシュ
   3,670,016B、画像画素上限 1,835,008、JS ヒープ 4096KB）。
6. **セッション永続化**（DESIGN §6）: タブ構成とアクティブタブを
   `$HOME/.netsurf/brain-session.txt` へ tmp + rename の原子的書換え。
   配置は microSD 前提のホーム配下のみ、eMMC には触らない。
7. **OSK 連携の前端側配線**（DESIGN §3 の前端分）: WM モードでは
   イベント毎に `bd_wm_client_im_sync`、ページにキャレットがある間は
   `bd_wm_client_im_notify(active, caret 矩形)` でシェル OSK へ通知。
   単独モードでは URL 欄フォーカスで OSK ウィジェットを出す経路まで。
8. **開始ページ**: コアの resource: フェッチャはホワイトリスト制
   （welcome.html 等のみ）だったため、自前の日本語スタートページを
   `res/welcome.html` として同梱し、ホームの既定にした
   （オフライン既定、DESIGN §6）。

### 800×480 横画面のトレードオフ（明示）

- 採用構成: タブ帯 40 + ツールバー 56 = クローム **96px**、本文
  **384px（80%）**。進捗バー 6px は読込中のみで、その間だけ本文が縮む。
- 代替案との比較: (a) 電話式 1 行（56px）なら本文 424px だがタブ状態が
  隠れ、2 枚上限の本機では帯のコストが小さい。(b) 下部ツールバーは
  本文を侵さないが Shelf/OSK と競合。(c) タブ帯を畳む案は「戻る/進むの
  可否」と同じく一瞥性を落とす。
- WM モードではシェルの窓タイトルバー（実測約 32px）が更に上に乗る
  ため、実際の本文は約 352px になる。単独モードでは 384px を確保する。
  この差は WM 側の設計事項として明示しておく。

`browser-engine/test-harness/shot_brain.c`: 実物の `bd_wm_server` を

| # | シナリオ | 結果 | 子 PSS |
|---|---|---|---|

| 02 | 画像ページ（2400×1800 JPEG 等） | 画像が表示サイズで描画（DCT スケーリング経路） | 39,235 kB |
| 03 | 「+」で 2 タブ目 | 2 タブ + 開始ページ表示、アクティブ切替 | 41,182 kB |
| 04 | メニュー開 | 全 8 項目 + セパレータがページ上に表示 | 38,563 kB |

クローム + ページが描ける）。

### 予算実測

- 全シナリオで PSS **37.9〜41.2MB**、予算 56MB に対して 15MB 以上の
  余裕。2 タブ時が最大（41.2MB）。UI 追加で予算は超えていない。
- ただしホスト x86-64 の数値であり、ARM ゲストでの再測は統合
  フェーズの宿題（M0 の nsfb 実測と同じ条件で測り直す）。

### 撮影中に見つけて直した欠陥

1. 戻る/進むアイコンの向きが逆（生成スクリプトの flip 指定ミス）。
2. タブが帯全幅に伸び、「+」が画面外へ押し出された → タブ幅を
   タイトル実測 + 86px で 160〜300px にキャップ（Chrome のタブ幅
   キャップと同じ考え方）。
3. メニューの下半分が消える: present 順序（root 描画 → ページ再描画）
   でページ再描画がオーバーレイを上書きしていた →
   ページダメージがあったフレームではオーバーレイを最後に
   再描画する段を追加（`brain_overlays_invalidate` + 再 paint、
   対象はオーバーレイ矩形のみ）。
4. 開始ページが 404: コア resource: のホワイトリストに start.html が
   無い（§1-8 のとおり welcome.html 化で解決）。
5. libnsfb の brain サーフェスはコンストラクタ登録方式で、静的
   アーカイブからは参照がないとリンク落ちする →
   `-Wl,-u,brain_rtns` で強制リンク（Makefile に理由コメント付き）。

## 4. 原則への対応

- **コピー/オーバーヘッド削減**: ページとクロームは同一バッファへの
  直接描画（中間サーフェスなし）。present はダメージ矩形のみ。
  タブ帯は署名（タイトル列 + アクティブ印）が変わった時だけ再構築し、
  throbber 周期の再レイアウトを避ける。メニューは開く時だけ再構築。
- **キャッシュ/メモリ**: 予算導出は M0 の仕組みをそのまま使用し、
  フロント側で新たな無制限キャッシュは作っていない。ダイアログの
  一覧収集は 200 件で打ち切る。
- **実機の現実**: セッションは原子的書換え。開始ページはローカル
  同梱でオフライン表示可。期限は日数ベースを使っていない
  （ディスクキャッシュは M0 の容量駆動のまま）。

## 6. ツールキット側の不足（利用側からの記録）

1. `tk_button` は子ウィジェットをコンテナとして配置できない
   （タブ内「×」がボタン外に溢れた）。タブは [ボタン + ×] の
   横ボックスで回避。ボタン内包部品の公式パターンがあるとよい。
2. オーバーレイだけを再描画する公開 API がない。tk_root_paint_damage
   は damage 矩形をテーマ背景で埋めてから再描画するため、ページ
   合成と組み合わせる場合は本前端のような二段 present が必要。
3. ボタンのテキスト整列（左寄せ）API がない。タブタイトルは
   中央寄せのまま（ラベルには整列 API がある）。

## 7. ビルド再現メモ

- 通常: トップ Makefile から `make TARGET=brain`（TARGET 検証リスト
  と nsoption の `#elif defined(nsbrain)` 接続を追加済み）。
- このホスト固有の事情: VM 差し替えで libcurl/libjpeg/libwebp の

  /tmp が満杯だったため TMPDIR は `browser-engine/.tmp-build` へ
  向けた（使用後に削除済み）。
- repo へは push していない（従来どおり統合フェーズで判断）。

## 9. クローム再設計（2026-11-20、ユーザー評価「無理やりその大きさに詰めた感じの UI。見づらいし使いづらい」を受けて）

### 9.2 実物の表示規則（Web 調査、2026-11-20）

- **Chrome 定常表示**（Chromium 一次ソース `location_bar_model_impl.cc`
  の `GetURLForDisplay`）: https スキームを省略、www / m 等の trivial
  subdomain を省略、**http はスキームを残す**（加えて "Not secure"
  表示）、デスクトップでは file スキームも省略して File チップに置換。
  フォーカス/編集中は完全な URL に復元される。
- **Chrome 117（2023）**: 鍵アイコンを tune アイコンへ置換（HTTPS が
  既定になったため）。HTTP の insecure 明示は継続。
- **Samsung Internet**: アドレスバーは URL/検索の統合欄で、セキュリ
  ティ状態（鍵/サイト情報）を欄内に併記。

### 9.3 設計決定（この画面専用に組み直す）

1. **帯の統合**: タブ 1 枚のときタブ帯を出さない（本文 +48px）。帯は
   2 枚のときだけ出す。高さ 48px、タブは [タイトル flex][× 48×48]、
   幅はタイトル実測 +96 を 160〜300px に制限 → 2 枚 + 間隔の最大合計
   616px が帯幅 800px に必ず収まる（構造的に溢れない）。
2. **新規タブはツールバーの「+」**（48×48、常設）に移す。ホームボタン
   はツールバーから外しメニューに一本化（新規タブは開始ページを開く
   ので実質同等。メニュー「ホームを開く」は存置）。
3. **ツールバー**: 56px（48px ターゲット + 上下 4px）、ボタン間隔 8px、
   端インセット 4px に統一。[戻る][進む][再読込][URL flex][+][メニュー]。
4. **進捗**: インフローを廃止し、本文領域の上端に重ねる 3px ライン
   （見た目はツールバー直下）。レイアウトシフトなし。
5. **ステータス**: 常設を廃止。表示は「読み込み中」と「テキスト変化後
   2.5 秒」だけの一時表示（`brain_schedule` で自動消去。再スケジュール
   はテキストが変わったときだけ）。"Done" も 2.5 秒で消える。
6. **URL 表示（定常時）**: https = ホスト(+ポート)+パス（スキームと
   www を省略 = Chrome 定常形）、http = スキームを残す（テキスト欄に
   "Not secure" ラベルの置き場がないため、スキーム可視が注意喚起を
   兼ねる）、file = ファイル名のみ（Chrome の File チップ相当）、
   resource/about 等の内部ページ = ページタイトル。長い場合はクエリを
   落とし、パスの途中を "…" で省略（欄の実幅で文字幅を実測して収める）。
   **タップ/フォーカスで完全 URL に復元し全選択**（編集モード）、
   Enter 確定後は表示形に戻る。
7. **本文の可読性**: 既定倍率を **125%** にする（brainreg
   `browser.default_scale` の前端既定値として投入。brainreg で変更可）。
   本文 16px → 実寸 2.7mm、レイアウト幅は 800/1.25 = 640 CSS px。
   設定ダイアログに「文字の大きさ」（小 100% / 標準 125% / 大 150%）
   を追加し、全ウィンドウへ即時適用 + 既定として保存する。
8. **メニュー行高**: ツールキットのメニュー行をテーマ row_h（v2 で
   56px、リスト行用）から control_h（48px）に変更する。メニューは
   一時ポップアップでリスト行とは別物（Material のメニュー行 48dp と
   同じ）。8 項目 + 区切り = 393px となりクライアント高 428px に収まる。

### 10.2 見た目: 参照との差分点検（追加指摘 15:40 への対応）

参照 = Material You（M3）/ Chrome light theme / One UI の面構成。
撮影 15〜17・22 と並べて点検した結果:

- **面の階層**: タブ帯 = トーナル面（surface_alt #E6E0E9 の塗り）、
  ツールバー = 白サーフェス面、アクティブタブ = ツールバーと同色の
  白い塗り（帯の上で「ツールバーの層の一部」に見える）、
  非アクティブタブ = 帯の上にフラット（塗りなし）。Chrome の
  ライトテーマ（帯グレー/ツールバー白/アクティブタブ白）と同構成。
- **URL 欄**: トーナルな塗りのピル（輪郭線なし）= omnibox の定常形。
- **輪郭線ピルの排除**: 残っていた発生源を全て潰した —
  タブ（既定ボタン描画の 1px 輪郭）→ フラット化、
  ダイアログの「閉じる」「文字の大きさ」→ container 色の
  トーナル塗りボタン（M3 tonal button 相当、輪郭なし）。
  アイコンボタンはグリフのみ + 押下ウォッシュ（Chrome と同型）。
- **浮遊面**: メニュー/ダイアログ/ステータスバブルは白サーフェス +
  影 + 大きい角丸（ツールキットの backdrop が担保、撮影 17）。
- 残る差分（正直な申告）: アクティブタブは角丸 999 のピル形で、
  Chrome の「ツールバーに接続したタブ形状」ではない（ツールキット
  のボタン形状がピルのため）。層の読み分けはできているが、形状の
  完全一致はツールキット側のタブ形状対応が要る。設定ダイアログの
  チェックボックスは M3 準拠の輪郭ボックス（これは参照側も輪郭）。

### 10.3 アイコン: 公式 Material 形状への差し替え（追加指摘への対応）

従来の icons.h は PIL 手描きの自作グリフ（特に再読み込みの円弧と
矢印頭が標準形からずれていた）。**全 8 点を Google 公式 Material
Icons（filled、24px グリッド、Apache 2.0）の SVG から変換**に
