## 2. 読み取り境界（構造情報からのみ確定した値）

媒体は 8,589,934,592 バイト。MBR は標準形式で4パーティションを持つが、MBR の外にも ROM スロットと FAT ボリュームが存在するため、**§7.5 のハッシュ対象範囲は媒体全体（0 〜 8,589,934,592）と決定した**（境界漏れを防ぐ安全側の解釈。報告書への記録をもって確定手続きとする）。全体 SHA-256 はホストで約28秒/回と実測した。

| 位置（バイト） | 構造 | 同定 |
|---|---|---|
| 831,525,376 | MBR part0, type 0x0B, FAT32 | \Nand（MBR 上 p1） |
| 131,072 | MBR part1, type 0x53, 0.5 MiB | ブート領域 |
| 1,179,648 (LBA 2304) | MBR part2, type 0x10, 32 MiB, +0x40 に "ECEC" | ROM スロット0（nk XIP） |
| 306,191,872 | MBR part3, type 0x0E, FAT16 | \Nand3（MBR 上 p4。物理順と論理順が入れ替わっている） |
| 34,799,616 (0x2120000) | ROM スロット1 | スロット0と同一イメージ（151モジュール、完全バックアップ複製） |
| 0x4120000 | ROM スロット2 | 133モジュールの別イメージ、長さ 12,141,436 バイト |
| 82,845,184 (LBA 161,807) | 隙間 FAT16 A, 64 MiB | \Nand2 |
| 149,948,416 (LBA 292,868) | 隙間 FAT16 B, 149 MiB | \Nand4 |

- ROM スロット0 の ROMHDR は使用域末尾付近のオフセット **0x1C84524** にある。ECEC ブロック（+0x40 "ECEC"、+0x44 = ROMHDR の VA 0x81E84524、+0x48 = ファイルオフセット 0x1C84524）から直接引け、physfirst 0x80200000 / モジュール数 151 / ファイル数 51 と相互照合した。
- FAT32 終端（6,606,334,464）から媒体末尾までの約1.98 GB と各隙間は構造的に未同定。全体ハッシュに含めることで未同定領域の変化も検出対象にした。
- **正直な記録（訂正済みの失敗）**: 探索中、一時「ゲストとホストで読める内容が食い違う」と判断したが、真因は自分の10進変換ミスだった（隙間 FAT の正しいオフセットは 82,845,184 と 149,948,416。誤って 82,886,656 / LBA 292,864 を使っていた）。食い違いは存在しない。格子採取23点では全てゲスト読みとファイル内容がバイト一致（SAME）だった。

## 3. 読み取り専用マウント経路

- Brainux ゲストのカーネル（6.1.70）は eMMC を mmcblk0 として認識し、MBR の p1〜p4 を列挙できる。隙間ボリューム2つは loop デバイスにオフセット指定（82,845,184 / 149,948,416）で割り当てた。
- 4ボリューム全てを read-only マウントして同定した。ファイル数は QEMU 側センサスと完全一致（\Nand 8,726 / \Nand2 36 / \Nand3 3 / \Nand4 0）。\Nand3 ルートは "BOOK" のみ、\Nand4 は "TMEMO" ディレクトリ1つ。
- 抽出の二経路照合:
  - TextMemoTool `/アプリ/TextMemoTool/AppMain.exe`（5,632 バイト、md5 `ea264f553a130a383dbaf5e80f7b7605`）: ゲスト md5sum とホスト FAT パーサ抽出で一致。
  - Calc `/ToolsApp/Calc/AppMain.exe`（848,896 バイト、md5 `6b9ae42b741ffb84afa2829c5b7ad265`）: ゲストと mtools で一致。
- レイヤー側の経路は自前 FAT リーダ（`wince-layer/shim/fatvol.c`）で確立した: pread ベース、LFN を UTF-16 のまま照合（日本語パスが正確に解決する）、**書き込み経路は構造的に存在しない**。書き込みは常に SD 側オーバーレイへ行く（§7.3）。ボリューム指定は環境変数 `CE_VOLUMES="Nand=<src>@<offset>;..."`（ゲストではブロックデバイス名）。
- 制約（記録）: ゲストカーネルには nls_utf8 / nls_cp932 モジュールが無く、カーネルマウントでは日本語 LFN が '?' に化ける（ファイル自体は読める）。レイヤーの fatvol は UTF-16 を自前で扱うため、この制約はレイヤー経路には影響しない。

## 4. §7.5 非破壊証明の実施状況

解釈（安全側、本書に記録）: 証明対象イメージ自体は WinCE で起動しない（初回設定ウィザードが状態を変える前科があるため）。CE 側チェックリストは、証明対象とバイト同一の双子（s0-cecheck.img）で実施する。各サイクル = 証明対象の事前 SHA-256 → Brainux ゲストで snapshot=on アタッチしてレイヤー活動（マウント・読み出し・アプリ実行） → 事後 SHA-256 のバイト一致確認。チェックリストはサイクル1（ベースライン）とサイクル10（最終）で実施する計画とした。

実施済み:
- サイクル相当のフルゲストセッション **2回**（2026-11-23 の run-ce3 初回、同 24 日の再構築 QEMU での run-ce3 3回目）で、証明対象の SHA-256 が前後とも `2987f8e99f934ef82c41f4cd66399f57e3dfba4321e54f47b0d766c1a7cae64f` で一致した。セッション内容には M1/M2 回帰、ボリューム読み取り、DLL ホスト、収録アプリ起動が含まれる（詳細は REPORT-wince-m3.md）。
- pristine / ベースラインの md5 不変も全セッションで確認した。

**未完了（理由つき）**: 残り8サイクルと CE 側チェックリスト（ベースライン・最終とも）は未実施。理由は検証基盤の喪失: 2026-11-24 の環境一掃でカスタム QEMU（pw-aj2）のバイナリと QEMU 側プロジェクト成果物が削除された。ユーザーが GitHub へ push 済みだった qemu リポジトリ（brain ブランチ `306a3d899c`）から再構築して1セッションは実施できたが、その後ランタイムライブラリ（libslirp / libfdt / libfuse3 / liblzfse）がシステムから失われ、再々構築はクローン済みリポジトリに対するセキュリティ確認の対象となったため、ユーザーの判断待ちで停止している。チェックリスト用ドライバ（`image-work/int19/wcecheck/run-wcecheck.py`、boottest2.py の型、双子を snapshot=on で起動し時系列撮影する）とサイクルドライバ（`image-work/int19/guest-ce3/run-cycle.py`）は作成済みで、基盤が戻ればそのまま実行できる。
- §7.5-7 の設計項目（CE 領域の要所の部分ハッシュ照合による起動時自己確認、いわゆる ce-guard 相当）は本ラインでは未実装。残件として記録する。

## 5. コピー/オーバーヘッド削減

- 読み取り経路は pread のみで、ボリューム全体のコピーを作らない。FAT キャッシュは1セクタ分だけ（下記）。
- ゲストへのアタッチは snapshot=on（差分オーバーレイ）で、8.6 GB の作業コピーをサイクルごとに複製しない。証明用コピー2本（proof / cecheck）は初回に各1回だけ作成した。
- ROM モジュールは媒体から直接マップせず、スロット抽出（romA.bin、33,554,432 バイト）を1回だけ作って使い回した。

## 6. キャッシュ/メモリ管理

- fatvol のキャッシュは FAT 1セクタの固定バッファのみ（バイト予算 = 512〜4,096 バイト、追い出しは単純な無効化）。ディレクトリ走査は都度読みで、大きな索引を RAM に載せない。
- ハッシュ計算はチャンク逐次読み（ピーク RSS は小さい）で、8.6 GB をメモリに載せない。

## 7. 実機の現実への対応

- **eMMC ノータッチ原則**: Brainux 側からの書き込み経路は存在しない（fatvol は読み取り専用、書き込みは SD オーバーレイのみ）。証明対象への WinCE 起動も行わない（双子で代替）ことで、ウィザード起因の状態変化リスクを証明対象から排除した。
- 突然のリセット前提: 読み取り専用経路は状態を持たないため、電源断からの復旧処理が不要な設計になっている。オーバーレイ側の書込みは既存の原子的書換え方針に従う（M1 以来）。
- オフライン・時刻不信: ハッシュ照合は時刻に依存しない。証明の記録はファイル（results-*.txt）に残し、日数ベースの有効期限のような仕組みは使っていない。
