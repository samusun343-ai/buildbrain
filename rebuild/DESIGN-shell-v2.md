## 1. 共通原則A: オーバーヘッドとコピー回数の最小化

ユーザーの全作業共通原則（2026-11-20）: 「最適化・魔改造・統廃合の全てにおいて、オーバーヘッドとコピー回数を極力減らす。無駄な処理を極限まで減らす」。本設計への適用箇所:

| 対象 | 旧 braindesk | シェル v2 の方針 | M1 実装状態 |
|---|---|---|---|
| .desktop パース | そもそも列挙なし（ハードコード表） | 起動時に1回だけパースし結果を常駐カタログ化。起動・検索・再表示では再パースしない。以後の更新は mtime 無効化リフレッシュ（§7） | **実装済み**（no-reparse テスト＋refresh テストで検証） |
| 起動時 argv 構築 | — | パース済み Exec 文字列のトークン化のみ（1文字列分）。ファイル再読はしない | 実装済み |
| アイコンのデコード/スケール | アイコン描画は毎回ベクタ描画関数 | デコード＋スケールは (パス,サイズ) ごとに1回だけ行いキャッシュ（§8）。再描画はキャッシュ済みピクセルの blit のみ | **実装済み**（iconcache、テスト21件） |
| フレームバッファ転送 | 全画面フラッシュ前提 | ダメージベース提示を原則とする（§9）。全画面コピーはフルリサイズ時等の例外に限定 | ツールキット側に `tk_fb_flush_damage`＋キャンバスのダメージ蓄積が実装された（並行するツールキット M3）。シェル本体のメインループへの組み込みは統合フェーズ |
| WM の共有メモリ経路 | クライアントバッファ固定・最大化はスケール貼り付け（余分な変換） | クライアントの shm バッファをコンポジット時に直接読む。中間バッファへのコピーを作らない。変更通知はダメージ矩形で運ぶ（§5） | **M2 実装済み**（§15。test_wm 51件で実クライアント2プロセスを駆動して検証） |
| イベント処理 | ポーリング的再描画の作り | イベント駆動。再描画は状態変化時のみ。フレーム経路で malloc しない | シェル UI はイベント駆動で構築済み（ツールキット側の設計に従う） |
| 設定読み取り | — | reg は小さい INI の都度パース。読み頻度が低くキャッシュが効かないため**あえてキャッシュしない**（§2 の「効くものだけキャッシュ」原則） | 実装済み |

「コピーを減らす」と「機能を減らす」は別物である。上の表の削減は全て重複処理の除去であり、機能表（§6）は監査の物差しに対して削っていない。

## 2. 共通原則B: キャッシュとメモリ管理

ユーザーの追加原則（2026-11-20）: 「キャッシュの方法にも工夫をする（メモリ負荷・無駄処理・肥大化をなくす）。メモリ管理も工夫し、高速化も」。

### 2.1 キャッシュの規律

1. **全てのキャッシュはバイト予算と追い出し方針を必ず持つ。** 予算なしのキャッシュは作らない。
2. **効くものだけをキャッシュする。** デコード/スケール（高コスト・高再利用）はキャッシュする。reg の INI 読み（低コスト・低頻度）はキャッシュしない。
3. **コンポーネント間で重複させない。** アイコンのキャッシュはシェルが1つだけ所有し（`bd_shell_icon_cache`）、デスクトップ/ランチャー/タスク表示はそれを共有する。アプリ側が個別にデコードし直す経路は作らない。
4. **無効化は根拠ベース。** .desktop は mtime（秒＋ナノ秒）、アイコンは明示 invalidate（ファイル差し替え時にシェルが呼ぶ）。

| キャッシュ | 予算 | 追い出し | 無効化 | 実装 |
|---|---|---|---|---|
| アイコン（デコード＋スケール済みピクセル） | **2 MiB** | LRU。予算超の単体は transient 扱いで保持しない | 明示 invalidate（パス単位、全サイズ） | iconcache.c 実装済み |
| .desktop パース結果（カタログ） | **1 MiB**（推定バイト数） | 追い出しではなくトリミング: Comment→Keywords の順に非必須文字列だけを落とす。Name/Exec/Icon/Categories は決して落とさない（起動可能性と名前検索を守る） | mtime リフレッシュ | desktop.c 実装済み |
| フォントグリフ | ツールキット側の所管（DESIGN-toolkit-v2 参照） | — | — | シェルは関与しない |

### 2.2 シェル常駐予算（PSS 目標、800x480 前提）

シェルプロセス単体の PSS 目標を **10 MiB 以下** と置く。内訳（上限として管理する値）:

| 項目 | 上限 | 根拠・備考 |
|---|---|---|
| コード＋静的データ | 2.0 MiB | libbdshell＋libbrainui2 静的リンク想定 |
| ツールキット構造（ウィジェットツリー等） | 1.5 MiB | グリフキャッシュはツールキット側予算に含む |
| メモリキャンバス（800x480 RGBA） | 1.46 MiB | 800×480×4B。提示先が fbdev でもこの1枚は必要 |
| 壁紙（スケール済み） | 1.46 MiB | キャッシュ内に保持。**現状は ImageView が複製を持つため実質2枚分（2.9 MiB）** — §8 の残課題として明記。M1 では予算表にこの実態を入れて合計を計算する |
| アイコンキャッシュ | 2.0 MiB | §2.1 の予算で保証 |
| .desktop カタログ | 1.0 MiB | §2.1 の予算で保証（fixtures 10件実測では数十KiB級） |
| スタック/ヒープ断片マージン | 0.6 MiB | §2.3 の方針で断片を抑える前提の余裕 |
| **合計** | **約 10.0 MiB** | 壁紙の二重保持を解消できれば約 8.6 MiB |

セッション全体の予算は §4 の X 共存測定で確定する（ここでは置かない。測っていない数字を置くことは監査 §6 違反になる）。目安として旧実測だけを記す: 素の X＋JWM セッション PSS 約45–50MiB、braindesk 系セッション（run 19）約12.8MiB。

### 2.3 断片化対策（プール/アリーナ方針）

- **長命と短命を分ける。** カタログ・アイコンキャッシュ・ウィジェットツリーは長命で、確保/解放のペアが明確。フレーム描画経路では新規 malloc をしない（既存バッファへの描画のみ）。
- **カタログのエントリ配列は単一の realloc 成長配列**（連続配置、削除は memmove）。文字列は現状個別 malloc だが、次段で**世代アリーナ**化する: load/refresh の世代ごとに文字列一式を1ブロックに確保し、世代交代時に丸ごと解放する（個別 free をなくし、断片化と解放漏れの両方を消す）。M1 では計画として明記し、未実施を隠さない。
- **アイコンキャッシュは「1エントリ＝ピクセル1確保」**。表示サイズが固定値の集合（グリッド48px 等）しかないためサイズクラスが少なく、解放ブロックの再利用率が高い。LRU 追い出しはエントリ単位で丸ごと解放する。
- **プールが有効な場所だけプールにする。** イベントオブジェクト等の高頻度小物はツールキット側の所管。シェル側で新たな汎用アロケータは作らない（それ自体がオーバーヘッドになる）。

## 3. セッション構成

```
systemd
 └─ greeter (braingreeter 後継; 照合核は旧 greeter.c から部品取り)
     └─ ユーザーセッション
         ├─ bd-shell (本設計: WM + シェル + ランチャー)
         ├─ ネイティブアプリ (libbrainui2 クライアント, §5 プロトコル)
         └─ [X 共存が選ばれた場合] X サーバ + 既存 X アプリ (§4)
```

- グリーターはログイン後に終了する使い捨てプロセス（常駐予算に入れない）。
- シェルはセッションの親としてアプリの起動（§7 の exec 抽象）と終了検知を持つ。
- 既定セッション化（setup_brainux.sh の変更、systemd unit）は統合フェーズの作業であり、M1 の範囲外。M1 のシェルはホストのメモリキャンバスで動作検証する段階。

## 4. X 互換の関門

絶対条件「既存アプリが無変更で動く」に対して、fbdev ネイティブ化だけでは既存 X アプリ（pcmanfm、lxterminal、netsurf-gtk、GTK アプリ）が動かない。監査 §0-6 の通り、旧構成で互換を満たしていたのは並存する X＋JWM セッションだった。選択肢:

| 案 | 内容 | 互換 | コスト（未測定は未測定と書く） |
|---|---|---|---|
| A. X セッション併存（現状維持） | ログイン時に「Brainux (X)」と「braindesk」を選ぶ | 完全（従来セッションそのまま） | DE としての一体感なし。常駐はどちらか一方のみ |
| B. シェル配下で X サーバを動かす | bd-shell が X サーバ（Xorg/Xephyr 類）を子プロセスとして起動し、X ウィンドウを WM のクライアントとして合成 | 完全を目指す（ルートレス相当の統合が要実装） | X サーバ分の PSS が常駐に乗る。統合の実装量が最大 |
| C. DE 自体を X 上に作る | シェルを X クライアントとして実装し、WM は X の WM が担う | 完全 | fbdev 経路の軽さを捨てる。ツールキット v2 の fbdev バックエンドが無駄になる |
| D. fbdev 専用（互換を捨てる） | 監査で否定済み。**採らない** | 不成立 | — |

**決定は測定後に回す。** M1 では方針決定に必要な測定計画までを置く:

測定計画（bdtest ハーネス＋SD イメージで実施）:
1. 構成ごとのセッション合計 PSS: (a) X＋JWM のみ（既存実測の再確認）、(b) bd-shell のみ、(c) bd-shell＋X サーバ（何も開かない状態）、(d) (c)＋代表 X アプリ3本（pcmanfm / lxterminal / netsurf-gtk）起動状態。
2. 起動時間: グリーター表示→シェル操作可能まで、(c) では X アプリ初回起動まで。
3. 入力遅延の目視確認: X アプリ上でのキー入力・スクロール（パネル実操作）。
4. 判定基準: 128MiB のうち OS＋セッション常駐が **64MiB を超える構成は不採用**（アプリ実行用に半分を残す）。(c)(d) がこの線を超えるなら案 A（併存）を正式化し、B の統合は行わない。
5. 測定は run 単位で記録し、数字なしに B/C を選ばない。

## 5. WM の窓モデル（設計。クライアント接続は M2 以降）

旧 bui_wm の欠陥（最大8窓・リサイズ不可・固定バッファ）への回答:

- **窓数**: 固定上限を持たない。実効上限はメモリ（クライアントバッファの shm 合計）で決まる。シェル側のタスクモデル（M1 実装済み）は BD_TASK_MAX=16 を管理上限として持ち、これは表示・切替の都合であり WM の窓数制限ではない（超えた分はタスク一覧に畳む）。
- **リサイズ可**: クライアントは新しいサイズでバッファを張り替え、WM に GEOM で通知する。WM は旧バッファを新バッファ提示まで保持し、ちらつきを避ける。最大化は「スケール貼り付け」ではなく実ジオメトリ変更（旧実装の欠陥の明示的な否定）。
- **状態**: 通常 / 最大化 / 最小化（タスクへ格納）/ 全画面。移動はタイトルバー掴み（単一指前提で掴み領域を広く取る: 装飾高さ 32px 以上、リサイズハンドルは隅の 24px 四方）。
- **フォーカス**: クリック（タップ）で付与する単純モデル。新規窓が前面。フォーカスなし窓へのキー配送はしない。
- **プロトコル**: 旧プロトコル（HELLO/GEOM/COMMIT/EVENT/CLOSE、Unix ソケット＋共有メモリ）の輸送方式を継承し、次を変える:
  - COMMIT に**ダメージ矩形リスト**を必須化（全画面再合成を常態化しない）。
  - 合成はクライアント shm を**直接読む**。中間コピーを作らない（原則A）。不透明窓はそのまま、半透明窓のみブレンド。
  - バッファ所有権: クライアントが2枚持ち（ダブルバッファ）、COMMIT 済みバッファは WM が解放通知（RELEASE）を返すまで再利用しない。
- M1 のシェル内タスクモデル（追加/切替/クローズ、アクティブタスク表示）はこの WM のシェル側受け皿であり、実クライアントの窓ではない。混同しないこと。

## 7. .desktop 列挙とランチャーモデル

仕様: freedesktop Desktop Entry Specification 1.5 に基づく（desktop.h の冒頭コメントが実装範囲の正本）。

- パース対象キー: Type / Name（ロケール解決: 完全ロケール→言語→無印）/ GenericName / Comment / Keywords / Icon / Exec / TryExec / Terminal / Hidden / NoDisplay / Categories。
- Hidden=true は「削除」として扱い、低優先ディレクトリの同 id をマスクする。NoDisplay は一覧から外すが id 検索では見える。Type≠Application は入れない。Exec 無しは「起動不可」として保持する（壊れたインストールを黙って隠さない）。
- ディレクトリ優先順位: load した順に id を主張し、先勝ち。
- カテゴリ: freedesktop メインカテゴリへ寄せ、追加カテゴリは公式対応表の部分集合でメインへ写像（WebBrowser→Network、FileManager→System 等）。
- Exec 展開: 引用符とエスケープを処理し、フィールドコードは %c（名前）/%k（パス）/%i（--icon アイコン）/%% を展開、%f %F %u %U と廃止コードは落とす（M1 はファイル/URL を渡さない）。
- 検索: Name/GenericName/Comment/Keywords/Categories への大小無区別部分一致。結果は名前順。
- **パースは1回だけ**（原則A）。`de_catalog_refresh()` は mtime（秒＋ナノ秒）が変わったファイルだけを再パースし、追加/削除/Hidden 化を反映する。テストで「mtime を完全復元した内容変更は再パースされない」ことまで検証している（＝再パースしていないことの直接証拠）。
- ピン留め/最近使用: reg の `shell` セクションに `pinned` / `recent`（';' 区切り id 列）として永続化。最近使用は新しい順、上限10件、重複は先頭へ移動。失効は件数ベースのみ（日数ベースの期限は使わない、§12.2）。
- 起動は exec コールバック抽象（`ln_exec_fn`）経由。本番実装 `ln_exec_real` は fork+execvp＋setsid。テストはモックで argv と記録条件（成功時のみ最近使用へ記録）を検証する。

## 8. アイコン経路

- 形式解決とアイコンの実描画（テーマ探索、ファイル名→パスの解決）は統合フェーズ。M1 は「デコード済みピクセルをいかに無駄なく回すか」を iconcache で固める: キー (パス, 幅, 高さ)、値=キャンバス形式そのままの RGBA（変換なしで ImageView/blit に渡せる）、予算2MiB、LRU、統計（hit/miss/evict）取得可能。
- 既知の残コピー: ツールキットの ImageView は set_pixels でピクセルを複製する。壁紙では「キャッシュ内スケール済み 1.46MiB＋ウィジェット内複製 1.46MiB」の二重保持になる（§2.2 で予算に算入済み）。解消案はツールキット側に「外部バッファ参照モード（所有権を移さない）」を足すことで、M2 のツールキット課題として記録する。黙って「ゼロコピー」とは書かない。

## 9. 描画・提示経路

- シェルはメモリキャンバスへ描画し、提示はバックエンド（ホスト検証: メモリのみ／実機: tk_fb）が行う。
- 原則は**ダメージベース提示**: 変わった矩形だけを RGB565 変換して fb へ送る。全画面転送（800x480 で約0.75MiB/回の変換＋書き込み）を毎フレーム行う設計にはしない。
- 現状の制約（正直に残す）: ツールキット v2 の tk_fb_flush は全画面変換・転送のみで、キャンバス側にダメージ蓄積 API が無い。必要なツールキット側追加: (1) キャンバスのダメージ矩形蓄積と取得/クリア、(2) tk_fb_flush_region。シェル側のメインループはこの API が入った時点でダメージ駆動に切り替える。M1 のシェルはイベント駆動で再描画自体を最小化しており、定常ポーリング描画はしていない。

## 10. brainreg 連携

## 12. 実機の現実（設計制約）

ユーザーの追加制約（2026-11-20）。机上の前提（電源は安定、ネットはある、時刻は正しい、記憶域は自分だけのもの）を設計に持ち込まない。

### 12.1 実機はちょくちょくリセットする — 永続化は原子的方式

前提: 書き込みの途中で電源が落ちる/リセットされることは通常事象である。

- **reg の書込みは tmp→fsync→rename→ディレクトリ fsync**（reg.c 実装済み）。途中終了で残るのは旧ファイルか新ファイルのどちらか一方だけで、壊れた中間状態は現れない。書き損じの `.tmp` が残っても読み手は `*.conf` しか見ないため無害。
- **起動時の検証と回復**: reg の読みは行単位で寛容（壊れた行は読み飛ばし、型付き getter は呼び出し側の既定値へフォールバック）。つまり検証は「読む時に壊れていれば既定値として扱う」方式で、壊れたストアがシェル全体を起動不能にすることはない。次の正規の書込みがファイルを丸ごと作り直すため、回復は自動で起きる（test_durability で検証: 破損ファイル→既定値フォールバック→再書込みで正常化、残留 tmp の無視）。
- **ピン留め/最近使用の id は読み込み時にサニタイズ**する: basename 形状でない id（'/' を含む、".."、空、過長）と重複は破損として捨てる。壊れた永続データは「少なくなる」方向にだけ劣化し、変な起動には化けない。
- **キャッシュは失われても壊れない**: アイコンキャッシュとカタログはメモリ上のみで、再起動で消えることが前提（再構築は load/refresh で完結する）。ディスクにキャッシュを置かないため、キャッシュの破損という故障モード自体が存在しない。
- シェル設定の値域検証は読み手側でも行う（volume は 0–100 にクランプ、panel_position は top/bottom 以外を既定扱い、wallpaper はパース不能なら既定色）。永続値が範囲外でも表示が壊れない。

### 12.2 ネットはデフォルトで繋がらない、時刻も信用できない

- **日数ベースの期限を一切使わない。** 最近使用は件数上限（10件）のみで消える。カタログやアイコンのキャッシュにも時間ベースの失効はない。オフラインが既定であり、オンライン前提の処理（更新チェック、時刻同期待ち等）はシェルの起動経路に置かない。
- mtime の使用は「同一ファイルの変更検知（前回見た値と等しいか）」に限る。絶対時刻としての意味は使わないため、時計がずれていても無効化判定は正しく働く（等値比較は時計の正しさに依存しない）。
- 時計表示は「表示しているだけ」で、シェルのいかなる判定（期限、順序、有効性）にも使わない。最近使用の順序は実時刻ではなく記録順（シーケンス）で決まる。

### 12.3 WinCE と Brainux の併用が前提 — SD とデバイスは共有

前提: SD とデバイスは WinCE と共有する。Brainux の占有を前提にした設計は壊れる温床になる。

- **シェルの書込み先は Brainux 側のユーザー設定領域（~/.config/brainreg.d）のみ。** SD 上の領域、WinCE 側のファイル、.desktop ファイル自体には一切書き込まない。カタログは読み取り専用、アイコンキャッシュはメモリ上のみ（§12.1）。WinCE 側のファイルを壊す経路はシェルには存在しない。
- **SD が WinCE 側で使われた/抜かれた状態から起動しても壊れない**: applications ディレクトリが無い・空・中身が総入れ替え、のいずれでもカタログは「その状態のカタログ」として成立する（load は0件でも正常、refresh は消失を「全件削除」として反映、シェルは空カタログでも生成・描画できる — test_vanishing_dir と test_shell の空カタログケースで検証）。
- **起動後に SD が抜かれた場合**: refresh でエントリは消える。消えたアプリを起動しようとした場合は exec の失敗として検知される（`ln_exec_real` は CLOEXEC パイプで exec 自体の失敗を返すため、fork 成功＝起動成功とは扱わない）。失敗した起動は最近使用にもタスクにも記録されない — 「あるはずのものが無い」ことが履歴を汚染しない。
- **長時間タスクの中断耐性**: シェル側の永続化は1書込みごとに完結する原子的更新の積み重ねであり、「長時間かけて書く」状態を持たない。途中で切れても次回起動は §12.1 の回復で通常状態に戻る。

### 18.3 Exec フィールドコードの仕様照合（追加項目: %f/%F/%u/%U 実装）

アプリ群第1波からの引き継ぎ（bd-files がファイルを渡して開く正規手段が無い）への対応として、`de_exec_argv_files()` を新設し、ランチャに `ln_launch_files()` を追加した。`de_exec_argv()` は「ファイル/URL を渡さない」形として従来どおり使える。

| コード | 仕様上の意味 | 実装 |
|---|---|---|
| %f | 単一ファイル | 実装: 先頭のファイルを現在のトークン内へ置換。リストが空なら除去 |
| %F | ファイルのリスト | 実装: ファイルごとに独立した引数へ展開。空なら除去 |
| %u | 単一 URL | 実装: %f の URL 版 |
| %U | URL のリスト | 実装: %F の URL 版 |
| %c | 名前（翻訳済み） | 実装（M1 から）: トークン内へ置換 |
| %k | .desktop ファイルの場所 | 実装（M1 から）: トークン内へ置換 |
| %i | アイコン | 実装（M1 から）: `--icon <Icon>` の独立引数対。Icon が無ければ除去 |
| %% | リテラル % | 実装（M1 から） |
| %d %D %n %N %v %m | 廃止コード | 除去（仕様どおり） |
| 未知のコード | — | 除去 |
| 引用符内のコード | 展開しない | 展開しない（M1 からの挙動、仕様どおり） |

- 仕様上の注意: 準拠した .desktop ではファイルコード（%f/%F/%u/%U）は Exec 全体で最大1つまで。本実装は複数現れた場合も各出現を同じリストで展開する（寛容な解釈）。
- テスト: test_desktop に追加（%u 置換、%F の複数展開と空リストでの除去、%U の複数展開、`--file=%f` のトークン内置換、引用符内がリテラルのまま残ること）。
- フォローアップ: apps 側 `bdmime` の「Exec 展開後にパスを末尾引数として追加する」回避策は、正規経路（`de_exec_argv_files` / `ln_launch_files`）へ移行可能になった。移行自体はアプリラインの作業とする。
