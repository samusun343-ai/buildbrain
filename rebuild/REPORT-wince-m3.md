## 1. 対象の選定と根拠

- **収録アプリ: TextMemoTool**（\Nand\アプリ\TextMemoTool\AppMain.exe、5,632 バイト、md5 `ea264f553a130a383dbaf5e80f7b7605`）。import が coredll のみに閉じ、序数25件のみ、ダイアログ主体の単機能アプリで、M0 分類から到達可能と判断した。
- 電卓（Calc）は第一候補だったが SharpLib.dll 依存のため **M4 領域**と確認し、M3 対象から外した（根拠: import 解析。SharpLib は coredll 239件＋ole32 6件を import する）。
- **原本 DLL: commctrl.dll**（設計 §9.2 の第一候補。import は coredll のみ、輸出77件）。加えて小さなユーティリティ系の **edwgsp.dll**（ベース 0x41AA0000、輸出3件の幾何ユーティリティ、coredll のみ import）を、ROM ホスト機構そのものの実証に使った。

## 2. 実装した内容（シム実装累計 208 → 381 シンボル）

- **モジュールシステム**（`loader/modules.c` 新設）: ファイル PE のロード（希望ベース→任意アドレス＋再配置）、ROM モジュールのネイティブベースへのマップ（衝突時は失敗を正直に返す）、import 束縛（転送輸出の追跡つき）、DllMain の依存順実行、TLS コールバック。
  - ROMHDR の位置は ECEC ブロックから引く方式にした（S0 で確定した値を使用）。
  - **E32 エントリ欄の形式がモジュールにより異なる**ことを実測した: Microsoft 製スロット DLL（commctrl）は VA 形式、サードパーティ製（edwgsp）は RVA 形式。ローダは両形式を受けるよう実装した。
  - qemu-user（ホスト検証環境）では [0x40000000, 0x41000000) が予約済みで commctrl（ベース 0x40120000）をマップできないことを最小テストで実測した。commctrl の実証は実ゲストで行う設計とし、ホストでは edwgsp（0x41AA0000）で代替した。
- **FS ブリッジ v1**（S0 の fatvol と統合）: CreateFileW 等をホスト fd / ボリュームカーソルの vfile 抽象で統一。読み取りはボリューム、書き込みはオーバーレイ。OPEN_ALWAYS 読み取りでボリュームファイルが空のオーバーレイに隠れる hazard を修正した。
- **ダイアログ管理＋組込みコントロール**（`shim/dialog.c`）: DLGTEMPLATE/EX のパース（EX の項目オフセットは実測で訂正）、ダイアログ単位変換、モーダルループ、Button/Edit/Static の各コントロール、RegisterHotKey、keybd_event。
- **commctrl ホストのためのバッチ**: DSA/DPA 動的配列、ImageList の中核（生成・追加・マスク付き追加・描画。ドラッグ系はスタブのまま）、インメモリレジストリ、ロケール/NLS（ja-JP 既定、数値・日付書式、CP932 は iconv 経由）、ミューテックス、ファイルマッピング、GDI 追加（LoadBitmapW の DIB 変換、DrawEdge、DrawFrameControl、GradientFill、クリップ演算ほか）、ウィンドウ追加（プロパティ、アトム、スクロール状態、メニューのデータ側ほか）、「機能が存在しない」ことが正しい答えになる集合（IME なし、空クリップボード、ジェスチャなし等は文書化した上でそのセマンティクスを実装）。
- **__GetUserKData**: ゼロ初期化した1ページを返す実装を追加した（DllMain で NULL を逆参照する疑いへの対処。下記のとおり**ゲスト未検証**）。

## 3. ホスト検証（qemu-arm ユーザーモード）の結果

- M1 回帰（tools/run-host.sh）PASS、M2 GUI 回帰（tools/run-host-gui.sh）PASS、M3（tools/run-host-m3.sh）PASS。
- cemodtest.exe（8項目）の結果: volread / voljp（日本語パス）/ volfind / overlay / **loadlib（edwgsp.dll の ROM ホスト、DllMain 完走、輸出3件解決）** / thread / dialog が OK。process のみ FAIL だが、原因はホストカーネルに ARM バイナリの binfmt が無く子ローダを exec できないこと（errno=8 ENOEXEC をログで確認済み）で、**ホスト環境のアーティファクト**と記録した（ゲストではネイティブ exec になる）。
- cectrltest.exe はホストでは commctrl=SKIP-VA（設計どおり。ゲストが本命）。
- 証明イメージの SHA-256 はホスト M3 実行の前後でも不変だった。

## 4. ゲスト検証（実イメージ＋QEMU ゲスト）の結果

実施セッション: run-ce3 初回（2026-11-23、従来 QEMU、ローダ md5 `32b166c7…`）と run-ce3 3回目（2026-11-24、再構築 QEMU、ローダ md5 `dd5bd7fa…`）。証拠は `image-work/int19/guest-ce3/results-ce3*.txt` と `run-ce3*.out`、撮影は同 `shots/`。

- **M1 回帰・M2 GUI 回帰: 両セッションとも PASS**（終了コード0、スタブ呼び出し0、結果ファイル md5 一致、GHOLD 撮影のシーン検査も通過）。
- **commctrl.dll**: ゲストでネイティブベース 0x40120000 へのマップに成功し、import 318件中 293件を実装へ束縛（スタブ25件）した上で、**DllMain 内で segfault した**（初回セッション）。そのセッションでは fault 位置の記録を有効化していなかったため、落ちた箇所は特定できていない。呼び出し側の消去法では、NULL を返すスタブを DLL がポインタとして逆参照する経路（筆頭は __GetUserKData）が疑わしく、§2 の対処を入れたが、**対処後のゲスト再検証は未実施**（§6 の基盤事情）。したがって commctrl のホスト動作は「マップと束縛まで確認、DllMain 完走は未確認」と記録する。
  - 残りスタブ25件の内訳: 名前つき16件（ImageList のドラッグ系・CopyDitherImage・ReplaceIcon、DrawIconEx、ジェスチャ系、SetWindowPosOnRotate、GetOwnerProcess、GetClipCursor 等。このうち GetOwnerProcess / GetClipCursor / ジェスチャ系 / SetWindowPosOnRotate / __GetUserKData は対処実装済み・未検証）と、序数のみで名前が coredll の輸出表にも無い8件（DSA/DPA ファミリの範囲内。名前を推測で束縛することはしなかった）。
- **TextMemoTool**: ゲストで起動し、25秒以上の常駐を確認（VmRSS 11,040 kB、PSS 4,352 kB、スタブ呼び出し0）。**ただし撮影2枚ともデスクトップしか映らず、アプリのダイアログ窓は画面で確認できなかった**。プロセスは生きており落ちてもいないため、「起動・常駐は確認、窓の表示は未確認」と記録する。原因（アプリ側の待ちか、ダイアログ配置の問題か）は未特定で、再検証が必要。
- cemodtest のゲスト実行は、初回はドライバ側の不備（シェルの `;` 分割で CE_VOLUMES が切れた、ブロックデバイスの権限）で、3回目は rootfs 内ファイルモード（660）で実行ファイルが開けず、いずれもテスト側の問題で中断した。修正（環境変数の引用、chmod、ファイルモード 755 化）はドライバと rootfs に反映済みだが、**修正後のゲスト再実行は未実施**。
- 資源実測（ゲスト）: ceguitest GHOLD 時 VmRSS 3,200 kB / PSS 約670 kB（M2 時点と同水準）。TextMemoTool は上記のとおり。ローダ単体の常駐は M1 時点で 608 kB（過去記録）。

## 5. コピー/オーバーヘッド削減

- ROM モジュールは媒体イメージからの直接マップ（ファイルへ展開しない）。ボリューム内 DLL の LoadLibrary と子プロセスの対象だけは、一時ファイルへ抽出してから読む（PE ローダがファイル前提のため。抽出先は fs ルート内の隠しファイルで、用途は起動時のみ）。
- import 束縛は起動時に一括で解決し、実行時の名前解決コストを持たない。
- DSA/DPA・ImageList 等のデータ構造は呼び出し側の所有で確保し、レイヤー側に大きな常駐状態を持たない。レジストリはプロセス内ツリーのみ（永続化しない）。

## 6. キャッシュ/メモリ管理

- fatvol の FAT キャッシュは1セクタ固定（S0 のとおり）。ImageList のストリップは必要数まで段階的に拡張し、上限は呼び出し側の追加回数にのみ依存する。
- ゲスト実測のメモリ増分: TextMemoTool 常駐時 VmRSS 11,040 kB（ローダ＋シム＋アプリイメージ込み）。128 MB 予算に対する単体アプリの実測値として記録する（M4 以降の大型アプリでは再測が必要）。

## 7. 実機の現実への対応

- ストレージは S0 の規律をそのまま適用（読み取りは eMMC ボリューム、書き込みは SD オーバーレイ、eMMC へは書かない）。M3 の全ゲストセッションで証明イメージの SHA-256 と pristine / ベースラインの md5 が不変だったことは S0 報告書に記録した。
- レジストリはインメモリのため、突然のリセットで壊れる永続状態を持たない（永続化は M5 の検討事項）。
- 時刻不信: GetLocalTime 等はホスト時刻をそのまま返すだけで、有効期限のような時刻依存の判定は入れていない。
