## 2. ダメージ転送の定量評価（実測）

`tests/bench_damage.c`（`make bench` で再実行可能）を追加し、Brain パネル形状 480×272・16bpp のメモリフレームバッファで `tk_fb_flush_damage()` の転送バイト数を実測した。全画面転送は 261,120 B。

| シナリオ | 転送バイト数 | 全画面比 | 削減率 |
|---|---:|---:|---:|
| 初期フレーム（全画面） | 261,120 B | 100.0% | — |
| 時計の秒更新（ラベル1個のテキスト変更、3回平均） | 19,488 B | 7.5% | 92.5% |
| 時計の分ロールオーバー（2桁変化） | 19,488 B | 7.5% | 92.5% |
| テキスト入力 1文字（ASCII / かな共通） | 33,408 B | 12.8% | 87.2% |
| スイッチ切替（test_tk3 と同条件） | 37,440 B | 14.3% | 85.7% |
| スクロール +40px（固定ヘッダ付きリスト） | 240,960 B | 92.3% | **7.7%** |
| スクロール +1ページ（同上） | 240,960 B | 92.3% | **7.7%** |

正直な読み取り:

- 小さい変更（時計・1文字入力・トグル）は転送量が対象ウィジェットの矩形まで落ち、85〜93% 削減できる。
- ダメージの粒度はウィジェット矩形単位であり、変更したグリフ単位ではない（秒更新と分ロールオーバーが同バイト数）。
- **スクロールはほぼ効かない**。スクロール量に関わらずビューポート全体が再転送され、削減できるのは固定ヘッダ分（7.7%）だけ。フレームバッファの blit/シフトによる最適化は未実装であり、残項目として記録する。
- 描画側も同様で、`tk_root_paint_damage()` はダメージ外ウィジェットも走査はする（キャンバス書き込みはクリップで捨てる）。tk.h のコメントに明記済みの既知の制限。

## 3. フォントサブセットのカバー率（実測）

同梱フォント `fonts/brainui-jp-subset.ttf`（1,282,032 B、cmap 5,354 コードポイント、Noto Sans CJK JP Regular のサブセット、OFL 1.1、内部名は "BrainUI JP" に改名）について、出荷済みファイルの cmap を IME 辞書 BIDF v3（`libbrainime/data/brainux3.bid3`）の表記集合と突き合わせて実測した。表記集合は v3 の構築入力から再構成した（本体 = BIDF v2 トークン列を `gen_sidecar.Bidf2` で読み出し、SUPP = `libbrainime/m3work/supp.tsv`）。

| 対象 | コードポイント | エントリ完全カバー |
|---|---:|---:|
| BIDF v3 本体（180,000 件） | 4,561 / 4,561 = **100.00%** | 180,000 / 180,000 = **100.00%** |
| BIDF v3 SUPP（35,112 件、NEologd/Sudachi 由来） | 1,119 / 1,121 = **99.82%** | 35,110 / 35,112 = **99.99%** |
| BIDF v3 合計（215,112 件） | 4,561 / 4,563 = **99.96%** | 215,110 / 215,112 |

- 欠けているのは **U+591B（夛）と U+5F0C（弌）** の2コードポイントのみで、影響は SUPP の2エントリ。
- 原因: サブセット構築（`fonts/build_subset.py`）の入力は words-mozc.tsv ＋評価コーパスで、IME M3 で追加された SUPP 語彙を含んでいない。SUPP が 99.8% 被っているのは基本レンジと本体漢字との偶然の重なりによる。
- 対処方針（記録のみ、本締めでは未実施）: `build_subset.py` の入力に supp.tsv を加えて再生成すればこの2字は閉じる。再生成は決定的で低コストだが、出荷物の差し替えになるため別作業とする。

## 4. SDK 検証の総括

- `make sdk-check` **通過**。手順は「`make install` でステージング → インストール済みヘッダと共有ライブラリだけを pkg-config 経由で参照して `examples/sdk_settings.c`（239行）をビルド → 実行」であり、サンプルは `tk.h` / `textcore.h` の公開 API のみで書かれている（内部ヘッダ `tk_internal.h` の参照なし、リンクは `libbrainui2.so`）。
- サンプルの実行結果: 初期フレーム 261,120 B 転送、スイッチ切替 37,440 B（14.3%）、編集可能 ComboBox へのタイピングで「カスタム」選択 -1、SpinButton へのタイピングで 42、ツールチップ表示まで到達し `SDK-OK` を出力。
- 共有ライブラリ形態: `libbrainui2.so.1.0`（1,243,168 B）＋ soname `libbrainui2.so.1` ＋ `libbrainui2.so` のシンボリックリンク、`libbrainui2.pc`、`install` ターゲット（ヘッダ・ライブラリ・同梱フォントを配置）。

### 発見された API の不足・引っかかり（記録）

1. **プログラムmatic なセッタが invalidate しない**。`tk_label_set_text` / `tk_textfield_set_text` / `tk_scrollview_scroll_to` はダメージを登録しないため、アプリ側が `tk_widget_invalidate()` を明示的に呼ばないと再描画されず転送も 0 B になる（§2 のベンチ初版で実際に踏んだ。タイマー駆動の時計や `tk_scrollview_tick()` の慣性スクロールが該当する）。tk.h のダメージ節に「明示的な invalidation がダメージを蓄積する」と書かれてはいるが、大手ツールキットはセッタ側で invalidate するのが普通であり、踏みやすい。セッタ側での自動 invalidate 化を推奨として記録する（本締めでは挙動を変えていない）。
2. **`tk_font_load_bundled()` の探索先頭が cwd 相対**（`fonts/brainui-jp-subset.ttf`）。ツリー外の作業ディレクトリからテストバイナリを実行するとフォントが見つからず NULL になる（§6 の ASan 実行で実際に踏んだ）。インストール後は `/usr/local/share/fonts/...` で解決するが、開発時は `BRAINUI_FONT_PATH` かツリールートでの実行が必要。

## 5. TextField パスワードマスク（追加必須項目）

シェル M2 からの引き継ぎブロッカー（グリーター v2 のパスワードが平文表示になる）への対応として、TextField にパスワードマスク表示モードを実装した。

- **API**: `tk_textfield_set_password(w, bool)` / `tk_textfield_is_password(w)`（`include/tk.h`）。状態はウィジェットの `password` フラグ（`tk_internal.h`）。
- **方式**: 表示だけの変換。バッファは平文を保持し `tk_textfield_text()` は平文を返す。描画時にコードポイント1つにつきマスクグリフ **●（U+25CF）** を1つ描くため、文字数とキャレット/選択の位置関係が平文時と一致する。文字数が見えるのはマスク入力欄の標準仕様として許容する。
- **composition の整合**: IME のプリエディットもマスクする。`draw_composition()` に mask 引数を追加し、文節のバイト長を「文節内コードポイント数 × 3バイト」に書き換えてから描くため、文節下線（アクティブ文節の2px アクセント／非アクティブの1px）と候補閲覧時の選択背景がマスクグリフの位置とずれない。TextView 側の呼び出しは mask=false で従来どおり。
- **ヒットテストの整合**: ポインタ DOWN のキャレット配置は、平文時は実グリフ幅で測る `tk_offset_at_x`、パスワード時は全文字の advance をマスクグリフ幅に置き換えた `masked_offset_at_x`（同じ最近傍ロジック）で測り、実文字列のバイトオフセットに写像する。Shift+クリックの選択拡張も同じ経路。
- **プレースホルダはマスクしない**（入力ではないため。空欄時に「パスワード」等の案内文が見えるのが正しい）。
- **テスト**: test_tk3 に21件追加（§6）。ピクセル比較で「同文字数の異なる秘密文が同一描画になる」「平文描画とは異なる」「composition 入りでも内容が隠れ、下線位置がマスク位置と一致する」ことを、同梱フォントを install した実グリフ描画で検証した。ヒットテストは「あいう」（3文字9バイト）でマスク境界クリック → バイトオフセット 6、Shift+クリックで選択 (0,6)、右端で 9、タイピングで実文字が追記されることを検証。
- **残る考慮事項（記録）**: (1) クリップボードのコピー/カットは平文を扱う現行仕様のまま（表示マスクの範囲外として今回は変更していない。グリーター統合時にポリシー判断が必要）。(2) グリーター v2 側で `tk_textfield_set_password` を呼ぶ配線はシェル M2 側の作業として残る（API は本節で提供済み）。

## 7. 原則への対応

- **コピー/オーバーヘッド削減**: ダメージ転送で「変わっていない画素は変換も転送もしない」を §2 で定量確認した。パスワードマスクは描画時のみの変換で、バッファの複製や永続コピーは作らない（マスク文字列は paint 中のスタック上に最大で実文字列の3倍、TextField のバッファ上限 1024 B に対して 3,075 B まで）。
- **キャッシュ/メモリ管理**: M3 締め範囲で新規キャッシュは追加していない。グリフキャッシュは M2 の上限付き（フォント毎 1024 グリフ、リング追い出し）のまま。
- **実機の現実**: パスワードマスクは表示層のみで永続化に関与しない。同梱フォントは SD 上の Brainux 領域に置かれる前提で、eMMC への書き込み経路は M3 の範囲に存在しない。時刻依存の処理はツールチップの 800ms 遅延のみで、これは単調時計（アプリループ供給）であり日数・有効期限の類ではない。
