### 格上げセルの根拠（2件）

新規 tests/test_tk18.c（10 checks、全 PASS）が
検証基盤。詳細は AUDIT §17.1。

- WinUI #16 Chip D ○ → ◐: WinUI に第一者の Chip は
  無く、実装は ToggleButton 形に追随する。その
  背景ブラシ遷移（83ms、ToggleButton
  themeresources が一次ソース）はチップ自身の
  描画経路でも有効だが未検証だった。tk18 で
  未選択（ControlFill）→ 選択（accent）の遷移に
  ついて、変化時点の無跳躍・中間値・settled 形の
  無クロック参照との一致・復帰側の遷移を画素
  検証した。
- WinUI #33 Segmented D ○ → ◐: WinUI に第一者の
  Segmented は無く、選択チェックの出現は選択
  グリフ遷移に追随する。tk16 は Android ペア
  （200ms）のみ検証していたため、tk18 で WinUI
  ペア（167ms / decelerate）の中間状態と完了
  フレームの settled 一致を検証した。
- いずれも第一者部品が存在しないため、部品自体の
  同等は主張できず上限は ◐。WinUI #18（Card）は
  遷移自体が実装に無いため ○ のまま（§17.1）。

### 発見・修正した不整合（sdk-check のドリフト）

総括の一環で `make sdk-check`（make check の
対象外だった SDK 検証）を実行し、3件の FAIL を
発見した。切り分け（デバッグ複製で実測）の結論:
**ライブラリの欠陥ではなく、サンプル側の前提が
M7 の寸法変更（control_h 48 → 56px）以降
ドリフトしていた**（AUDIT §17.4）。
- Switch のダメージ転送 56,160B（行 rect +
  2px インフレート）が 272px 高ステージの
  21.5% となり「< 1/5」前提を割った。ライブ
  ラリの挙動（転送はトグル行のみ・1 rect）は
  正しい。
- ステージ高不足でボタン行が root の外
  （中心 y=288 > 272）に落ち、ダイアログが
  開かなかった。境界を尊重するヒットテストは
  正しい。
修正: サンプルのステージ高を 272 → 360 に変更
（examples/sdk_settings.c、理由と数値をコメント
に明記）。Switch 行は全体の 16.2% に戻り、
ダイアログフローも通る。再発防止として
sdk-check を Makefile の check ターゲットに
組み込んだ。ライブラリ本体の変更はしていない。
この不整合が M7〜M18 の「消費者回帰ゼロ」
（3スイート確認）の範囲外にあったことも記録
する。

### アプリ再開への準備状態

- **ビルド**: `make all` で libbrainui2.a /
  libbrainui2.so.1.0（+ .so / .so.1 リンク）が
  生成されることを確認。`make install` の
  ステージング配置（ヘッダ・ライブラリ・
  pkg-config・フォント）も sdk-check の過程で
  毎回検証される。
- **公開 API**: 公開ヘッダは include/tk.h、
  include/textcore.h、include/tk_kbd.h、
  include/osk.h の4本。消費者（apps / shell /
  osk）と SDK サンプルはこの公開面のみで
  ビルドされる（apps/Makefile の SDK 規律）。
  なお .so の動的シンボル（794件）には内部
  関数も含まれており、visibility による公開面の
  絞り込みは行われていない（現状の記録として
  明記する。アプリ再開の支障にはならない）。
- **消費者**: 現行ライブラリで アプリ 1,048 /
  シェル 683 / OSK 319 が無修正で全 PASS。
  SDK サンプル（examples/sdk_settings.c）も
  公開 API のみで設定画面を構成・実行でき、
  sdk-check は make check に組み込み済み。
- 以上から、アプリ作り直しを現行ライブラリの
  上で再開する前提（ライブラリのビルド・公開
  API・消費者の健全性）は本弾の実行で確認
  できた。ライブラリ側の残件は上記の判断待ち
  11件 + Slider 提案と終端 35件であり、いずれも
  アプリ実装をブロックする性質のものではない
  （判断待ちは寸法の適応認定、終端は参照不在・
  形の相違・基盤制約によるもの）。

### コピー/オーバーヘッド削減

- 本弾はライブラリ本体（src/）を変更していない
  ため、描画・転送経路へのコピー追加はない。
- 追加した test_tk18 は既存スイートと同じ
  「キャンバスを都度確保・解放」方式で、常駐
  コストはない。make check への sdk-check
  組み込みは実行時間を約1秒延ばす（ステージング
  install + サンプル実行）。

### キャッシュ/メモリ管理

- ライブラリ側に新規キャッシュ・静的バッファを
  追加していない。tk18 の ASan/UBSan 実行で
  メモリエラー・UB なし、直接リーク 0 を確認
  （間接リークはテストハーネスのラッパツリー
  由来で既存スイートと同形）。

### 実機の現実への対応

- 永続化・時刻依存・リセット耐性に関わる変更は
  ない。sdk サンプルの修正は文書化済みの実寸
  （187ppi・control_h 56px）に消費者側の前提を
  合わせたもので、実機の寸法規則そのものは
  変更していない。
- 終端理由のうち #21 の scale 成分は、実機の
  基盤契約（即時描画・ダメージベース転送・
  静止時転送ゼロ）を守るための制約として
  確定記録した（§16.5）。

### 未検証の明記

- 本弾の検証は全てホスト上のヘッドレス描画と
  measure 実測による。SD イメージ + QEMU
  ゲストでの実操作・実画面の目視照合は統合

- .so の動的シンボルに内部関数が含まれる件は

  （version script 等）は本弾では行っていない。
