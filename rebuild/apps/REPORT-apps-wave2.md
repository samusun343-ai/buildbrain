## フォローアップ対応: bdmime のファイル受け渡しを正規経路へ移行（2026-11-20）

### 背景

第1波レポート §5-1 の API 不足: シェルの `de_exec_argv` が Exec の `%f/%F/%u/%U` を捨てるため、
`apps/common/bdmime` は「Exec 展開後にファイルパスを末尾引数として追加」する回避策で
ファイルを開いていた。シェル側に `de_exec_argv_files`（フィールドコード展開）と
`ln_launch_files`（ランチャー側ラッパ）が実装されたため、正規経路へ移行した。

### 移行内容

| 対象 | 変更 |
|---|---|
| `common/bdmime.c` | `bd_mime_argv` の内部を `de_exec_argv` + 末尾追加から `de_exec_argv_files(e, &path, 1, NULL, 0)` へ置換。回避策のコード（argv 配列の組み替え・strdup 追加）は全削除 |
| `common/bdmime.c/.h` | 複数ファイル版 `bd_mime_argv_files(cat, paths, n)` を新設（ハンドラは先頭パスの拡張子で決定、`%F` が全パスに展開）。ヘッダ冒頭の「ギャップ」記述を新セマンティクスに書き換え |
| `files/tests/test_files.c` | M 節を新セマンティクスで検証し直し、ケース追加（下記）。フィクスチャのカタログ登録数は 1→3 件に |

### 新セマンティクス（移行に伴う振る舞いの変化）

- `%f` は **Exec 行内の位置にそのまま置換**される（末尾とは限らない）。`Exec=bd-notes --open %f` なら argv は `[bd-notes, --open, <path>]`。
- `%F` はファイルごとに 1 引数へ展開される（複数ファイルを開く正規手段ができた）。
- **Exec にフィールドコードが無いハンドラにはパスが渡らなくなった**（freedesktop 本来の意味論で、シェル自身の `ln_launch_files` と同一）。回避策時代は無条件に末尾追加されていたため、コード無し Exec に依存していたハンドラは「ファイルなしで起動する」動作に変わる。ツリー内のハンドラは全て `%f` 宣言済み（bd-notes / bd-files / bd-tasks の .desktop を実測確認）で影響なし。新規ハンドラは Exec に `%f`/`%F` を書くことが必須 — 第2波の bd-player は複数ファイル対応として `%F` で出すこと。
- URL（`%u/%U`）は bdmime の対象外のまま（bdmime はファイル専用。URL を開く経路はブラウザ側の仕事で、必要になった時点で `de_exec_argv_files` の urls 引数を使う）。

### あえて移行しなかったもの

- **bd-files の起動実行部**（`files_app_open_selected` の exec hook / `default_launch`）は `ln_launch_files` へ移行していない。理由: `ln_launch_files` はシェルのランチャーの責務（起動をシェルの「最近使った項目」へ記録する）を含むラッパであり、ファイルマネージャはランチャーではない。bd-files がシェルの recents を書くのは二重管理になる。bd-files は従来どおり `bd_mime_argv`（中身は正規経路に移行済み）+ 自前の exec hook（テスト差し替えの継ぎ目）を使う。シェルからアプリを起動する経路はシェル側が `ln_launch_files` を使えばよく、パス受け渡しの展開規則は両者で同一になった。

**電源断耐性（端末の現実への対応、本アプリの核）**: 録音は追記式で
約1秒分の音声ごとに fflush+fsync。ヘッダのサイズ欄は停止時に初めて
確定するが、`rc_wav_info` はデータチャンク位置+ファイル長から長さを
導出するため、**未ファイナライズ（電源断相当）でも一覧表示と再生が
正しい長さで可能**。`rc_wav_repair` がヘッダを実ファイル長で書き直す。
テストでは「録音→abandon（電源断シミュレーション）→一覧に正しい長さで
出現→修復→ヘッダ正常」を実証。削除の追い出しは**容量（バイト予算、
既定 64MiB）+削除連番の古い順**で、日数ベースの期限は使わない。

**ゲスト実証の注記**: QEMU ゲスト側の録音は仮想化側の既知の問題
（キャプチャが FIFO overrun → EIO で即死、MEMORY.md の RECORDING-TEST
参照）があるため、アプリの正しさはホスト/モック（シンセソース+null
シンク+実 WAV 検証）で証明し、ゲスト実証は統合フェーズに残す。

### 7. 設定アプリ / 管理系

設定アプリ（参照調査 §9 のレイアウト: 左サイドバー+上部検索+右詳細
ペインを踏襲）:

- ページは実在する 7 つ: キーボード / 画面 / サウンド / Wi-Fi / 電源 /
  日付と時刻 / 端末情報。**端末に存在しないカテゴリ（Bluetooth・印刷・
  ゲーム等）を飾りで並べることはしない**（「なんちゃって」回避の判断。
  §9 の「カテゴリ名を参照どおりに」との緊張はここに記録する）。
- **正本は brainreg と bd_backend で、シェルのクイック設定と同一の
  経路を使う**（二重管理なし）: 輝度/音量は bd_backend（テストはモックで
  書込み回数まで検証）、キーボードは kbdsettings ブリッジ（リピート
  プリセット/遅延/間隔/長押し）、スリープは reg `power` 節、日時は
  bd-clock が読む `datetime/local_offset_min` を編集（30分刻みにスナップ）。
  システム時刻そのものの設定は特権が必要なため OS 統合事項として明記。
- Wi-Fi は bd_wifi 経由（状態/SSID/IP、スキャン、PSK 欄（マスク付き）
  からの接続、切断）。スプリカント不在時は情報行+失敗で graceful。
- 端末情報は sysmodel 経由（uname、rootfs バージョン、メモリ、
  マウント別ストレージ）。

管理系（bd-admin）: プロセス（一覧は /proc の stat を comm 内の
空白・括弧に耐えるパースで読み、PID/名前/RSS/CPU ソート、SIGTERM/
SIGKILL を実子プロセスで UI テスト済み）、ストレージ（/proc/mounts +
statvfs）、メモリ（meminfo）、ログ（末尾有界読み=定数メモリ、行境界
から開始、部分文字列フィルタ）。

`.desktop` は `apps/desktop/` に 6 件（player は `Exec=bd-player %F`
+ 音楽 MimeType 群）。セッションへの配置は OS 統合フェーズ。

### 10. 恒常原則への対応（各節の要約）

- **コピー/オーバーヘッド削減**: プレイヤーはポンプ式（スレッドなし、
  tick あたり上限フレーム数）でデコードし、走査キャッシュは
  (mtime, size) 不変なら再プローブしない（テストで probe 回数を固定）。
  レコーダのトリムとピーク算出はストリーミングで定数メモリ。管理系の
  ログ読みは末尾有界。設定は行を都度読み直し、設定値の私的コピーを
  持たない。
- **キャッシュ/メモリ管理**: プレイヤーのメタデータキャッシュは
  **バイト予算（既定 4MiB）+ 最終スキャン順の追い出し**を持ち、テストで
  1バイト予算→全追い出し→復帰を検証。電卓の履歴は件数キャップ 200。
  レコーダの最近削除はバイト予算+削除連番。無制限に育つキャッシュは
  第2波に存在しない。
- **実機の現実**: 永続化は全て bdstore の原子的書換え（履歴・レート・
  meta・プレイリスト・再生状態・brainreg）。時刻ベースの有効期限は
  どこにも使っていない（追い出しは容量・件数・使用実績のみ）。
  書込み先は Brainux 領域（アプリのデータディレクトリと SD 前提の
  カタログ）のみで、eMMC には触れない。録音は電源断を通常事象として
  設計し、テストで再現した（§5）。
