### 棚卸し（現行 textcore/フォント処理の実態、実コードで確認）

- 整形・計測・描画は全て `src/tk_font.c` に集約され、**stb_truetype のみ**で
  実装されている。他の src/*.c は stbtt を使わない（tk_draw.c の言及は
  コメントのみ）。textcore.c（編集コア）は計測を一切行わず tk 側の
  tk_text_* に委ねるため、本件の変更範囲は tk_font.c 内部に閉じる。
- フォント読み込み: ファイル全体を自前でメモリに読み（所有）、
  stbtt_fontinfo が参照する。フォールバックはチェーン方式で、
  コードポイントごとに `resolve()` が担当フォントを決める。
- 計測（tk_text_width_px）: コードポイント単位ループ。advance は hmtx を
  グリフごとに整数 px へ丸めて合算。カーニングは stbtt_GetGlyphKernAdvance
  （'kern' テーブルのみ、同一フォント内）だけ。
- 描画（tk_canvas_draw_text_px）: 同じくコードポイント単位。グリフ
  キャッシュは (glyph, px) キー、**1024 エントリ/フォントの件数上限＋
  リング追い出し**（ビットマップ実バイトは w*h）。
- 欠落（比較レポート §3 の自己申告どおり）: 合字なし（"fi" は2グリフで
  描かれる）、GPOS カーニングなし、結合文字はフォント側 advance 頼みで
  クラスタ概念なし、bidi なし、改行は禁則（JIS X 4051 サブセット）のみ。
- tk_text_cp_width / tk_font_cp_advance は単一コードポイントの文脈なし
  計測（パスワードマスク幅、折り返しの per-cp 幅、OSK 等が使用）。

### プローブ実測（実装方式の確定、/tmp の使い捨てプログラムで実施）

HarfBuzz（hb_face_create をファイル blob から生成 + hb_font_set_scale
(px*64)）の実挙動:

- DejaVu Sans 16px: "fi" → **1グリフ**（合字 gid 5042）、"ffi" → 1グリフ。
  "AV" → A の advance が単独 701 → 636（26.6 単位）= **GPOS カーニング
  −1.02px** が効く。e + U+0301 → 合成済み é の1グリフ。
- Noto Sans CJK TTC 16px: face_index での取り出しがそのまま動く。
  全角 advance は 1024（= 16.00px ちょうど）で、現行の EM 規約
  （px = EM サイズ）と一致。か + U+3099 → 1グリフ・advance 全角
  （クラスタとして正しく処理される）。"fi" 合字あり（gid 58975）。
- **同梱サブセットフォント**: "fi" は2グリフのまま、"AV" のカーニングも
  無し — サブセット化（pyftsubset）で GSUB 合字/GPOS が落とされている。
  ライブラリ側が整形を持つようになっても、同梱フォント自体は恩恵を
  受けない（日本語本文には無関係）。フォント再生成時に
  --layout-features を残すことが申し送り事項（本弾の範囲外）。
- FreeType と stb の計測一致: ascender/descender/height（行高 =
  asc − desc + gap と一致）、hmtx advance、NO_HINTING ラスタライズの
  ビットマップ寸法・オフセット（'A' 11x12・off(0,−12) 等）が全て一致。
  → ラスタライザを FreeType に替えても形状・寸法の退行なし。

### 設計判断（実施前に確定）

1. **置換範囲**: tk_font.c 内部のみ。公開 API（include/tk.h の宣言）は
   変更しない。ロードは FT_New_Memory_Face、整形は hb_face_create
   （同一の自前所有バッファを参照 = フォントデータのコピーは増えない）。
2. **整形**: コードポイントごとの担当フォント解決（従来の resolve()）で
   アイテム化し、同一フォントの連続区間を hb_shape する。hb_font は
   (フォント, px) ごとに作り小さな配列にキャッシュ（上限 8、リング）。
   スケールは px*64（26.6 固定小数点 px）。方向は LTR を明示する
   （判断 4 と対）。
3. **描画**: ペンは 26.6 固定小数点で累積し、グリフごとに丸めて配置
   （累積誤差なし）。ビットマップは従来のグリフキャッシュに
   FreeType ラスタライズで供給する。**ヒンティングは無効**
   （FT_LOAD_NO_HINTING）: 従来 stb と同一形状を保ち、本弾の変更を
   「整形の正しさ」だけに限定する。ヒンティングの可否は実機の
   小サイズ可読性で別途評価する申し送り。
4. **bidi（FriBidi 109 KiB）は入れない**。根拠: (1) 同梱フォント群に
   RTL スクリプト（ヘブライ/アラビア）のグリフが無く、並べ替えても
   .notdef になるだけで実益がない。(2) 表示要件は日本語＋ラテン文字で、
   混植は英数字・記号列（弱い方向性のみ。論理順 = 表示順で正しい）。
   (3) アイテム化の継ぎ目（区間単位整形）ができるため、将来 RTL
   フォントと同時に入れる場合は FriBidi で論理順→視覚順の区間分割を
   足す追加実装で済む。HarfBuzz 側は区間内整形を担う。
5. **UAX#14 は全面実装しない**。現行の禁則（JIS X 4051 サブセット）が
   対象コンテンツ（日本語＋ラテン文字）の改行要件を担う。本弾では
   代わりに**クラスタ原子性**を折り返しに加える（合字・結合文字の
   途中で行を割らない）。UAX#14 の全ペア規則は多言語フォントを持た
   ない現状では大半が検証不能で、必要になった時点で禁則表の拡張と
   して足せる。
6. **整形結果のキャッシュは置かない**（方針として明記）。整形は
   描画・計測呼び出し内の一時処理で、結果は再利用する scratch
   バッファに置き、保持もコピーもしない。保持キャッシュは従来の
   グリフビットマップのみで、既存の予算枠（1024 件リング）のまま。
   整形コストはベンチで裏付ける（§検証）。
7. **計測の丸め是正**: tk_text_width_px は従来グリフごとに整数 px へ
   丸めて合算していた（1グリフあたり最大 +0.5px の累積誤差）。
   整形合計（26.6）を最後に1回だけ丸める方式に改める。これは意図
   した是正であり、ラテン文字主体の文字列幅が従来より最大で数 px
   小さくなる場合がある（CJK 全角は不変）。テストのピンが動く場合は
   理由として本項を引く。
8. **改行コードの幅**: 従来 tk_text_width_px は '\n' に .notdef の
   advance を数えていた（実質バグ）。整形では改行はグリフを生ま
   ないため幅 0 になる。これも是正として記録する。
9. **リンク形態**: 利用側（shell / apps / osk）は ../libbrainui2.a を
   静的リンクし -lm のみを付けている。tk_font.o が hb/FT を参照する
   ようになると、利用側のリンク行に -lharfbuzz -lfreetype の追加が
   要る（コード変更ではなくリンクフラグ）。本弾では利用側を編集
   しないため、ビルド確認で失敗の内訳（未定義参照が hb/FT のみか）
   を切り分け、追加で通ることを手作業リンクで実証し、申し送りと
   して記録する。.pc には Requires.private / Libs.private を正しく
   付ける（SDK 経路はこれで解決する）。

### 実施（tk_font.c の backend 差し替え）

- `src/tk_font.c` を全面差し替え（公開 API・同梱フォント探索・禁則表は
  無変更）。ロード = FT_New_Memory_Face（face_index=-1 のプローブで
  face 数を取得し従来どおりクランプ）、整形 = hb_face_create を同一
  バッファから生成し hb_font は (フォント, px) ごとに最大 8 個を
  リングキャッシュ。アイテム化は従来の resolve() で行い、同一
  フォントの連続区間を hb_shape（方向は LTR 明示、script は推測）。
- 描画は 26.6 固定小数点ペンで累積しグリフごとに丸めて配置。
  ラスタライズは FreeType（FT_LOAD_NO_HINTING | NO_AUTOHINT、
  FT_RENDER_MODE_NORMAL）で従来のグリフキャッシュ（(gid, px) キー、
  1024 件リング）に供給。yoff は hb の y-up を符号反転して適用。
- 折り返しは全文を1回整形し、クラスタ先頭のコードポイントに
  クラスタ advance を集約。**クラスタ内部の境界では折らない**
  （last_break の候補を cluster_start の位置に限定）。禁則規則と
  ハード改行の扱いは従来どおり。
- Makefile: pkg-config で harfbuzz/freetype2 の cflags/libs を取得
  （無い環境向けに Debian 配置へのフォールバック付き）。全テストと
  .so のリンクに追加。.pc に Requires.private / Libs.private を追加。
  tk.h は backend 名のコメントのみ更新（宣言は無変更）。
- 新規テスト `tests/test_shape.c`（整形テスト 22 件）を追加し
  `make check` に組み込み。内容: 合字（ffi の幅関係＋「fi」の
  1回描画 vs 2回描画のピクセル差 32px、旧 backend では差 0）、
  GPOS カーニング（AV が A+V より狭い）、結合文字（e+U+0301 が
  合成済み é と同幅・ダクテン付き仮名が基底グリフの advance 内に
  収まる）、混植のアイテム化（全体幅 ≒ 部分の和、両スクリプトの
  描画）、折り返しのクラスタ原子性（"fifififi" が合字境界でのみ
  折れる）。

### 実測（取り込み前後の差分）

ライブラリ単体の負荷可能領域（.text+.rodata+.data.rel.ro+.data）:

| 条件 | 変更前 | 変更後 | 差分 |
|---|---|---|---|
| ホスト x86-64 .so | 383,267 B | 336,563 B | **−46,704 B (−12.2%)** |
| ARM EABI5 .so（gcc-14 -mcpu=arm926ej-s、同一条件で新旧ビルド） | 380,792 B | 330,852 B | **−49,940 B (−13.1%)** |

- stb_truetype の実装コード（約 47〜50KB）がライブラリから消え、
  整形・ラスタライズは rootfs 既存の共有ライブラリ
  （libharfbuzz.so.0 = 1,378,772 B、libfreetype.so.6 = 722,404 B、
  他コンポーネントと共有される file-backed ページ）に移った。
  .so の DT_NEEDED に両者が入ることを readelf で確認。
- RSS（比較レポート §5 の方式）: qemu-arm-static + 対象 rootfs で
  測定用サンプル（同梱フォントを読み 854×480 キャンバスに日英
  混植3行を描画）を新旧 .so で実行。**ピーク RSS は両者とも
  15.3 MiB で、差は測定限界（0.1 MiB）以下**。同じサンプルの
  合計幅は 437 → 434（混植行の合字・カーニング・丸め是正分）。
  グリフキャッシュ件数は両者 33 で同一。
- ホスト native の test_font ピーク RSS は 22.0 → 25.3 MiB
  （+3.3 MiB）。これは hb/FT の .so マッピングと内部表を含む
  ホストプロセスの値で、実機では file-backed な共有ページが
  主体になる（上記 qemu 実測で差が出なかったことと整合）。
- 描画性能（ホスト bench_paint、同一条件）: テキストページ
  全面描画 0.576 → 0.469 ms/frame、ラベル1個のダメージ描画
  0.060 → 0.043 ms、一覧画面 0.693 → 0.627 ms。整形導入で
  遅くなった経路は無い（per-cp の線形キャッシュ走査が消えた分
  むしろ速い）。ARM 実機での絶対値は統合フェーズで測る。

### 利用側ビルド確認（shell / apps / osk、コード変更なし）

- 3者とも**コンパイルは全て通過**し、失敗はリンク時の
  hb_*/FT_* 未定義参照のみ（apps では 32 件全て tk_font.c 由来、
  shell / osk も同型）。公開 API の破壊は無い。
- 実証: shell の test_shell は、失敗したリンクコマンドそのままに
  `-lharfbuzz -lfreetype` を足すとリンク成功し **126 passed**。
  apps の test_files_ui も同様に成功し **48 PASS / 0 FAIL**。
- **申し送り（各ラインの Makefile 担当者向け）**: shell/Makefile、
  apps/Makefile、osk/Makefile の libbrainui2.a をリンクする行に
  `-lharfbuzz -lfreetype`（または pkg-config --libs harfbuzz
  freetype2）の追加が必要。ソース変更は一切不要。SDK 経由
  （.pc）の利用者は Requires.private で自動的に解決する。
  本ラインでは他ラインのファイルを編集しないため、適用は
  各ライン側の作業になる。

## 総括

- テキスト整形は HarfBuzz、フォントのロード/計測/ラスタライズは
  FreeType に移行し、合字・GPOS カーニング・結合クラスタが
  正しく処理されるようになった。公開 API は無変更、既存テスト
  のピンは無変更で全通過した。
- 最終状態: `make check` **22 スイート 3,734 件全通過 + SDK-OK**
  （開始時 3,712 件 → test_shape 22 件を追加）。
- ライブラリ単体は ARM 実測で −49,940 B（−13.1%）。整形の実費は
  rootfs 既存の共有ライブラリ（HarfBuzz 1,346 KiB + FreeType
  705 KiB、file-backed で他と共有）に移り、qemu-arm 実測の
  ピーク RSS に差は出なかった。
- 残件・申し送り:
  1. 利用側3ライン（shell / apps / osk）の Makefile への
     `-lharfbuzz -lfreetype` 追加（上記「利用側ビルド確認」節）。
     これが入るまで各ラインの `make check` はリンクで止まる。
  2. 同梱サブセットフォントの再生成時に pyftsubset の
     --layout-features を残すこと（現行サブセットは GSUB/GPOS が
     落ちており、合字・カーニングの恩恵はシステムフォント側
     でのみ出る。日本語本文は無影響）。
  3. ヒンティングの評価（本弾は NO_HINTING で従来形状を維持。
     小サイズの可読性は実機で別途評価する）。
  4. FriBidi / UAX#14 全面対応は、RTL グリフを持つフォントを
     入れる判断とセットで再検討する（本弾の判断根拠は
     「設計判断」節 4・5）。
  5. ARM 実機での整形性能・描画の最終確認は統合フェーズ。
