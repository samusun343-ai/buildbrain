## 1. 旧設計の何を繰り返さないか

旧 bui.h の根本的な誤りは「ウィジェット＝描画関数（void 戻り、状態なし、イベントなし、ヒットテストはアプリ側の手書き座標計算）」だった。v2 は以下を設計の出発点として固定する。

1. **保持モード（retained mode）のウィジェットツリー**。ウィジェットは状態を持つオブジェクトであり、生成・破棄・親子関係・可視/有効状態をライブラリが管理する。即時モード（Nuklear/ImGui 式）は採らない。理由: 128MB・単一コアでも保持モードの方が再描画コストをダメージベースに限定でき、フォーカスや IME composition のような持続状態と相性が良い（GTK/LVGL と同じ判断）。
2. **2パスレイアウト**（measure → arrange）を全ウィジェットに強制する。絶対座標の手置きは TKFixed コンテナの中だけに隔離する。
3. **イベントはライブラリが配送する**。ヒットテスト、ポインタキャプチャ、バブリング、フォーカスはツールキットの責務であり、アプリはコールバックを受けるだけ。
4. **テキスト編集は共有コア（textcore）に一本化**する。TextField/TextView は textcore のクライアントであり、アプリ毎に編集ロジックを再実装しない。
5. **ライブラリとして配布可能な形**にする: 公開ヘッダは `include/` に分離、静的/共有ライブラリをビルドし、`make install`（prefix 配下へのヘッダ＋lib＋pkg-config 風 .pc）を持つ（M1 では Makefile の install ターゲットまで。実イメージへの SDK 導入は次マイルストーン）。

## 2. アーキテクチャ層構成

```
アプリ
  │  tk.h（公開 API: ウィジェット/レイアウト/イベント/テーマ）
ウィジェット層   tk_widgets.c   Label/Button/.../ListView
コア層           tk_core.c      ツリー、2パスレイアウト、イベント配送、フォーカス、ダメージディスパッチ
テキスト編集     textcore.c     バッファ＋カーソル/選択/Undo/クリップボード/行レイアウト橋渡し
描画層           tk_draw.c      メモリキャンバス（RGBA8888）、クリップ、基本図形、テキスト計測IF
バックエンド     tk_fb.c        fbdev（RGB565 変換、ダブルバッファ的フラッシュ）※旧 bui_fb の設計を参考に新規実装
                 tk_evdev.c     evdev → tk_event 変換（キーボード/抵抗膜タッチ）※旧 bui_input の設計を参考に新規実装
                 tk_alsa.c      （後段）ALSA 直接 ioctl の音量IF ※旧 bui_alsa の設計を参考に新規実装予定、M1 未着手
```

バックエンドは差し替え可能にし、ホストではメモリキャンバス＋合成イベントで全コアをテストする。実機経路（fbdev/evdev）は同じ tk_event / tk_canvas 抽象を通る。

## 3. ウィジェット体系

「動作実装」するものと、体系として定義のみ（後段で実装）するものを分ける。最低ラインは LVGL の 30+ 種・GTK の約70クラス（監査§2）であり、下表の全種を体系の正規メンバーとする。「無い」のではなく「未実装」と明記するのが本書の約束である。

| ウィジェット | 役割 | 状態（M2 終了時点） |
|---|---|---|
| Label | 静的テキスト表示、折り返し計測 | **実装済み** |
| Button | 押下可能なラベルボタン、clicked 通知 | **実装済み** |
| CheckBox | 二値トグル、changed 通知 | **実装済み** |
| Radio | グループ内単一選択（group_id で兄弟と連携） | **実装済み** |
| Switch | CheckBox のスライダ型表現（CheckBox と状態モデル共有） | **実装済み（M2）** |
| Slider | 連続値（float 0..1／範囲指定）、ドラッグ＋キー操作 | **実装済み** |
| ProgressBar | 決定型進捗表示 | **実装済み（M2）** |
| TextField | 1行テキスト編集（textcore 使用、IME composition 受け口） | **実装済み** |
| TextView | 複数行テキスト編集（textcore＋行レイアウト） | **実装済み（M2）**: 折り返し（禁則付き）・スクロール・編集可能/読取専用の両モード。ドラッグ選択は未実装 |

| Separator | 区切り線（レイアウト参加） | **実装済み（M2）** |
| ImageView | 画像表示（stb_image でデコード、ピクセル直接指定も可） | **実装済み（M2）** |

## 4. レイアウトエンジン

- 全ウィジェットは `measure(constraints) -> desired_size` と `arrange(rect)` を持つ。コンテナは子の measure を集計し、arrange で矩形を割り当てる。
- **Box/Flex（tk_box）**: 方向（縦/横）、spacing、padding、各子の flex 重み（0=自然サイズ、>0=余剰を重み比例配分）、主軸の最小サイズ要求、交差軸の整列（start/center/end/stretch）。CSS flexbox のサブセットであり、order・gap の個別指定・baseline 整列は未実装（差分表に明記）。**flex-wrap は M2 で横方向のみ実装**（縦方向の wrap は未実装。wrap 時は flex 重みを無視する）。
- **Fixed（tk_fixed）**: 子に明示矩形を与える。旧 scenes.c の手置き方式をここにだけ封じ込める移行用コンテナであり、新規画面での常用は想定しない。
- **Grid（M2 実装済み）**: 子は行優先で `cols` 列に流し込む。各列幅/行高は子の希望サイズの最大から決め、余剰は等分、不足は比例縮小する。セルスパン・列重みの個別指定は未実装。
- サイズ制約は min/max を含む constraints 構造で渡す。循環参照（子の希望が親を決め親が子を絞る）は constraints の max で断ち切る、GTK と同型の割り切り。

## 5. イベント配送とヒットテスト

- イベント種別: POINTER_DOWN / UP / MOVE / WHEEL、KEY_DOWN / UP（keysym＋UTF-8 テキスト＋修飾状態）、FOCUS_IN / OUT、TEXT_INPUT（確定文字列）、COMPOSITION（IME 未確定文字列の更新/確定/取消）。
- 配送規則: (1) ルートから座標で最深の可視・有効な子へヒットテスト。(2) 対象ウィジェットへ配送し、処理されなければ親へバブリング。(3) POINTER_DOWN を処理したウィジェットがポインタキャプチャを取り、UP まで MOVE/UP はキャプチャ先へ直行する（Slider のドラッグ、ScrollView のスクロールに必須）。
- キーイベントはフォーカス保持ウィジェットから配送し、バブリングする。未処理の Tab/Shift+Tab はルートがフォーカス移動として消費する。
- ダブルクリック、長押し、ジェスチャ、ホバー（抵抗膜タッチでは意味が薄い）は M1 の対象外として明記する。

## 6. フォーカスチェーン / タブオーダー

- フォーカス可能フラグ（can_focus）を持つウィジェットだけが対象。順序はツリーの深さ優先探索順（＝生成・追加順）を既定とし、明示順序の上書き API は後段。
- tk_focus_next / tk_focus_prev は不可視・無効・can_focus でないウィジェットをスキップし、循環する。
- フォーカス喪失/獲得で FOCUS_IN/OUT を配送し、TextField は獲得時にカーソル表示状態へ遷移する。
- Dialog 実装時にはフォーカストラップ（モーダル内循環）をこの仕組みの上に載せる（M1 未実装）。

## 7. テーマ / デザイントークン

- テーマは値の構造体（tk_theme）: 色（背景/表面/文字/弱文字/アクセント/アクセント上文字/枠/フォーカス/選択/危険）、寸法（余白単位 8px、角丸、行高、コントロール高）、を一箇所に集約する。旧 bui_skin の「OS 再現レイアウト分岐」は継承しない。色テーマの切替はトークン差し替えのみで行い、レイアウトは変えない（ユーザーの単一独自デザイン方針）。
- ウィジェットは色や寸法を直書きせず tk_theme から引く。M1 はライト1テーマ分のトークン値を持ち、ダーク値は後段で同じ構造に足す。

## 8. テキスト編集コア（textcore）との接続

- ストレージは **ギャップバッファ**を採用する。ピーステーブルとの比較: ピーステーブルは大量の小編集と履歴共有に強いが、(a) 当機の編集対象はメモ・設定・フォーム程度のサイズ（数十KB級）でギャップバッファの弱点（離れた位置への連続編集でのギャップ移動コスト）が問題にならない、(b) 行インデックスと Undo を単一バッファ上で素直に実装でき、バグの入り込む面が小さい、(c) メモリ断片化が少なく 128MB 環境で予測可能。以上から M1 はギャップバッファとし、将来の大規模文書対応時にピーステーブルへ差し替え可能なよう、公開 API はバッファ実装を隠蔽する。
- 単位は UTF-8 バイト列＋コードポイント。カーソル移動・削除の既定単位は**書記素クラスタ近似**: コードポイント単位を基礎に、結合文字（U+0300–036F 等の範囲と異体字セレクタ、絵文字修飾子）を前文字に吸着させ、ZWJ 連結は1クラスタとして扱い、国旗（Regional Indicator）は2つ組で扱う。完全な UAX #29 書記素分割・行折り（UAX #14）・双方向（UAX #9）は未実装であり、対象範囲をここに明記する（日本語の通常テキストと一般的な絵文字は上記近似で実用範囲をカバーする想定だが、ゲスト検証は後段）。
- Undo/Redo: 編集操作（挿入/削除、位置と文字列を保持）のスタック。連続入力と連続削除は coalesce（合体）して1履歴にする。履歴上限あり（件数とバイト数の両方）。
- クリップボードは抽象IF（set/get のコールバック＋所有者データ）経由とし、X 選択や Wayland 等の実体はバックエンドが後段で差し込む。textcore 自身は OS のクリップボードに触れない。
- 行レイアウト橋渡し: 行範囲の取得、offset↔(行,列)変換、幅関数（コードポイント→桁数コールバック）による折り返し行の列挙 API を提供し、TextView と描画層はこれを使う。禁則処理・フォント依存の実測幅は描画層の幅関数に委ねる。

## 10. M1 の成果物と検証方法

## 11. M2 実施記録（2026-11-20）

### 11.1 実装したもの

- **残りウィジェット全種の動作実装**: Switch、ProgressBar、TextView、Tabs、Menu（ポップアップ＋サブメニュー＋チェック項目）、MenuBar、Dialog（モーダル、フォーカストラップ、外側クリック嚥下）、ComboBox（Menu 合成）、SpinButton、Separator、ImageView（stb_image デコード＋ピクセル直接指定）、TreeView（展開/折畳み、選択、キー移動）。Grid コンテナと横 Box の flex-wrap も実装。
- **オーバーレイ層**: Menu/Dialog はウィジェットツリーの子ではなく tk_root のオーバーレイとして載る（描画・ヒットテストはツリーより上、モーダル時は入力を独占）。これにより Box レイアウトを壊さずポップアップが出せる。
- **テキスト整形とグリフ描画の実体化**（§11.2）。TextView/TextField の計測・クリック位置決め・折り返しは全て実フォント計測に切替（フォント未設定時のみ近似にフォールバック）。
- **ScrollView ドラッグスクロール**: 子が DOWN を消費する（ボタン等）ケースに備え、ルートにキャプチャ相のジェスチャ認識を入れた。閾値（6px）を超えたら最寄りの ScrollView 祖先がキャプチャを奪い、`suppress_click` でリリース時の誤クリックを防ぐ。解放速度から `tk_scrollview_tick()` で減速する慣性付き。

### 11.2 フォント方針（ロード API とフォールバック）

- **フォントファイルは同梱しない**（同梱の判断は統合フェーズ）。ライブラリは `tk_font_load(path, face_index)` で .ttf/.otf/.ttc を読み、`tk_font_install()` でツールキット全体に設定する。`tk_font_load_default()` はホスト便宜の探索（`$BRAINUI_FONT_PATH` → Noto Sans CJK → DejaVu Sans → Liberation Sans）であり、実機のフォント選定は統合フェーズの判断事項。
- **フォールバック**: `tk_font_set_fallback` でチェーンを作る。コードポイントが主フォントに無ければ次のフォントで計測・描画し、チェーン全体に無ければ主フォントの .notdef を使う。
- **サイズの約束**: `font_px` は **em サイズ**（`stbtt_ScaleForMappingEmToPixels`）。`stbtt_ScaleForPixelHeight` は ascent−descent を px に写すため、Noto Sans CJK（ascent−descent=1448 / em=1000）では全角 advance が 0.69 倍に縮むことを実測で確認し、採用しなかった。em 約束では全角 advance = font_px ちょうどになる。
- **グリフキャッシュ**: フォント毎に最大 1024 グリフ（リング追い出し）、(グリフ番号, px) キー。ラスタライズは初回のみ。
- **禁則処理**: `tk_text_wrap` が JIS X 4051 系の行頭禁止（句読点・小書き仮名・閉じ括弧等）/行末禁止（開き括弧等）を守り、語境界（空白）→禁則を守る任意位置→強制改行の優先順で折る。

### 11.3 近似との差（実測、DejaVu Sans + Noto Sans CJK、font_px=16）

| 文字列 | 等幅近似（M1） | 実フォント（M2） |
|---|---|---|
| "Hello" | 40 | 40（偶然一致） |
| "WWWW" / "iiii" | 32 / 32（区別不能） | 64 / 16 |
| "MMMM" | 32 | 56 |
| 行高 | 21 | 19（DejaVu の hhea 実値） |

## 13. 後続の小規模 API 追加（2026-11-20、アプリ群第2波 §8 の API 不足への対応）

### 13.1 セッタの自動 invalidate 原則

M3 締め（REPORT-toolkit-m3.md §4-1）では「セッタ側での自動 invalidate 化」を推奨として記録したが、既存セッタ群（`tk_label_set_text`、`tk_textfield_set_text` 等）の挙動変更は影響範囲が大きいため、今回は変更しない。代わりに今後の原則を定める:

- **M3 より後に追加するセッタ／状態変更 API は、状態が実際に変化したときに自ら `tk_widget_invalidate()` する**（呼び出し側の明示 invalidate を不要にする）。変化がない呼び出しでは invalidate しない。
- 既存セッタの挙動は当面変えない（アプリ側は従来どおり明示 invalidate を続ける）。既存セッタの自動化は、影響範囲を実測してから別途判断する。

### 13.2 追加した API

- `tk_button_set_label()` — アプリ群第2波 §8-1（ボタンラベルのセッタが存在しない）への対応。§13.1 の原則どおり、ラベルが実際に変わったときだけ invalidate する。bd-player の再生/一時停止ボタンの動的切替（「▶ 再生」⇔「⏸ 一時停止」）に使用。
- `tk_listview_move_row()` と読み取りアクセサ `tk_listview_item()` — 同 §8-2（キューの並べ替え部品がない）への最小対応。ドラッグ並べ替えではなく「行を from から to へ移動する」モデル API とした。文字列はコピーせずポインタを移動するだけ、選択は項目に追随し、選択インデックスが変われば on_select を発火する。実際の移動では invalidate する（§13.1）。UI 側の配線（bd-player のキュー並べ替えボタン等）はアプリラインの作業として残す。

検証: test_tk3 に新規 35 件（ボタンの自動 invalidate とピクセル変化、同値再設定の no-op、ListView の順序・選択追随・範囲外拒否）を追加し、ツールキット全 559 件が PASS。

## 14. M5 実施記録（2026-11-20、ツールキット本格強化）

ユーザー評価「GUI ライブラリの強化がまだまともにできていない」「実機での
見た目の窮屈さと動作の感じも本気で最適化を」を受けた本格フェーズ。
詳細と実測は REPORT-toolkit-m5.md。

### 性能
- スクロールシフト高速パス（root 単位 opt-in `tk_root_set_scroll_blit`）:
  ScrollView の内容が不変で描画済み状態が既知のとき、キャンバス内で
  保持ピクセルを memmove し、露出帯＋スクロールバーのサム移動域
  （旧サムのゴースト域を含む）だけを再描画する。fb flush はデバイス
  メモリ内でシフトを再生し、帯だけを変換する。800×480 のリストで
  スクロールフレーム転送 731,200 B → 24,350 B（−96.7%）
  （M5 時点の実測。当時の撮影キャンバス 800×480 での値であり、
  現行パネルは 854×480・約179.2ppi、AUDIT §20）。
  既定 off の理由: WM クライアントは COMMIT がダメージ矩形のみで
  シフトを伝えられないため。直接 fb のシェルセッション
  （bd_session、fb 保有時のみ）が opt-in 済み。
  正しさは「シフト経路 vs 全再描画の全ピクセル一致」テストで担保
  （test_tk4）。内容変更・部分描画・イベントは dirty 化して確実に
  フォールバックする。
- 描画カリング: tk_paint が clip と交差しないサブツリーをスキップ
  （60 行ツリー中の 1 ラベル再描画 3.5 ms → 0.06 ms）。ListView は
  行単位でもカリング。
- グリフ描画を 1 ピクセル毎の clip/damage からグリフ単位の一括
  ブレンドへ（算術は従来と完全同一）。fill_round_rect は行直接
  書込み化。fb flush は bpp 別特化。

### 動作の感じ（アニメーション基盤、src/tk_anim.c）
- 整数 1 値の時間ベース補間。tk_root_tick 駆動、イージング
  （linear / ease-out / ease-in-out cubic）、標準 160 ms
  （トークン 150–200 ms）。粗いメインループでは中間フレームが
  減るだけで duration は伸びない（劣化方針）。無効化スイッチ
  `tk_root_set_animations_enabled`（UI-REDESIGN の要求どおり）で
  最終値を同期配送。braindesk2 はアニメ中だけステップを 16 ms に
  短縮（~60 fps 目標、実機では帯域が律速し自動的に間引かれる）。
- 適用: Switch ノブのスライド（150 ms）、Dialog の出現
  （+12 px から ease-out）、Menu の出現（−6 px）。浮動面の出現に
  限定しフェードなし（UI-REDESIGN §アニメ制約どおり）。

### API 不足の解消（§9 の差分表とアプリ群レポート §5/§8 の統合分）
- セッタ自動 invalidate の全面化: §13 の原則を旧セッタ全域へ
  （label/textfield/textview/checkbox/radio/slider/progress/
  spinbutton/combobox/listview/tabs/treeview/imageview/menu/
  set_visible/set_enabled）。変化時のみ invalidate。
- textcore 検索: tc_find / tc_find_next（ギャップバッファ越し、
  文書の平坦化コピーなし。ASCII のみ case-fold）。
- 画像: tk_image_scale_to_fit / tk_image_load_thumbnail /
  tk_imageview_load_thumbnail（面積平均＋α 重み、拡大なし）。
- ファイル選択ダイアログ: tk_filedialog_*（Dialog 合成、
  拡張子フィルタ、dirs-first、ドットファイル除外、256 件上限）。
- 日付/時刻ピッカー: TK_W_DATEPICKER / TK_W_TIMEPICKER
  （セグメント＋ステッパー、うるう年込みの日クランプ）。
- ListView 複合行: チェック行（チェックボックスセルは選択を
  変えず on_check 発火）と見出し行（選択不可、キー移動は
  スキップ）。フラグは set_items でリセット、move_row で追随。
- 密度トークン: tk_theme_density(base, level)（行/コントロール
  高さを ×5/4・×3/2。unit とフォントは不変）。
