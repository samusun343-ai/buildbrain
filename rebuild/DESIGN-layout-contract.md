# レイアウト・描画・品質の新契約（2026-11-22）

土台の立て直しの正本。根拠は AUDIT-foundation.md の調査（Android /
WinUI / LVGL の一次資料）。「どの設計をどこから採り、どこを採らな
かったか」を §8 に明記する。例外は実機適合を数値で示せる場合のみ。

## 1. レイアウト契約

1. **レイアウトは「与えられた矩形」の純関数**。アプリとウィジェットは
   ルートに渡された矩形 (w, h) だけから配置を決める。画面寸法
   （854×480 等）をレイアウトの入力にしてはならない。画面寸法を知って
   よいのはシェル（作業領域の計算）と fb フォールバックの初期値だけ。
2. **計測と配置の分離**（Android/WinUI の2パスに倣う）。各ウィジェット
   は「希望寸法（desired）」を返せること。コンテナは希望を聞いてから
   最終矩形を割り当てる。割り当ては親の内容領域を超えない
   （はみ出しはスクロールコンテナの専管事項。それ以外の silent な
   クリップは契約違反）。
3. **寸法はトークン経由のみ**。行高・余白・コントロール寸法はテーマの
   トークン（row_h, row_h2, control_h, pad…）から取る。アプリ内の
   直書き寸法は「その画面固有の設計寸法」だけに許し、理由コメントを
   必須とする。
4. **最小寸法以下での振る舞いは決まった形にする**。潰して描くのでは
   なく、(a) スクロールに逃がす、(b) 省略記号で切り詰める（テキスト）、
   (c) 優先度の低い要素から隠す、のいずれかをコンテナが選ぶ。
   負の寸法・0 寸法の対話要素は生成しない。
5. **密度はテーマの派生で切り替える**。高さが閾値（トークン
   compact_below、初期値 420px）未満の窓では、アプリは
   tk_theme_compact() の派生テーマ（row_h2→row_h 相当への詰め、
   ヘッダの書体一段階縮小）を使い、固定費を先に削る。拡大方向の
   tk_theme_density と対の仕組みとする。

## 2. 窓とバー（insets）の契約

Android WindowInsets の考え方をそのまま採る:

1. バー（ステータス＋ナビ／タスクバー）は**シェルだけが描く**。アプリは
   バー領域を一切描かないし、受け取らない。
2. WM がアプリへ渡すのは「内容矩形」だけ。作業領域＝画面 − バー −
   窓枠、が最大化窓の内容矩形になる。アプリ側に insets の概念は
   漏らさない（渡す矩形が既に差し引き済み）。
3. **最大化は寸法ではなく意図で表す**。アプリは HELLO で
   「最大化で開く」フラグを立てる（寸法 0×0 の要求＝最大化、として
   プロトコルに明記）。854×480 のような実寸要求は浮動窓の希望寸法
   としてのみ意味を持つ。
4. **最小寸法は WM が執行する**。アプリは HELLO で最小寸法を宣言し、
   WM はリサイズ・復元配置を [最小寸法, 作業領域] にクランプする。
   浮動窓の初期配置も作業領域内に収める（下端超えの禁止）。
5. 全画面（バー無し）は明示的な窓状態でのみ。既定にはしない。

## 3. 描画（塗り責任）の契約

Android の「親が子の後ろを描く」原則を、責任の所在として明文化する:

1. **ホスト（bdapp_run / シェル）が最初の所有者**。窓バッファの
   初回フレームとリサイズ後の初回フレームは、必ず全面描画
   （tk_root_paint: キャンバス全面をテーマ背景で消去してから描く）
   でなければならない。fb 直描きモードも同じ（初回は全面）。
2. **差分描画はジャーナルの規律の上でのみ**。前回コミット矩形を
   次バッファへ再無効化する規律（bdapp_run 実装済み）を契約とし、
   これを外れた差分最適化は禁止。
3. **ウィジェットは自分の矩形を塗るか、透明であることを宣言する**。
   透明なウィジェットの下は親が不透明に塗る。結果として「窓矩形内の
   全ピクセルは誰かが塗る」が常に成り立つ。未塗装の黒はバグであり、
   テストでセンチネル色（マゼンタ）を使って機械検出する。
4. シェルの合成も同じ。デスクトップ＋窓＋バーの合成後、画面の
   全ピクセルが決まっていること（壁紙が全面を覆う、窓の角の処理を
   明示する）。

## 4. レイヤ（重なり）の契約

1. 重なり順は固定: デスクトップ（壁紙・アイコン・マスコット）＜
   窓 ＜ シェルのオーバーレイ（履歴・ランチャー・クイック設定）＜ バー。
2. **マスコットはデスクトップ層の住人**。窓が前面にある間は姿を
   出さない（デスクトップが見えている時だけ出る）。例外は作らない
   （従来の「全画面窓だけ隠す」例外はこの規則に吸収される）。

## 5. 表明（invariant）の契約

1. ライブラリ境界に TK_ASSERT を置く: レイアウト入口（w,h ≥ 0）、
   矩形演算（負寸法の禁止）、キャンバス操作（範囲内）、WM 幾何
   （内容矩形 ⊆ 作業領域）。
2. テスト用に tk_root_validate(root) を用意する: 全ウィジェットに
   ついて「矩形が非負」「スクロール外では親の内容領域に収まる」を
   検査する。マトリクステストは全サイズでこれを呼ぶ。
3. TK_ASSERT は NDEBUG で無効化できる（実機の速度を守る）。ただし
   テストビルドでは常時有効。

## 6. 品質ゲート（底上げの合格条件）

| ゲート | 内容 | 合格 |
|---|---|---|
| G-1 サニタイザ | 全テストスイートを ASan+UBSan で実行 | 検出 0 |
| G-2 静的解析 | gcc -fanalyzer を src/・shell/src・apps/common に適用 | 高深刻度の指摘 0（残りは監査文書に理由つきで記録） |
| G-3 ファジング | 入力を受ける部品（brainreg、.desktop パーサ、テキストレイアウト入口）に libFuzzer 形式ハーネス＋種コーパス、各 60 秒以上 | クラッシュ 0 |
| G-4 カバレッジ | gcov で src/・shell/src の行カバレッジを実測し記録 | 数値を報告書に残す（今後の下限とする） |
| G-5 文字列安全 | strcpy/strcat の全廃（境界つき関数へ置換） | 0 件 |
| G-6 レイアウトマトリクス | §7 のマトリクスで全アプリを構築・検証 | 全セル合格 |

## 7. テストマトリクス（網羅の定義）

LVGL の「参照画像比較＋カバレッジ」と、レスポンシブ検証の
「ブレークポイント境界で見る」方法を組み合わせる。

- **サイズ軸**: 854×480（全画面相当）/ 850×368（最大化窓の実寸）/
  480×272（宣言最小）/ 427×240（半分）/ 320×200（最小以下→
  決まった振る舞いの確認）/ 851×367（端数）/ 480×800（縦向き:
  プレビュー系のみ）
- **モード軸**: android / winui（テーマが変わる）
- **明暗軸**: light / dark
- **状態軸**: 標準データ / 空 / 長い文字列 / 多数項目
- **自動検査（全セル）**: tk_root_validate、センチネル塗り検査
  （四隅＋全ピクセルの未塗装検出）、対話要素の最小寸法
- **ゴールデン比較**: 代表セル（最大化窓×両モード×明暗）は PPM の
  ハッシュを tests/golden/ に保存し、差分が出たら目視で承認して
  更新する（LVGL の ref_imgs 方式）
- ゲストでは実寸（最大化窓・両モード）の撮影で最終照合する。

## 8. 採った設計・採らなかった設計

| 設計 | 出所 | 採否 | 理由 |
|---|---|---|---|
| measure/arrange の概念分離（希望寸法→割当て） | Android / WinUI | **採る**（実装は既存の desired＋flex を契約化） | レイアウト破綻の型を「希望と割当ての不一致」として検査可能にするため |
| WindowInsets（バーはシェル所有、内容矩形だけ渡す） | Android | **採る** | ユーザー決定（バー常時表示＋切替可能）と一致。アプリにバーを意識させない |
| 遅延レイアウト（dirty にして描画前に解消） | LVGL | **採る**（既存の invalidate 方式を契約化） | 128MB・低速 CPU で都度全再計算は無駄。既存実装も同方式 |
| border-box・スタイル保持の寸法 | LVGL/CSS | 部分的に採る | 寸法のトークン化は採る。スタイルオブジェクトの全面導入は既存テーマ構造で代替済みのため見送り |
| 完全な2パスの再帰 measure（MeasureSpec の3モード） | Android | **採らない** | 実機適合: 現行 flex＋desired で同じ保証（§1-2 の検査）が得られ、全ウィジェットの作り替えは 128MB 環境での検証コストに見合わない。保証は検証器（§5-2）で担保する |
| XAML の非同期レイアウトキュー | WinUI | **採らない** | 単一スレッド・即時描画の現行ループで足りる。遅延は LVGL 方式（dirty フラグ）で既に実現 |
| スクリーンショット参照比較＋カバレッジ CI | LVGL | **採る**（§6/§7） | 目視頼みをやめるための核 |
| ASan/UBSan 常時＋libFuzzer | LLVM / OSS-Fuzz の実務 | **採る**（§6） | メモリ誤りの検出は人手では不可能 |
