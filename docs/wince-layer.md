# WinCE アプリ互換レイヤー設計 (BrainCE Layer)

Brainux (Linux) の上で、eMMC の WinCE 領域にある WinCE アプリケーションを
そのまま実行するための互換レイヤーの設計。Wine / WSL と同じ発想で、
**エミュレーションではなく API/ABI 翻訳**で動かす。

## なぜ「ほぼネイティブ」が成り立つか

- PW-SH6 の SoC は i.MX283 (ARM926EJ-S)。WinCE バイナリも Linux バイナリも
  同じ ARM 命令セットのリトルエンディアン PE/ELF であり、CPU 命令は
  翻訳なしにそのまま実行できる。QEMU のような命令エミュレーションは不要。
- 必要なのは (1) PE ローダ、(2) coredll を中心とする WinCE API の
  Linux 実装 (シム)、(3) WinCE のファイルシステム名前空間の再現、の3点。
- WinCE のファイルシステムは eMMC 上の実物を使う。実機では WinCE 領域を
  マウントし、CE 名前空間 (`\Windows`, `\Program Files` 等) の実体にする。
  アプリから見れば「いつもの場所にいつものファイルがある」状態になる。

## 難しいのはメモリモデルと ABI

- WinCE (CE 6 系) のプロセスは 32MB スロット前提のアドレス配置や
  DLL の固定スロット配置など、Linux のプロセスモデルと異なる前提を持つ。
  ローダ側でアドレス空間を予約し、CE の配置規則に合わせてマップする
  (Wine の preloader と同じ問題設定)。
- ARM の呼び出し規約は AAPCS と近いが、構造体返し・TLS・例外処理で差がある。
  シム DLL は CE 側 ABI に合わせてビルドし、Linux 側との境界で変換する。
- GWE (グラフィックス/ウィンドウ) は最大の作業量。CE の HWND/メッセージ
  モデルを libbrainui のサーフェス、または X11 のウィンドウへ写像する
  「CE ウィンドウサーバ」を置く。辞書アプリのような素直な GWE アプリが
  第一目標で、ドライバ直叩きのアプリは対象外から始める。

## コンポーネント

1. **ce-loader**: PE パーサ、再配置、インポート解決 (シム DLL へ束縛)、
   binfmt_misc 登録で `.exe` を直接起動可能に。
2. **coredll シム**: ファイル、メモリ、スレッド、同期、レジストリ、
   文字列/ロケール。公開ドキュメント (Microsoft の WinCE API 資料) を
   仕様として実装する。
3. **GWE シム**: ウィンドウ、メッセージループ、GDI 基本描画、入力
   (キーボード/タッチ) の写像。
4. **FS ブリッジ**: CE パス → 実マウントへの変換、大文字小文字の
   非区別、レジストリハイブの実ファイル参照。
5. **段階的スタブ**: 未実装 API はログ付きスタブで返し、実アプリの
   要求に応じて実装範囲を広げる (Wine の開発方式)。

## マイルストーン

- **M0** 本設計。
- **M1** ローダ + 最小 coredll で、ファイル書き込みだけを行う自作
  テスト用 CE バイナリが Linux 上で動く。
- **M2** GWE 最小実装で MessageBox 級の GUI が出る。
- **M3** 実アプリ (単機能のもの) が実機で起動する。
- **M4** 辞書級アプリの実用化、FS ブリッジ完成。

## 前提と制約

- 仕様は公開資料とブラックボックス観察のみから取る (本プロジェクト共通の
  法的制約)。eMMC の解析はしない。CE 領域のマウントと観察は実機上で
  ユーザ自身のデータを対象に行う。
- テスト用 CE バイナリの自作は QEMU プロジェクト側で実証済み
  (カスタムアプリ起動 p20-B) のビルド経路を流用できる。
- これは長期フェーズであり、braindesk 本体の完成を妨げない順序で進める。
